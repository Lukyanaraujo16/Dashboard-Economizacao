# Dashboard Economização

# 09.1 — Estrutura do Projeto

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define a organização física e modular oficial do repositório do Dashboard Economização.

Ele responde, de forma definitiva, às seguintes perguntas:

- onde cada tipo de código deve morar;
- qual é a responsabilidade de cada diretório de primeiro nível;
- quem pode importar quem;
- quando um novo módulo deve ser criado;
- onde termina a infraestrutura e onde começa o domínio;
- o que nunca deve ser criado no repositório.

A estrutura definida aqui é a materialização da ADR-033 (Estrutura Física do Repositório) e da ADR-034 (Estratégia de Monorepositório).

Este documento não define arquitetura conceitual. Isso pertence ao documento `02-arquitetura.md`. Aqui é definido apenas onde essa arquitetura vive em disco.

---

# 2. Escopo

Este documento regula:

- os diretórios de primeiro nível do repositório;
- a responsabilidade de cada aplicação (`frontend/`, `backend/`, `worker/`);
- a responsabilidade de cada pacote compartilhado (`packages/*`);
- a responsabilidade da infraestrutura (`infrastructure/*`);
- a localização do schema de dados (`prisma/`);
- a localização da documentação (`docs/`);
- a localização da automação de repositório (`.github/`);
- as regras de importação entre pacotes;
- a política de criação de novos módulos e novos pacotes;
- a política de crescimento futuro do monorepositório.

Este documento não regula:

- arquitetura interna do backend — ver `09.3-backend.md`;
- arquitetura interna do frontend — ver `09.4-frontend.md`;
- convenções de tipagem — ver `09.2-convencoes-typescript.md`;
- modelagem de dados — ver `03-modelagem-banco.md` e `09.5-banco-de-dados.md`.

# 3. Regras Obrigatórias

## 3.1 Estrutura oficial de primeiro nível

O repositório deverá possuir exatamente a seguinte estrutura de primeiro nível, conforme ADR-033:

```
frontend/
backend/
worker/
packages/
infrastructure/
prisma/
docs/
.github/
```

Nenhum outro diretório de código de aplicação deverá ser criado no primeiro nível do repositório sem alteração formal da ADR-033.

Arquivos de configuração de raiz (`package.json`, `pnpm-workspace.yaml`, `tsconfig.base.json`, `eslint.config.mjs`, `prettier.config.mjs`, `.editorconfig`, `.env.example`, `README.md`) permanecem na raiz e não constituem exceção a esta regra.

## 3.2 Monorepositório simples

O monorepositório utiliza pnpm workspaces como único mecanismo de composição dos pacotes, conforme ADR-038, que estabelece o pnpm como gerenciador de pacotes oficial do projeto.

Não deverá ser adotado Turborepo, Nx, Rush, Lerna, Bazel ou qualquer orquestrador equivalente durante o MVP, conforme ADR-034.

A orquestração de tarefas deverá ocorrer por meio de scripts no `package.json` da raiz utilizando execução recursiva do pnpm.

## 3.3 Nomenclatura dos pacotes

Todo pacote do workspace deverá utilizar o escopo oficial `@dashboard-economizacao/`.

Nomes oficiais:

| Diretório | Nome do pacote |
|---|---|
| `frontend/` | `@dashboard-economizacao/frontend` |
| `backend/` | `@dashboard-economizacao/backend` |
| `worker/` | `@dashboard-economizacao/worker` |
| `packages/shared/` | `@dashboard-economizacao/shared` |
| `packages/types/` | `@dashboard-economizacao/types` |
| `packages/config/` | `@dashboard-economizacao/config` |
| `packages/ui/` | `@dashboard-economizacao/ui` |

Dependências internas deverão ser declaradas explicitamente no `package.json` do consumidor utilizando o protocolo `workspace:*`.

## 3.4 Proibição de import por caminho relativo entre pacotes

Código de um pacote nunca deverá alcançar outro pacote por caminho relativo.

Proibido:

```ts
import { formatCurrency } from '../../../packages/shared/src/money';
```

Obrigatório:

```ts
import { formatCurrency } from '@dashboard-economizacao/shared';
```

Caminhos relativos são permitidos apenas dentro do próprio pacote.

## 3.5 Todo diretório deve ter responsabilidade declarada

Não é permitido criar diretório cuja responsabilidade não possa ser descrita em uma frase objetiva.

Nomes proibidos por serem semanticamente vazios:

- `utils/` genérico no topo de uma aplicação;
- `helpers/`;
- `common/`;
- `misc/`;
- `core/` sem escopo definido;
- `lib/` usado como depósito;
- `stuff/`, `temp/`, `new/`, `old/`, `v2/`.

Se não é possível nomear a responsabilidade, o código provavelmente pertence a um módulo existente.

## 3.6 Proibição de arquivos "utils" gigantes

Não deverá existir arquivo do tipo `utils.ts` acumulando funções sem relação entre si.

Toda função utilitária deverá viver em um arquivo nomeado pelo domínio técnico ao qual pertence.

Proibido:

```
packages/shared/src/utils.ts   (450 linhas, 38 funções não relacionadas)
```

Obrigatório:

```
packages/shared/src/money/format-currency.ts
packages/shared/src/money/round-monetary.ts
packages/shared/src/date/resolve-period.ts
packages/shared/src/date/compare-periods.ts
packages/shared/src/text/slugify.ts
```

Limite operacional de revisão: um arquivo de utilitário com mais de 150 linhas ou mais de 5 exportações não relacionadas deverá ser dividido.

## 3.7 Proibição de duplicação entre frontend e backend

Regra de negócio, cálculo financeiro, tipo de contrato de API, enumeração de domínio e mensagem de validação compartilhada nunca deverão existir em duas implementações — uma no `frontend/` e outra no `backend/`.

Se um conceito é necessário nas duas pontas, ele pertence a `packages/types/` (contrato) ou `packages/shared/` (comportamento puro).

Exemplos concretos de itens que devem ser compartilhados e não duplicados:

- nomes e chaves oficiais dos indicadores financeiros;
- enumeração de status de sincronização da integração Conta Azul;
- enumeração de severidade de insight;
- enumeração de papéis (usuário de empresa, administrador, superadministrador);
- formato dos filtros de período aceitos pela API;
- formatação monetária e de percentual exibida ao usuário.

Atenção: compartilhar formatação não significa compartilhar cálculo autoritativo. O cálculo oficial dos indicadores permanece no Motor Analítico dentro do `backend/`, conforme ARQ-010 e ARQ-011. O frontend consome o resultado; nunca recalcula.

## 3.8 Isolamento de tenant não é compartilhável

Nenhuma decisão de isolamento por tenant, autorização ou validação de permissão deverá residir em `packages/*` ou no `frontend/`.

Essas decisões pertencem exclusivamente ao `backend/`, conforme ARQ-002 e ARQ-013.

`packages/types/` pode declarar o tipo `TenantId`. Não pode declarar quem tem acesso a ele.

# 4. Padrões Aprovados

## 4.1 `frontend/` — Aplicação Next.js

Responsabilidade: interface do usuário do painel do cliente e do painel administrativo.

Contém:

- rotas e páginas Next.js;
- componentes de tela e composição visual;
- estado de interface;
- clientes HTTP que consomem a API do backend;
- resolução e aplicação de tema/branding do tenant;
- formatação e apresentação de dados já calculados.

Não contém:

- regra de negócio financeira;
- cálculo autoritativo de indicador;
- decisão de autorização;
- acesso ao PostgreSQL;
- acesso ao Redis;
- token, segredo ou credencial da Conta Azul;
- chamada direta à API da Conta Azul.

As API Routes do Next.js não constituem o núcleo da aplicação (ADR-006). Elas podem existir apenas para necessidades estritamente de frontend, como handoff de sessão, health check da própria aplicação web ou proxy de leitura sem regra de negócio.

## 4.2 `backend/` — API Fastify

Responsabilidade: autoridade de negócio da plataforma.

É o único componente autorizado a:

- decidir autorização e escopo de tenant;
- executar regras de negócio;
- calcular indicadores oficiais;
- acessar o banco de dados de escrita;
- manipular credenciais da Conta Azul;
- enfileirar jobs no BullMQ.

A arquitetura interna do backend (módulos, rotas, serviços, repositórios, adapters) é definida em `09.3-backend.md`.

## 4.3 `worker/` — Processos assíncronos

Responsabilidade: execução de jobs BullMQ fora do ciclo de requisição HTTP, conforme ADR-011 e ADR-012.

Contém:

- consumidores de fila (processors);
- registro e configuração das filas;
- responsabilidade de scheduler para tarefas recorrentes;
- orquestração de sincronizações da Conta Azul;
- recálculo analítico, geração de insights, geração de relatórios pesados, entrega de notificações.

Regra estrutural fundamental: o `worker/` não reimplementa regra de negócio.

O worker é uma casca de execução. Ele resolve o contexto do job, invoca o caso de uso apropriado do `backend/` e registra o resultado.

Se uma lógica precisa existir tanto em uma rota HTTP quanto em um job, ela pertence a um serviço/caso de uso do `backend/`, importado pelo worker — nunca copiado.

O `worker/` é um processo separado e deve poder ser reiniciado, escalado ou movido de máquina sem alterar o `backend/` (ADR-026).

## 4.4 `packages/types/` — Contratos

Responsabilidade: contratos de tipo compartilhados entre aplicações.

Contém:

- tipos de requisição e resposta da API;
- tipos de payload de job das filas;
- o registro tipado de eventos de `docs/09.16-eventos.md` e o registro tipado de filas e payloads de `docs/09.14-filas.md`, por serem contratos compartilhados entre processos;
- identificadores de domínio (`TenantId`, `UserId`, `SyncRunId`);
- enumerações de domínio (status de sincronização, severidade de insight, papéis, tipos de relatório);
- tipos de filtro analítico e período.

Restrições:

- não contém implementação executável;
- não contém dependência de runtime;
- não importa `packages/shared`, `packages/ui`, `frontend`, `backend` ou `worker`;
- não reexporta tipos gerados pelo Prisma.

Motivo da última restrição: o modelo de persistência é detalhe interno do backend. Expor tipos do Prisma via `packages/types` acoplaria o frontend ao schema do banco.

## 4.5 `packages/shared/` — Lógica pura compartilhada

Responsabilidade: funções puras, determinísticas e sem efeito colateral utilizadas por mais de uma aplicação.

Contém:

- formatação monetária, percentual e numérica no padrão brasileiro;
- resolução de períodos e intervalos de datas;
- comparação e normalização de rótulos de período;
- validação de formato puramente estrutural;
- constantes de domínio estáveis;
- erros de domínio compartilhados.

Restrições:

- proibido acesso a rede;
- proibido acesso a disco;
- proibido acesso a banco de dados ou Redis;
- proibido uso de `process.env`;
- proibido import de React, Fastify, Prisma ou BullMQ;
- pode importar `packages/types`.

Regra prática de revisão: se a função não pode ser testada sem mock, ela não pertence a `packages/shared`.

## 4.6 `packages/config/` — Configuração compartilhada de ferramentas

Responsabilidade: configuração de ferramentas de desenvolvimento reutilizada pelos pacotes.

Contém:

- presets de `tsconfig` derivados de `tsconfig.base.json`;
- fragmentos compartilhados de ESLint;
- configuração compartilhada de testes;
- constantes de build compartilhadas.

Restrições:

- não contém segredo;
- não contém valor de ambiente de produção;
- não contém regra de negócio.

Valores de ambiente permanecem em `.env` e em `.env.example`. A validação do ambiente de execução pertence a cada aplicação, não a este pacote.

## 4.7 `packages/ui/` — Design System

Responsabilidade: componentes visuais reutilizáveis entre o painel do cliente e o painel administrativo.

Contém:

- componentes de apresentação sem estado de domínio;
- primitivas visuais (botões, campos, tabelas, cards, gráficos base);
- tokens de tema compatíveis com o branding por tenant.

Restrições:

- não faz chamada HTTP;
- não conhece rota da aplicação;
- não conhece `TenantId`;
- não decide permissão;
- não busca dado próprio.

Todo dado entra por props. Um componente de `packages/ui` deve renderizar corretamente em isolamento total.

Consumidor exclusivo: `frontend/`. `backend/` e `worker/` nunca importam `packages/ui`.

## 4.8 `infrastructure/docker/` — Imagens

Responsabilidade: Dockerfiles das aplicações e artefatos de build de imagem.

Contém um Dockerfile por processo executável: frontend, backend, worker.

Não contém orquestração, nem valor de ambiente concreto.

## 4.9 `infrastructure/compose/` — Orquestração

Responsabilidade: arquivos Docker Compose que descrevem a topologia de execução.

Contém a composição de frontend, API, worker/scheduler, PostgreSQL, Redis e Nginx, conforme ADR-003, ADR-004 e ADR-025.

Volumes persistentes de PostgreSQL e Redis são declarados aqui.

Segredos nunca são escritos nestes arquivos; são referenciados por variável de ambiente.

## 4.10 `infrastructure/nginx/` — Proxy reverso

Responsabilidade: configuração do Nginx como proxy reverso, conforme ADR-013, ADR-014 e ADR-015.

Contém roteamento para frontend e API, terminação TLS, headers de segurança e templates de configuração para os cenários com e sem domínio.

## 4.11 `infrastructure/scripts/` — Operação

Responsabilidade: scripts operacionais da VPS, conforme ADR-016 a ADR-024.

Contém `install.sh`, `update.sh`, `backup.sh`, `restore.sh` e utilitários de apoio.

Restrições:

- scripts operacionais não contêm regra de negócio;
- scripts devem ser idempotentes sempre que tecnicamente viável (ADR-019);
- operações destrutivas exigem confirmação explícita;
- cada script tem uma responsabilidade única e não é fundido com outro.

## 4.12 `prisma/` — Schema e migrations

Responsabilidade: fonte única do schema de dados e das migrations, conforme ADR-007 e ADR-008.

Contém `schema.prisma`, migrations versionadas e seeds quando necessários.

O diretório vive na raiz e não dentro do `backend/` porque o schema é ativo compartilhado entre backend, worker e operação (migrations executadas pelo instalador e pelo `update.sh`).

Restrições:

- somente o `backend/` e o `worker/` consomem o Prisma Client;
- o `frontend/` nunca importa Prisma Client, direta ou indiretamente;
- alteração de schema sempre acompanhada de migration versionada.

## 4.13 `docs/` — Documentação oficial

Responsabilidade: documentação de produto, arquitetura, decisões e padrões.

A numeração é significativa e estável: `00`–`08` definem o produto e as decisões; a série `09.x` define como implementar.

Documentação de padrão de desenvolvimento não vive em README de subpasta nem em comentário de código. Vive aqui.

## 4.14 `.github/` — Automação de repositório

Responsabilidade: workflows de CI, templates de issue e pull request.

Contém a verificação obrigatória de lint, typecheck, testes e build.

Não contém segredo em texto claro.

## 4.15 Matriz oficial de dependências

Direção permitida de importação:

| De ↓ / Para → | types | shared | config | ui | backend | worker | frontend |
|---|---|---|---|---|---|---|---|
| `packages/types` | — | não | não | não | não | não | não |
| `packages/shared` | sim | — | não | não | não | não | não |
| `packages/config` | não | não | — | não | não | não | não |
| `packages/ui` | sim | sim | sim | não | não | não | não |
| `backend` | sim | sim | sim | não | — | não | não |
| `worker` | sim | sim | sim | não | sim | — | não |
| `frontend` | sim | sim | sim | sim | não | não | — |

Leitura das regras críticas:

- o grafo de dependências é acíclico;
- `frontend` nunca importa `backend`;
- `backend` nunca importa `frontend`;
- `worker` importa `backend` para reutilizar casos de uso; a recíproca é proibida;
- `packages/*` nunca importa aplicação.

## 4.16 Organização interna por feature

Dentro de `backend/`, `worker/` e `frontend/`, a organização primária é por feature de domínio, não por tipo técnico.

Aprovado:

```
backend/src/modules/tenants/
backend/src/modules/auth/
backend/src/modules/integrations/conta-azul/
backend/src/modules/sync/
backend/src/modules/analytics/
backend/src/modules/insights/
backend/src/modules/advisor/
backend/src/modules/reports/
backend/src/modules/notifications/
backend/src/modules/audit/
```

Reprovado:

```
backend/src/controllers/
backend/src/services/
backend/src/repositories/
```

Motivo: agrupar por tipo técnico obriga o desenvolvedor a abrir quatro diretórios distantes para entender uma única feature, e faz o acoplamento entre features passar desapercebido em revisão.

A estrutura interna de cada módulo é definida em `09.3-backend.md`.

## 4.17 Propriedade de feature

Cada feature de domínio possui exatamente um módulo proprietário.

O módulo proprietário é o único autorizado a:

- persistir as entidades daquele domínio;
- expor casos de uso daquele domínio;
- definir os contratos daquele domínio.

Outros módulos consomem a feature pela interface pública do módulo proprietário. Nunca acessam as tabelas ou os arquivos internos de outro módulo.

Exemplo: o módulo `analytics` não escreve na tabela de sincronização; ele consulta o caso de uso publicado por `sync`.

## 4.18 Quando criar um novo módulo

Um novo módulo deverá ser criado quando **todas** as condições abaixo forem verdadeiras:

1. representa um conceito de negócio nomeável do Dashboard Economização;
2. possui entidades ou casos de uso próprios;
3. poderia ser descrito isoladamente no PRD;
4. sua remoção não deixaria o restante do sistema incoerente por dependência oculta.

Um novo módulo **não** deverá ser criado quando:

- existir apenas para abrigar uma função;
- for apenas uma variação de um módulo existente;
- representar uma tela e não um domínio;
- for criado por antecipação a uma funcionalidade não aprovada no roadmap (ADR-035).

Na dúvida, o código deve nascer dentro do módulo existente mais próximo. Extrair um módulo depois é barato; desfazer um módulo prematuro que já espalhou dependências é caro.

## 4.19 Quando criar um novo pacote

A criação de novo diretório em `packages/` exige justificativa registrada em ADR.

Critério mínimo: o código precisa ser consumido por, no mínimo, duas aplicações distintas e não pertencer conceitualmente a nenhum dos quatro pacotes existentes.

Reutilização por uma única aplicação não justifica pacote. Justifica módulo interno.

## 4.20 Separação entre infraestrutura e domínio

Duas noções distintas de "infraestrutura" coexistem no projeto e não devem ser confundidas:

**Infraestrutura de plataforma** — `infrastructure/`.

Descreve como o sistema é executado, empacotado, exposto e operado: Docker, Compose, Nginx, TLS, scripts de instalação e backup.

Não conhece regra de negócio. Nunca importa código de aplicação.

**Infraestrutura técnica de aplicação** — `backend/src/infrastructure/`, `worker/src/infrastructure/`.

Contém adaptadores para recursos externos ao processo: cliente Prisma, cliente Redis, conexões BullMQ, cliente HTTP, cliente do provedor de IA, storage de arquivos, logger.

Não contém regra de negócio. Expõe capacidade técnica consumida pelo domínio.

**Domínio** — `backend/src/modules/*/domain/`.

Contém regras de negócio do Dashboard Economização: cálculo de inadimplência, regras de fluxo de caixa, regras de geração de insight, políticas de deduplicação de alerta.

Não conhece Fastify, HTTP, Prisma, Redis nem BullMQ.

Regra de dependência: domínio nunca depende de infraestrutura concreta. Quando o domínio precisa de um recurso externo, ele declara a interface e a infraestrutura fornece a implementação.

# 5. Padrões Proibidos

São expressamente proibidos:

1. **Turborepo, Nx ou orquestrador equivalente** — viola ADR-034.
2. **Diretório de primeiro nível fora da ADR-033** — nenhum `apps/`, `libs/`, `src/` na raiz, `api/`, `server/` ou `web/`.
3. **Import relativo atravessando fronteira de pacote** — todo `../../packages/` é erro de estrutura.
4. **Diretório genérico sem responsabilidade** — `utils/`, `helpers/`, `common/`, `misc/`, `core/` sem escopo.
5. **Arquivo `utils.ts` acumulador** — depósito de funções não relacionadas.
6. **Duplicação de regra entre frontend e backend** — dois cálculos para o mesmo indicador.
7. **Cálculo autoritativo de indicador no frontend** — viola ARQ-010 e ARQ-011.
8. **Prisma Client no frontend** — direta ou transitivamente.
9. **Acesso a banco ou Redis a partir de `packages/*`**.
10. **`packages/ui` importando `packages/config` de runtime, fazendo fetch ou conhecendo tenant**.
11. **Regra de negócio duplicada no `worker/`** — worker orquestra, não reimplementa.
12. **Segredo versionado** em `infrastructure/`, `packages/config/` ou `.github/`.
13. **`backend/` importando `frontend/`** ou qualquer dependência cíclica entre pacotes.
14. **Módulo acessando tabela de outro módulo** diretamente.
15. **Diretórios de versão paralela** — `v2/`, `new/`, `old/`, `legacy/`, `backup/`, `copia/`.
16. **Código morto mantido comentado** em lugar de removido e recuperável via Git.
17. **Reexportação de tipos do Prisma via `packages/types`**.
18. **Módulo criado por antecipação** a funcionalidade não aprovada no roadmap.
19. **Configuração de ambiente de produção versionada** fora de `.env.example`.
20. **Documentação de padrão fora de `docs/`**.

# 6. Exemplos Conceituais

## 6.1 Onde vive o cálculo de inadimplência

O indicador de inadimplência precisa aparecer no card da dashboard, no relatório em PDF e na análise do Consultor Financeiro (ARQ-011).

Distribuição correta:

```
packages/types/src/analytics/indicators.ts
  → chave oficial do indicador e formato da resposta

backend/src/modules/analytics/domain/delinquency.ts
  → regra oficial de cálculo (fonte única)

backend/src/modules/analytics/services/get-dashboard-indicators.ts
  → caso de uso consumido pela rota HTTP

backend/src/modules/reports/services/build-financial-report.ts
  → consome o mesmo domínio analítico

backend/src/modules/advisor/services/build-advisor-context.ts
  → consome o mesmo domínio analítico

packages/shared/src/money/format-currency.ts
  → apresentação do valor, sem cálculo

frontend/src/features/dashboard/components/delinquency-card.tsx
  → exibe o valor já calculado
```

Distribuição incorreta:

```
frontend/src/features/dashboard/utils/calc-delinquency.ts   ← proibido
worker/src/jobs/analytics/calc-delinquency.ts               ← proibido (duplicação)
packages/shared/src/delinquency.ts                          ← proibido (regra de negócio em pacote puro)
```

## 6.2 Onde vive a integração com a Conta Azul

Separação obrigatória entre conector e normalizador (ARQ-005, ARQ-006):

```
backend/src/modules/integrations/conta-azul/
  connector/        → OAuth, chamadas HTTP, paginação, rate limit, erros externos
  normalizer/       → tradução do formato Conta Azul para o modelo interno
  contracts/        → interface ExternalERPConnector
  schemas/          → validação da resposta externa
```

O `connector/` nunca gera KPI. O `normalizer/` nunca faz chamada HTTP. Nenhum campo com nome originado da API da Conta Azul atravessa a fronteira do `normalizer/`.

## 6.3 Fluxo de uma sincronização entre diretórios

```
worker/src/jobs/sync/sync-tenant-financials.ts
  → resolve contexto do job, invoca caso de uso, registra resultado

backend/src/modules/sync/services/run-tenant-sync.ts
  → orquestra a sincronização (regra)

backend/src/modules/integrations/conta-azul/connector/
  → busca dados externos

backend/src/modules/integrations/conta-azul/normalizer/
  → traduz para o modelo interno

backend/src/modules/sync/repositories/
  → persiste de forma idempotente (ARQ-009)

backend/src/modules/analytics/services/
  → recalcula dados derivados
```

O job do worker deve permanecer curto. Se um arquivo em `worker/src/jobs/` cresce além da orquestração, é sinal de que regra de negócio vazou para o processo errado.

## 6.4 Decidindo o destino de um novo trecho de código

```
O código decide permissão ou escopo de tenant?
  → backend/src/modules/<feature>/   (nunca em packages ou frontend)

O código é regra de negócio financeira?
  → backend/src/modules/<feature>/domain/

O código fala com PostgreSQL, Redis, BullMQ, HTTP externo ou IA?
  → backend/src/infrastructure/  ou  worker/src/infrastructure/

O código é função pura usada por mais de uma aplicação?
  → packages/shared/<domínio-técnico>/

O código é apenas um tipo ou enumeração compartilhada?
  → packages/types/

O código é componente visual sem estado de domínio?
  → packages/ui/

O código descreve como o sistema roda ou é implantado?
  → infrastructure/

Nenhuma das opções acima?
  → o código provavelmente pertence ao módulo existente mais próximo;
    não crie novo diretório para acomodá-lo.
```

# 7. Critérios de Revisão

Um commit em `main` ou a integração de uma branch de trabalho deverá ser recusado quando:

1. criar diretório de primeiro nível fora da ADR-033;
2. introduzir Turborepo, Nx ou orquestrador equivalente;
3. conter import relativo atravessando fronteira de pacote;
4. criar diretório ou arquivo genérico sem responsabilidade declarável;
5. adicionar função a um `utils.ts` acumulador em vez de criar arquivo nomeado;
6. duplicar regra, tipo, enumeração ou cálculo entre `frontend/` e `backend/`;
7. implementar cálculo autoritativo de indicador fora do Motor Analítico;
8. introduzir dependência do Prisma Client no `frontend/`;
9. introduzir acesso a rede, disco, banco ou `process.env` em `packages/shared`;
10. fazer `packages/ui` executar fetch, conhecer rota ou conhecer tenant;
11. reimplementar regra de negócio no `worker/` em vez de invocar caso de uso do `backend/`;
12. violar a matriz de dependências da seção 4.15;
13. criar dependência cíclica entre pacotes;
14. acessar tabela ou arquivo interno de outro módulo;
15. criar módulo novo sem atender aos quatro critérios da seção 4.18;
16. criar pacote novo em `packages/` sem ADR correspondente;
17. misturar regra de negócio em `infrastructure/`;
18. versionar segredo ou configuração de produção;
19. criar diretório de versão paralela;
20. deixar código morto comentado.

Checklist objetivo de revisão estrutural:

- [ ] A estrutura de primeiro nível permanece igual à ADR-033.
- [ ] Todo novo arquivo está em um diretório com responsabilidade clara.
- [ ] Nenhum import cruza fronteira de pacote por caminho relativo.
- [ ] A matriz de dependências da seção 4.15 é respeitada.
- [ ] Nenhum conceito foi duplicado entre frontend e backend.
- [ ] Regra de negócio está em `modules/*/domain/`, não em infraestrutura.
- [ ] Decisão de tenant e autorização permanece no backend.
- [ ] Nenhum arquivo utilitário ultrapassou o limite da seção 3.6.
- [ ] `pnpm lint`, `pnpm typecheck` e `pnpm build` passam na raiz.

# 9. Diretriz Final

A estrutura do Dashboard Economização é deliberadamente simples: três aplicações, quatro pacotes compartilhados, uma pasta de infraestrutura, um schema de dados.

Essa simplicidade não é provisória — é o padrão aprovado. Ela existe para que qualquer pessoa consiga localizar qualquer trecho de código em segundos, e para que o crescimento do produto não exija reorganização estrutural.

O crescimento futuro deverá ocorrer **dentro** desta estrutura, adicionando módulos de domínio, e não **acima** dela, adicionando camadas de orquestração.

Toda dúvida sobre onde colocar código deverá ser resolvida por este documento antes da implementação, nunca durante a revisão.
