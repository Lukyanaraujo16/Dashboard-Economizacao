# Dashboard Economização

# 09.4 — Frontend

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define o padrão oficial de desenvolvimento do frontend do Dashboard Economização.

O frontend do projeto é construído com Next.js e TypeScript, conforme ADR-005 (Next.js + TypeScript) e ADR-006 (backend separado do Next.js) do documento 08.

O App Router é o padrão obrigatório de roteamento do projeto, conforme ADR-039.

O objetivo deste padrão é garantir que a camada de interface:

- apresente informação financeira de forma correta, previsível e consistente;
- respeite integralmente o contrato de experiência definido no documento 05;
- permaneça uma camada de apresentação, nunca uma camada de autoridade de negócio;
- consuma exclusivamente a API interna do Dashboard Economização;
- respeite o isolamento multiempresa em toda a superfície visual;
- possua estados completos de carregamento, erro e ausência de dados;
- seja responsiva e acessível desde a primeira implementação;
- permaneça manutenível conforme o produto cresce em telas e indicadores.

Este documento regula como implementar o frontend.

Ele não redefine funcionalidades, telas ou fluxos, que pertencem aos documentos 01 e 05.

---

# 2. Escopo

Este documento se aplica a todo código contido em `frontend/`.

Estão dentro do escopo:

- organização do App Router;
- fronteira entre Server Components e Client Components;
- páginas e rotas;
- layouts e shells de navegação;
- componentes de domínio e componentes visuais;
- hooks;
- serviços de acesso à API interna;
- gerenciamento de estado;
- estados de loading, erro e vazio;
- formulários e validação de entrada na interface;
- formatação e apresentação de valores financeiros, datas e percentuais;
- acessibilidade;
- responsividade;
- tema e branding aplicados na interface;
- reuso e composição de componentes.

Estão fora do escopo deste documento:

- escolha de biblioteca de UI;
- escolha de biblioteca de gráficos;
- definição de paleta, tipografia, grid e demais itens de design visual;
- regras de negócio financeiras, que pertencem ao backend;
- contrato da API interna, definido no documento 09.6;
- integração com Conta Azul, definida no documento 04 e implementada exclusivamente no backend.

# 3. Regras Obrigatórias

## 3.1 O backend é a autoridade

O frontend é uma camada de apresentação e interação.

Toda regra de negócio, cálculo financeiro oficial, decisão de autorização e normalização de dados pertence ao backend.

O frontend deverá exibir o resultado produzido pelo backend, não recalculá-lo para reinterpretar a realidade financeira da empresa.

## 3.2 Origem única dos dados

O frontend deverá consumir exclusivamente a API interna do Dashboard Economização.

Nenhuma tela, componente, hook ou rota do Next.js poderá chamar diretamente a API do Conta Azul ou qualquer outro ERP.

Dados externos chegam ao frontend somente depois de sincronizados, normalizados e expostos pela API interna.

## 3.3 Isolamento multiempresa

Toda leitura de dados no frontend ocorre dentro do contexto do tenant da sessão autenticada.

O frontend não deverá:

- manter dados de tenants diferentes na mesma estrutura de cache sem chave de isolamento;
- reaproveitar dados carregados antes de uma troca de contexto;
- assumir que o tenant informado na interface é suficiente para autorizar a leitura.

A validação real do tenant é sempre responsabilidade do backend, conforme documentos 09.6, 09.7 e 09.8.

## 3.4 App Router obrigatório

Todo o roteamento do frontend utilizará o App Router do Next.js, conforme ADR-039.

Não deverão ser criadas rotas no diretório `pages/`.

A estrutura de diretórios deverá refletir o mapa de rotas conceitual do documento 05, criando somente as rotas efetivamente implementadas.

## 3.5 Server Components como padrão

Componentes deverão ser Server Components por padrão.

A diretiva `"use client"` somente deverá ser adicionada quando existir necessidade real, tais como:

- estado local de interação;
- efeitos de ciclo de vida;
- manipulação de eventos do usuário;
- uso de APIs do navegador;
- bibliotecas que exigem execução no cliente.

A fronteira cliente deverá ser empurrada para baixo na árvore, isolando a interatividade em componentes pequenos em vez de transformar páginas inteiras em Client Components.

## 3.6 Nenhum segredo no navegador

Nenhum segredo poderá existir no bundle enviado ao navegador.

É proibido expor:

- tokens de acesso ou refresh do Conta Azul;
- chaves de provedores de IA;
- credenciais de banco de dados, Redis ou storage;
- segredos de assinatura de sessão;
- qualquer variável de ambiente sensível prefixada para exposição pública.

Somente configurações verdadeiramente públicas poderão ser expostas ao cliente.

## 3.7 Estados obrigatórios

Toda área que depende de dados remotos deverá tratar explicitamente:

- estado de carregamento;
- estado de erro;
- estado vazio;
- estado de sucesso.

Ausência de dado é um estado válido de negócio e não deverá ser exibida como erro, conforme seção 69 do documento 05.

## 3.8 Nenhum dado fictício em produção

Nenhum componente poderá exibir valores inventados, mockados ou de exemplo em ambiente produtivo.

Quando um indicador não puder ser calculado com dados confiáveis, o componente deverá apresentar estado vazio explicativo ou não ser exibido.

## 3.9 Responsividade desde a criação

Toda tela deverá ser implementada com comportamento responsivo desde sua primeira versão.

Não será aceita implementação apenas desktop com promessa de adaptação posterior.

Funcionalidades essenciais não poderão depender de `hover` ou de mouse.

## 3.10 Acessibilidade mínima

Toda implementação deverá garantir:

- elementos semânticos adequados;
- rótulos associados aos campos de formulário;
- foco visível e navegação por teclado nos fluxos essenciais;
- contraste suficiente considerando branding do tenant;
- informação nunca comunicada exclusivamente por cor.

## 3.11 TypeScript estrito

O frontend seguirá integralmente o documento 09.2.

É obrigatório:

- tipar respostas da API interna;
- tipar props de componentes;
- evitar `any`;
- tratar dados remotos como potencialmente ausentes até validação.

## 3.12 Formatação centralizada

Formatação de moeda, data, percentual e unidades deverá ser realizada pelos utilitários centralizados de `@dashboard-economizacao/shared`, conforme o documento 09.1.

Essas funções não deverão ser reimplementadas no `frontend/`. Quando conveniente, o frontend poderá apenas reexportá-las a partir de `lib/`.

Não deverá existir formatação financeira duplicada e divergente espalhada em componentes.

# 4. Padrões Aprovados

## 4.1 Organização de diretórios

Estrutura de referência dentro de `frontend/`:

```
frontend/
  src/
    app/
      (public)/
      (app)/
      (admin)/
      layout.tsx
    components/
      ui/
      layout/
      charts/
    features/
      dashboard/
      reports/
      consultant/
      notifications/
      admin/
    hooks/
    services/
    lib/
    types/
    styles/
```

Diretrizes:

- `app/` contém apenas roteamento, layouts, páginas e seus arquivos especiais;
- `components/ui/` contém componentes visuais genéricos e sem conhecimento de domínio;
- `components/layout/` contém shells, menus, cabeçalhos e estruturas persistentes;
- `features/` contém componentes de domínio agrupados por área funcional;
- `services/` contém o acesso à API interna;
- `hooks/` contém hooks reutilizáveis;
- `lib/` contém utilitários puros específicos do frontend e a reexportação dos formatadores de `@dashboard-economizacao/shared`;
- `types/` contém tipos compartilhados de contrato.

## 4.2 Grupos de rota

Grupos de rota deverão separar as três experiências definidas no documento 05:

- área pública e autenticação;
- painel do cliente;
- painel administrativo.

Cada grupo poderá possuir seu próprio `layout.tsx`, com shell, navegação e proteção de acesso adequadas ao contexto.

## 4.3 Arquivos especiais do App Router

Deverão ser utilizados os arquivos nativos do App Router:

- `layout.tsx` para estrutura persistente;
- `page.tsx` para conteúdo da rota;
- `loading.tsx` para estado de carregamento de segmento;
- `error.tsx` para erros recuperáveis do segmento;
- `not-found.tsx` para recursos inexistentes.

O uso desses arquivos é preferível a implementações manuais equivalentes.

## 4.4 Fronteira cliente

Padrão aprovado:

- página como Server Component responsável por orquestração e busca inicial de dados;
- componentes interativos isolados como Client Components;
- passagem de dados já serializáveis do servidor para o cliente;
- nenhum componente de layout inteiro convertido em cliente apenas por causa de um botão.

## 4.5 Componentes de domínio e componentes visuais

O projeto distingue formalmente duas naturezas de componente.

Componente visual:

- não conhece endpoints;
- não conhece regras financeiras;
- recebe dados prontos por props;
- é reutilizável em qualquer contexto;
- exemplos conceituais: card, tabela, badge, drawer, skeleton, estado vazio.

Componente de domínio:

- conhece o significado do dado exibido;
- compõe componentes visuais;
- conhece o serviço da API interna correspondente;
- pertence a uma feature;
- exemplos conceituais: card de inadimplência, painel de contas a receber, lista de insights.

Componentes visuais não deverão importar serviços de API.

Componentes de domínio não deverão reimplementar estruturas visuais já existentes.

## 4.6 Serviços de API

Todo acesso à API interna deverá ocorrer por meio de serviços dedicados em `services/`.

Um serviço deverá:

- concentrar a construção da URL e dos parâmetros;
- aplicar autenticação conforme estratégia oficial do projeto;
- tipar entrada e saída;
- traduzir o formato de erro da API para um erro tipado da aplicação;
- não conter lógica de renderização.

Componentes não deverão executar chamadas HTTP diretamente.

## 4.7 Estados de dados remotos

Padrão aprovado para dados remotos:

- carregamento inicial preferencialmente no servidor, quando o dado não depender de interação;
- atualização e revalidação no cliente quando houver filtros, paginação ou interação contínua;
- chave de cache incluindo tenant, período e filtros relevantes;
- invalidação explícita após operações que alteram dados.

Não deverá existir estado global compartilhado guardando dados financeiros de forma indefinida.

## 4.8 Estado da aplicação

Hierarquia recomendada:

1. estado derivado do servidor, sempre que possível;
2. estado de URL para filtros compartilháveis, como período e paginação;
3. estado local do componente;
4. contexto compartilhado apenas para preocupações transversais, como sessão, tema, tenant ativo e modo suporte.

Biblioteca de estado global somente deverá ser introduzida quando houver necessidade comprovada, conforme ADR-035.

## 4.9 Filtros globais

O filtro de período definido no documento 05 deverá:

- ser representado na URL do segmento correspondente;
- ser preservado durante a navegação interna da mesma sessão;
- ser validado na interface quanto a intervalos inválidos;
- ser enviado à API interna em formato definido pelo documento 09.6.

O período nunca deverá ser recalculado de forma divergente entre componentes da mesma tela.

## 4.10 Loading

Padrões aprovados:

- skeleton com forma aproximada do conteúdo final;
- indicação discreta de atualização em background;
- preservação de espaço para evitar deslocamento brusco de layout.

A dashboard não deverá ser bloqueada aguardando sincronização externa.

## 4.11 Erro

Padrões aprovados:

- mensagem compreensível ao usuário final;
- indicação do que pode ser feito;
- ação de tentar novamente quando aplicável;
- registro técnico enviado à observabilidade conforme documento 09.11 — Logs;
- fallback de segmento por meio de `error.tsx`.

Mensagens técnicas e identificadores internos não deverão ser exibidos diretamente ao cliente.

## 4.12 Estado vazio

Padrões aprovados:

- texto explicativo do motivo da ausência;
- ação sugerida quando existir;
- diferenciação clara entre ausência de dado e ausência de conexão.

## 4.13 Formulários

Padrões aprovados:

- validação na interface para melhorar a experiência;
- validação definitiva sempre no backend;
- mensagens de erro associadas ao campo correspondente;
- bloqueio de envio duplicado durante submissão;
- feedback explícito de sucesso e de falha.

## 4.14 Tema e branding

O branding do tenant deverá ser aplicado por sistema central de tema, conforme seção 85 do documento 05.

Padrões aprovados:

- variáveis de tema resolvidas em um único ponto;
- fallback automático para a identidade da plataforma quando um valor estiver ausente;
- proteção de legibilidade aplicada de forma centralizada.

Cores de tenant não deverão ser aplicadas manualmente em componentes individuais.

## 4.15 Semântica de indicadores

Direção de variação e cor deverão considerar o significado do indicador, conforme seção 14 do documento 05.

O componente deverá receber a semântica esperada em vez de assumir que aumento é sempre positivo.

## 4.16 Modo suporte

Quando a sessão estiver em modo suporte, a interface deverá manter sinalização persistente e visível em toda a navegação interna.

O indicador não poderá ser removido por preferência visual de uma tela específica.

## 4.17 Reuso

Antes de criar um componente novo, deverá ser verificado se já existe equivalente.

Duplicação será aceita apenas quando a semântica for realmente distinta.

Componentes equivalentes deverão possuir comportamento equivalente, conforme seção 82 do documento 05.

# 5. Padrões Proibidos

## 5.1 Autorização crítica apenas no frontend

É proibido tratar verificação de permissão realizada no frontend como controle de segurança.

Ocultar um botão, esconder um item de menu ou bloquear uma rota no cliente são recursos de experiência, nunca de autorização.

Toda decisão de acesso deverá ser reavaliada e imposta pelo backend.

## 5.2 Chamada direta ao Conta Azul

É proibido, em qualquer circunstância:

- chamar endpoints do Conta Azul a partir do navegador;
- chamar endpoints do Conta Azul a partir de Server Components ou Route Handlers do Next.js;
- iniciar ou concluir fluxo OAuth do Conta Azul no frontend;
- armazenar, transportar ou renderizar tokens do Conta Azul.

A integração pertence exclusivamente ao backend.

## 5.3 Segredos no navegador

É proibido:

- expor variáveis de ambiente sensíveis ao cliente;
- embutir chaves em constantes do código;
- transportar segredos em props, atributos de dados ou estado global;
- registrar segredos em logs do navegador.

## 5.4 Cálculo financeiro oficial no frontend

É proibido implementar no frontend, como fonte de verdade:

- apuração de faturamento;
- cálculo de inadimplência;
- consolidação de fluxo de caixa;
- projeções financeiras;
- classificação de despesas;
- agregações oficiais por categoria ou período.

Cálculos financeiros são determinísticos e pertencem ao backend, conforme ADR-031.

Permanece permitida apenas transformação de apresentação, como ordenar uma lista já recebida, converter valor em texto formatado ou montar a série de um gráfico a partir de dados já agregados pela API.

## 5.5 Dados fictícios silenciosos

É proibido:

- preencher gráficos com valores inventados;
- exibir mock em produção;
- manter dados de exemplo como fallback silencioso de erro;
- apresentar projeção como valor realizado.

## 5.6 Outras proibições

É igualmente proibido:

- criar rotas em `pages/`;
- transformar `layout.tsx` de alto nível em Client Component sem necessidade;
- executar `fetch` disperso dentro de componentes visuais;
- misturar dados de tenants distintos em um mesmo cache;
- exibir mensagem de erro técnica ao cliente final;
- criar rotas ou itens de menu para funcionalidades ainda não implementadas;
- introduzir dependência nova sem justificativa técnica registrada.

## 5.7 Escolha de biblioteca de UI

Este documento não define biblioteca de componentes, biblioteca de gráficos, estratégia de estilização nem sistema de design.

Essa decisão pertence ao documento 08 e permanece pendente conforme sua seção de itens em aberto.

Nenhuma implementação deverá adotar biblioteca de UI de forma implícita antes da decisão formal.

# 6. Exemplos Conceituais

## 6.1 Fluxo correto de dados

```
Componente de domínio
        ↓
Serviço da API interna
        ↓
API interna (Fastify)
        ↓
Banco de dados / cálculos oficiais
        ↑
Sincronização Conta Azul (backend)
```

O frontend nunca aparece conectado diretamente ao Conta Azul.

## 6.2 Fronteira cliente correta

```
app/(app)/dashboard/page.tsx        → Server Component
  └── DashboardFilters              → Client Component
  └── KpiSummary                    → Server Component
        └── KpiCard                 → componente visual
  └── CashFlowChart                 → Client Component
```

Somente os pontos que exigem interação são clientes.

## 6.3 Separação de componentes

Componente visual, sem conhecimento de domínio:

```
KpiCard
  props: título, valor formatado, variação, semântica, período
```

Componente de domínio, com conhecimento do indicador:

```
DelinquencyKpi
  obtém dados via serviço
  define semântica de variação
  renderiza KpiCard
```

## 6.4 Estados de uma seção

```
carregando → skeleton
erro       → mensagem + ação de tentar novamente
vazio      → "Nenhum título vencido no período selecionado"
sucesso    → conteúdo real
```

## 6.5 Verificação de permissão

Correto:

```
Frontend oculta ação não permitida (experiência)
Backend rejeita a operação não permitida (segurança)
```

Incorreto:

```
Frontend oculta ação
Backend aceita a operação sem verificar
```

## 6.6 Formatação centralizada

```
@dashboard-economizacao/shared
  formatCurrency
  formatDate
  formatPercent
  formatCompactNumber

frontend/src/lib/format
  reexporta os formatadores acima, sem reimplementá-los
```

Componentes utilizam esses utilitários e não implementam formatação própria.

# 7. Critérios de Revisão

Uma implementação de frontend somente poderá ser aprovada quando:

1. utilizar App Router, sem rotas em `pages/`;
2. manter Server Components como padrão e isolar corretamente a fronteira cliente;
3. consumir exclusivamente a API interna;
4. não conter qualquer referência ao Conta Azul;
5. não expor segredos no bundle do navegador;
6. não conter regra de autorização crítica implementada apenas no cliente;
7. não conter cálculo financeiro oficial duplicado;
8. tratar loading, erro e estado vazio;
9. não exibir dados fictícios;
10. respeitar o contexto de tenant em toda leitura e em todo cache;
11. utilizar serviços tipados para acesso à API;
12. separar componentes visuais de componentes de domínio;
13. utilizar utilitários centralizados de formatação;
14. aplicar branding pelo sistema central de tema;
15. funcionar em desktop e em largura mobile compatível;
16. atender aos requisitos mínimos de acessibilidade;
17. respeitar integralmente o documento 09.2;
18. atender aos critérios de aceite de UX da seção 92 do documento 05.

# 9. Diretriz Final

O frontend do Dashboard Economização existe para transformar dados financeiros já processados em entendimento imediato.

Ele apresenta, contextualiza e organiza informação.

Ele não decide, não calcula oficialmente, não autoriza e não integra sistemas externos.

Toda vez que uma implementação de interface precisar assumir responsabilidade de negócio para funcionar, isso indica que a responsabilidade está no lugar errado e deverá ser movida para o backend.
