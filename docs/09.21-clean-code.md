# Dashboard Economização

# 09.21 — Clean Code

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define o padrão oficial de legibilidade e organização interna do código do Dashboard Economização.

O objetivo é único e mensurável: **reduzir o tempo e o risco de alterar este código daqui a seis meses**, por alguém que não estava presente quando ele foi escrito — inclusive quando esse alguém for quem o escreveu.

Este documento não é uma adesão a uma escola de programação. Ele adota deliberadamente uma posição sobre o assunto, coerente com a ADR-035 e com a ADR-031:

> **Clean Code aqui é um meio, nunca um fim.** Nenhuma regra deste documento justifica tornar o código mais difícil de entender.

Essa ressalva é necessária porque a aplicação dogmática de princípios de código limpo produz um dano específico e frequente: funções minúsculas que só existem para satisfazer uma contagem de linhas, camadas de abstração que só existem para satisfazer um princípio, e indireção que obriga o leitor a abrir cinco arquivos para entender uma regra que caberia em quinze linhas explícitas.

No Dashboard Economização, quando um princípio de código limpo conflitar com a clareza real do código, **a clareza vence**. Sempre. E a decisão de contrariar um princípio é registrada em comentário curto, para que a próxima pessoa saiba que foi deliberado.

A prioridade, em ordem, é:

1. **correto** — especialmente em cálculo financeiro, isolamento entre empresas e autorização;
2. **claro** — compreensível na primeira leitura por alguém competente que não conhece o contexto;
3. **simples** — sem elemento que não esteja pagando por si;
4. **conciso** — nesta ordem, e nunca à custa das anteriores.

# 2. Escopo

Este documento regula:

- nomenclatura de variáveis, funções, tipos, arquivos e conceitos;
- tamanho e responsabilidade de funções, classes e módulos;
- responsabilidade única aplicada com critério;
- profundidade de aninhamento e uso de retornos antecipados;
- complexidade condicional e simplificação de fluxo;
- duplicação: quando é defeito e quando é a opção correta;
- criação de abstrações e o custo que elas cobram;
- números mágicos, constantes e configuração;
- efeitos colaterais e funções puras;
- tratamento de valores ausentes e estados impossíveis;
- comentários, na parte que complementa `docs/09.20-documentacao.md`;
- código morto e resíduo de desenvolvimento.

Este documento **não** regula:

- tipagem e sintaxe de TypeScript — pertence a `docs/09.2-convencoes-typescript.md`;
- arquitetura em camadas do backend — pertence a `docs/09.3-backend.md`;
- estrutura de componentes de interface — pertence a `docs/09.4-frontend.md`;
- formatação automática — pertence ao Prettier e ao ESLint configurados no repositório;
- quando refatorar código existente — pertence a `docs/09.22-refatoracao.md`;
- decisões de desempenho — pertencem a `docs/09.18-performance.md`.

# 3. Regras Obrigatórias

## 3.1 O nome revela a intenção

Um nome existe para que o leitor não precise ler a implementação.

Regras:

- o nome descreve **o que a coisa é ou faz**, não como foi implementada;
- variável de domínio usa o vocabulário do domínio: `titulosVencidos`, `valorInadimplente`, `empresaAtiva`;
- função que retorna booleano é uma afirmação: `estaVencido`, `podeSincronizar`, `temIntegracaoConectada`;
- função com efeito é um verbo no imperativo: `calcularInadimplencia`, `registrarAuditoria`, `avancarCursor`;
- nome curto é aceitável apenas em escopo curto — o índice de um laço de três linhas pode ser `i`; o parâmetro de uma função de vinte linhas não pode ser `d`;
- abreviação só é aceita quando é o termo real usado no projeto;
- o nome não mente: `getUsuario` que também grava no banco tem nome errado;
- unidade e moeda aparecem no nome quando houver risco de ambiguidade: `valorEmCentavos`, `prazoEmDias`, `timeoutMs`.

Nomes de código permanecem em inglês quando esse for o padrão do restante do projeto, conforme `docs/09.2-convencoes-typescript.md`; o vocabulário de negócio permanece o do domínio em português quando já for assim adotado. O que este documento exige é **consistência**: o mesmo conceito não muda de nome entre camadas.

## 3.2 O nome é atualizado quando o significado muda

Um nome que descrevia corretamente a intenção original e não acompanhou a mudança é uma armadilha, exatamente como um comentário desatualizado.

Renomear um identificador cujo significado mudou faz parte da própria mudança, e não é considerado refatoração paralela.

## 3.3 Uma função faz uma coisa em um nível de abstração

Regras:

- a função tem um propósito descritível em uma frase sem "e";
- os passos internos estão aproximadamente no mesmo nível de abstração — não se mistura orquestração de alto nível com manipulação de string na mesma função;
- a função não surpreende: não faz nada relevante que o nome não anuncie;
- consulta e comando são separados sempre que possível: uma função que responde algo não altera estado de forma silenciosa.

O critério prático de responsabilidade única aplicado neste projeto: **um motivo de mudança**. Se duas razões de negócio completamente distintas obrigam a editar a mesma função, ela provavelmente tem duas responsabilidades.

O que este projeto **não** adota é a leitura literal de "uma função deve ter poucas linhas". Uma função de cálculo financeiro com trinta linhas lineares e bem nomeadas é mais fácil de auditar do que a mesma regra espalhada em oito funções de quatro linhas — e auditabilidade de cálculo financeiro é prioridade máxima aqui, conforme `docs/09.17-testes.md`.

## 3.4 Tamanho é sintoma, não regra

Não existe limite numérico obrigatório de linhas por função ou por arquivo neste projeto.

Existe, sim, um conjunto de sintomas que exigem atenção em revisão:

- a função não cabe na tela e exige rolagem para ser compreendida;
- é necessário um comentário para separar "blocos" internos — cada bloco costuma ser uma função;
- a função tem mais de três ou quatro parâmetros sem que formem um conceito;
- há muitas variáveis locais vivas simultaneamente;
- há mais de dois níveis de aninhamento além do corpo;
- o nome da função precisou de "e" ou de "handler" genérico para caber.

Cada sintoma é um convite a olhar, não uma reprovação automática. Um analisador de casos com dezoito ramos explícitos e planos pode ser longo e perfeitamente claro.

## 3.5 Retorno antecipado em vez de aninhamento

Validações, pré-condições e casos de exceção saem primeiro. O caminho principal fica no nível mais externo da função, sem indentação acumulada.

Regras:

- pré-condição inválida retorna ou lança imediatamente;
- `else` após um bloco que retorna é removido;
- aninhamento maior que dois ou três níveis exige justificativa — normalmente a solução é extrair uma função ou inverter uma condição;
- laço com muitas condições internas costuma esconder uma função de filtragem esperando para ser nomeada.

## 3.6 Condicional complexa recebe nome

Uma expressão booleana que exige releitura é extraída para uma constante ou função com nome de negócio.

O ganho não é estético: a condicional nomeada passa a ser testável isoladamente e passa a aparecer, com esse nome, na conversa sobre a regra.

## 3.7 Números e cadeias mágicas não aparecem na regra

Valor literal com significado de negócio recebe nome.

Aplica-se obrigatoriamente a:

- prazos, janelas e períodos;
- limites de paginação, de lote e de concorrência;
- timeouts e intervalos de retentativa;
- percentuais e fatores de cálculo;
- códigos de status, códigos de erro e chaves de configuração;
- valores monetários de referência;
- strings que representam estado, tipo ou papel.

Não se aplica a valores autoevidentes no contexto imediato: `0`, `1`, `-1`, o segundo argumento de uma divisão por dois em uma média. Criar `const UM = 1` é ruído.

A constante mora perto de quem a usa quando pertence a um módulo, e em local compartilhado quando é usada por mais de um pacote, conforme `docs/09.1-estrutura-do-projeto.md`. Valor que muda por ambiente não é constante: é configuração, conforme `docs/09.25-boas-praticas-gerais.md`.

## 3.8 Efeito colateral é explícito

Regras:

- a função anuncia no nome quando escreve, publica, envia ou registra;
- não se altera parâmetro recebido nem estado global de forma oculta;
- não se cria estado compartilhado mutável entre módulos;
- consulta não grava; se precisar gravar — auditoria, por exemplo — isso é parte declarada do contrato da operação;
- o instante atual, a aleatoriedade e o identificador gerado são injetados quando influenciam o resultado, conforme `docs/09.17-testes.md` §4.8.

A última regra tem consequência direta na testabilidade de todo cálculo financeiro sensível a data.

## 3.9 Função pura quando houver benefício real

Toda **regra de negócio determinística** é escrita como função pura: entrada, saída, sem dependência de estado externo.

Aplica-se obrigatoriamente a:

- cálculo de indicador financeiro;
- classificação e elegibilidade;
- normalização de dado externo;
- formatação de valor, data e texto;
- decisão de retentativa, de elegibilidade de sincronização e de deduplicação.

Não se aplica a código cuja essência é efeito: persistência, chamada HTTP, publicação em fila. Envolver esse tipo de código em uma casca "pura" apenas para satisfazer o princípio adiciona indireção sem ganhar nada.

O motivo desta regra é concreto: função pura é a única coisa que se testa com custo próximo de zero, e cálculo financeiro é justamente o que precisa ser testado exaustivamente neste produto.

## 3.10 Estado impossível não é representável quando o custo for baixo

Preferir modelagem em que um estado inválido não pode ser construído a validar o estado inválido em toda leitura.

Exemplos de aplicação: união discriminada em vez de vários campos opcionais que "não podem ocorrer juntos"; valor monetário em uma representação única; período com início e fim como um conceito, e não como dois parâmetros soltos que podem ser trocados de ordem.

A ressalva vale: essa técnica é adotada quando reduz erro real, e não como exercício de tipagem. Detalhes de tipagem pertencem a `docs/09.2-convencoes-typescript.md`.

## 3.11 Duplicação é avaliada, não eliminada por reflexo

Duplicação é defeito quando **o mesmo conhecimento** está escrito em dois lugares e precisará mudar junto.

Duplicação **não** é defeito quando dois trechos são apenas parecidos hoje, por coincidência, e respondem a razões diferentes.

Regra prática deste projeto: **duas ocorrências são um fato; três são um padrão.** Extrair na segunda ocorrência costuma acoplar dois contextos que ainda não se conhecem.

Duplicação que é sempre defeito, sem exceção:

- regra de cálculo financeiro replicada;
- regra de autorização replicada;
- aplicação do escopo por empresa replicada;
- mapeamento de dado externo replicado;
- mesma constante de negócio escrita duas vezes.

Nesses casos, a réplica não é redundância: é a garantia de que um dia as duas cópias vão divergir e produzir números ou permissões diferentes para a mesma pergunta.

## 3.12 Abstração precisa se pagar

Toda abstração cobra um preço: mais um arquivo, mais um nome, mais um salto na leitura, mais um lugar onde o comportamento pode estar.

Uma abstração só é criada quando:

- existe um problema concreto e presente que ela resolve;
- existem casos reais — não hipotéticos — que a justificam;
- o código fica mais fácil de entender **depois** dela, e não apenas mais curto.

É proibido criar abstração:

- para "seguir Clean Code";
- para atender a um princípio de arquitetura por si só;
- para preparar uma variação que ninguém pediu;
- para evitar duplicação que ainda não existe;
- porque a implementação atual "pode ser trocada um dia" sem que exista intenção real de trocá-la.

Esta regra é a aplicação direta da ADR-035: simplicidade antes de complexidade, necessidade antes de tendência, clareza antes de abstração.

## 3.13 Código explícito é preferido a código esperto

Quando houver duas soluções corretas, escolhe-se a que exige menos conhecimento implícito para ser entendida.

Consequências práticas:

- encadeamento excessivamente denso é quebrado em passos nomeados quando o passo intermediário tem significado;
- operador ou construção obscura não é usada para economizar linhas;
- metaprogramação, tipagem acrobática e geração dinâmica de comportamento exigem justificativa concreta;
- a solução que qualquer pessoa da equipe consegue depurar às duas da manhã vence a solução elegante que só o autor entende.

## 3.14 Código morto é removido

Não permanecem no repositório:

- função, tipo, arquivo ou pacote sem uso;
- código comentado "para o caso de precisar" — o histórico do Git já guarda isso, conforme `docs/09.19-git.md`;
- ramo condicional inalcançável;
- parâmetro nunca utilizado;
- variável de ambiente lida e ignorada;
- artefato de depuração: log temporário, valor fixo de teste, atalho de desenvolvimento.

A remoção acompanha a mudança que tornou o código morto. Remover código morto de área não relacionada é assunto de `docs/09.22-refatoracao.md`.

## 3.15 O código não silencia erro

Bloco de captura vazio é proibido, conforme `docs/07-prompts-cursor.md` §29.

Erro é tratado na camada adequada, com contexto suficiente para diagnóstico e sem expor detalhe interno ao usuário final, conforme `docs/09.10-tratamento-de-erros.md`. Um erro engolido transforma um defeito diagnosticável em um comportamento inexplicável.

# 4. Padrões Aprovados

## 4.1 Convenções de nomenclatura

| Elemento | Padrão | Exemplo |
|---|---|---|
| Variável e função | `camelCase` | `valorInadimplente`, `calcularInadimplencia` |
| Booleano | afirmação | `estaVencido`, `podeSincronizar`, `temIntegracao` |
| Função com efeito | verbo imperativo | `registrarAuditoria`, `publicarJob` |
| Função pura de cálculo | verbo + substantivo | `calcularFluxoDeCaixa` |
| Tipo e interface | `PascalCase` | `TituloReceber`, `ResultadoSincronizacao` |
| Constante de módulo | `SCREAMING_SNAKE_CASE` | `LIMITE_PADRAO_DE_PAGINA` |
| Arquivo | `kebab-case` | `calcular-inadimplencia.ts` |
| Valor com unidade | sufixo explícito | `timeoutMs`, `valorEmCentavos`, `prazoEmDias` |

## 4.2 Nomes aprovados e reprovados

Aprovados:

```
titulosVencidosEmAberto
valorInadimplenteEmCentavos
empresaEfetiva
estaDentroDoPeriodo
calcularProjecaoDeCaixa

```

## 4.3 Retorno antecipado

Aprovado:

```ts
function calcularInadimplencia(titulos: Titulo[], referencia: Data): Centavos {
  if (titulos.length === 0) return 0;

  const vencidosEmAberto = titulos.filter((t) => estaVencidoEmAberto(t, referencia));
  return somarValores(vencidosEmAberto);
}
```

Reprovado:

```ts
function calcularInadimplencia(titulos: Titulo[], referencia: Data): Centavos {
  if (titulos.length > 0) {
    if (referencia) {
      let total = 0;
      for (const t of titulos) {
        if (t.status !== 'cancelado') {
          if (t.pagoEm === null) {
            if (t.vencimento < referencia) {
              total += t.valor;
            }
          }
        }
      }
      return total;
    } else {
      return 0;
    }
  } else {
    return 0;
  }
}
```

O segundo não é pior por ser longo. É pior porque a regra de negócio — quais títulos contam — está enterrada em quatro níveis de indentação, e não pode ser testada nem nomeada isoladamente.

## 4.4 Condicional nomeada

Reprovado:

```ts
if (
  empresa.ativa &&
  empresa.integracao?.status === 'conectada' &&
  empresa.integracao.expiraEm > agora &&
  !empresa.sincronizacaoEmAndamento
) { ... }
```

Aprovado:

```ts
function podeIniciarSincronizacao(empresa: Empresa, agora: Instante): boolean {
  if (!empresa.ativa) return false;
  if (empresa.integracao?.status !== 'conectada') return false;
  if (empresa.integracao.expiraEm <= agora) return false;
  return !empresa.sincronizacaoEmAndamento;
}

if (podeIniciarSincronizacao(empresa, agora)) { ... }
```

Ganhos concretos: a regra passa a ter nome, passa a ser testável com casos de borda e passa a existir em um único lugar quando aparecer a segunda chamada.

## 4.5 Constantes nomeadas

Reprovado:

```ts
if (diasEmAtraso > 90) { ... }
const pagina = await buscar({ limite: 200 });
setTimeout(tentarNovamente, 30000);
```

Aprovado:

```ts
const DIAS_PARA_INADIMPLENCIA_GRAVE = 90;
const REGISTROS_POR_PAGINA_CONTA_AZUL = 200;
const INTERVALO_ENTRE_TENTATIVAS_MS = 30_000;
```

Se o valor varia por ambiente, ele deixa de ser constante e vira configuração validada na inicialização.

## 4.6 Função pura de regra de negócio

```ts
// Pura: mesma entrada, mesma saída, sem relógio, sem banco, sem rede.
export function calcularInadimplencia(
  titulos: readonly Titulo[],
  referencia: Instante,
): Centavos {
  return titulos
    .filter((titulo) => estaVencidoEmAberto(titulo, referencia))
    .reduce((total, titulo) => total + titulo.valorEmCentavos, 0);
}
```

O `referencia` é parâmetro, e não `new Date()` interno. Essa única decisão é o que permite testar virada de mês, virada de ano e fuso de forma determinística.

## 4.7 Separação entre orquestração e regra

Aprovado:

```ts
// Camada de aplicação: orquestra. Não contém regra de cálculo.
async function gerarIndicadoresDoPainel(empresaId: EmpresaId, referencia: Instante) {
  const titulos = await repositorioDeTitulos.listarPorEmpresa(empresaId);

  return {
    inadimplencia: calcularInadimplencia(titulos, referencia),
    aReceberNoPeriodo: calcularAReceber(titulos, referencia),
  };
}
```

A orquestração conhece infraestrutura e não conhece a fórmula. As funções de cálculo conhecem a fórmula e não conhecem infraestrutura. Cada uma é testada pelo que realmente é.

## 4.8 Duplicação aceitável e duplicação inaceitável

Aceitável:

```
Dois formulários com validações parecidas, de módulos diferentes,
que evoluirão por razões diferentes.
Unificá-los hoje criaria um componente com parâmetros de configuração
para acomodar duas telas que ainda vão divergir.
```

Inaceitável:

```
A regra "título vencido e em aberto" escrita no cálculo do dashboard
e novamente na geração do relatório.
No dia em que a definição mudar, dashboard e relatório passarão a
exibir números diferentes para a mesma pergunta — e o cliente
descobrirá antes da equipe.
```

## 4.9 Abstração justificada e injustificada

Justificada:

```
Abstração de provedor de IA (ADR-028).
Motivo concreto: a decisão de provedor está parcialmente aprovada
e a troca é prevista. Existe um problema real e presente.
```

Injustificada:

```
Uma interface de repositório com uma única implementação,
criada "para permitir trocar o Prisma um dia",
sem qualquer intenção registrada de trocá-lo (ADR-008 é aprovada).
Custo: um arquivo a mais, um salto a mais na leitura, zero benefício hoje.
```

## 4.10 Quando contrariar um princípio deliberadamente

É aceitável, e às vezes correto, escrever uma função longa e linear em vez de fragmentá-la — por exemplo, um cálculo financeiro com muitas exclusões, em que ver todos os critérios juntos é o que permite auditar a regra.

Nesse caso, registra-se a decisão:

```ts
// Mantida linear de propósito: os critérios de exclusão precisam ser
// lidos em conjunto para auditar o indicador contra o PRD.
// Fragmentar esconderia a regra em cinco arquivos.
```

O comentário existe para que a próxima pessoa não "conserte" algo que foi decidido.

# 5. Padrões Proibidos

É proibido:

1. usar nome genérico — `data`, `temp`, `aux`, `item2`, `processar`, `handle` — em escopo relevante;
2. usar nome que não corresponde ao que o código faz;
3. manter nome cujo significado mudou;
4. escrever função que faz algo relevante não anunciado pelo nome;
5. misturar consulta e comando sem que o efeito faça parte do contrato declarado;
6. alterar parâmetro recebido ou estado global de forma oculta;
7. usar o relógio, aleatoriedade ou identificador gerado diretamente dentro de regra de negócio;
8. duplicar regra de cálculo financeiro;
9. duplicar regra de autorização ou aplicação de escopo por empresa;
10. duplicar mapeamento de dado externo;
11. extrair abstração para eliminar duplicação que ainda não é padrão estabelecido;
12. criar abstração sem caso de uso real e presente;
13. criar interface com implementação única sem intenção registrada de variação;
14. criar camada, wrapper ou indireção "para seguir Clean Code";
15. fragmentar uma regra coesa em funções minúsculas que só existem para reduzir contagem de linhas;
16. usar número ou cadeia mágica com significado de negócio;
17. tratar valor que varia por ambiente como constante de código;
18. acumular mais de dois ou três níveis de aninhamento sem justificativa;
19. manter condicional booleana composta e ilegível sem nome;
20. usar construção obscura ou "esperta" para economizar linhas;
21. usar metaprogramação ou tipagem acrobática sem justificativa concreta;
22. deixar código comentado no repositório;
23. deixar função, tipo, arquivo, parâmetro ou ramo sem uso;
24. deixar log de depuração, valor fixo de teste ou atalho de desenvolvimento;
25. usar bloco de captura vazio ou silenciar erro;
26. escrever comentário que apenas narra o que a linha faz;
27. justificar qualquer decisão de código apenas com "é Clean Code" ou "é boa prática", sem apontar o problema concreto resolvido.

O item 27 é o mais importante desta lista. Toda regra deste documento tem um motivo prático; quando o motivo não se aplica ao caso, a regra também não se aplica.

# 6. Exemplos Conceituais

## 6.1 Fragmentação excessiva

Reprovado:

```ts
function calcularInadimplencia(titulos: Titulo[], referencia: Instante) {
  return somar(mapearValores(filtrarVencidos(filtrarEmAberto(filtrarValidos(titulos)), referencia)));
}

function filtrarValidos(t: Titulo[]) { return t.filter((x) => x.status !== 'cancelado'); }
function filtrarEmAberto(t: Titulo[]) { return t.filter((x) => x.pagoEm === null); }
function filtrarVencidos(t: Titulo[], r: Instante) { return t.filter((x) => x.vencimento < r); }
function mapearValores(t: Titulo[]) { return t.map((x) => x.valorEmCentavos); }
function somar(v: number[]) { return v.reduce((a, b) => a + b, 0); }
```

Aprovado:

```ts
function estaVencidoEmAberto(titulo: Titulo, referencia: Instante): boolean {
  if (titulo.status === 'cancelado') return false;
  if (titulo.pagoEm !== null) return false;
  return titulo.vencimento < referencia;
}

export function calcularInadimplencia(titulos: readonly Titulo[], referencia: Instante): Centavos {
  return titulos
    .filter((titulo) => estaVencidoEmAberto(titulo, referencia))
    .reduce((total, titulo) => total + titulo.valorEmCentavos, 0);
}
```

A segunda versão tem menos funções e diz mais. Os três critérios que definem inadimplência estão juntos, com nome, em um lugar testável. Na primeira, a regra está distribuída em quatro funções sem significado de negócio, e o leitor precisa reconstruí-la mentalmente na ordem inversa da leitura.

## 6.2 Abstração prematura

Reprovado:

```
Antes de existir o segundo tipo de relatório:
  interface EstrategiaDeRelatorio
  class FabricaDeRelatorios
  class RegistroDeEstrategias
  class RelatorioDeRecebiveis implements EstrategiaDeRelatorio
```

Aprovado:

```
Enquanto existe um tipo de relatório:
  função gerarRelatorioDeRecebiveis(...)

Quando o segundo aparecer, a variação real será conhecida —
e a abstração será desenhada sobre o que os dois de fato compartilham,
e não sobre o que se imaginou que compartilhariam.
```

## 6.3 Nome que mente

```ts
// Nome errado: também grava e dispara job.
async function getEmpresa(id: EmpresaId) {
  const empresa = await repositorio.buscar(id);
  await repositorio.registrarUltimoAcesso(id);
  await fila.publicar('aquecer-cache', { id });
  return empresa;
}
```

Correções possíveis, ambas aceitáveis:

- separar em `buscarEmpresa` e as operações de efeito, chamadas explicitamente por quem orquestra;
- manter junto, se o efeito for parte do contrato, e nomear `carregarEmpresaParaSessao`.

O inaceitável é manter `getEmpresa`.

## 6.4 Estado impossível

Reprovado:

```ts
type Integracao = {
  status: 'desconectada' | 'conectada' | 'expirada';
  accessToken?: string;
  refreshToken?: string;
  expiraEm?: Date;
};
```

Todo consumidor precisa verificar campos opcionais que "não deveriam" estar ausentes quando o status é `conectada` — e algum consumidor vai esquecer.

Aprovado:

```ts
type Integracao =
  | { status: 'desconectada' }
  | { status: 'conectada'; credenciais: CredenciaisContaAzul; expiraEm: Instante }
  | { status: 'expirada'; expirouEm: Instante };
```

## 6.5 Duplicação correta

```
Duas funções de formatação, uma para exibição em tela
e outra para o corpo do relatório exportado.

Hoje são idênticas.
Elas respondem a públicos diferentes e mudarão por razões diferentes:
a de tela seguirá docs/05-ui-ux.md; a do relatório seguirá o formato
esperado pelo arquivo exportado.

Unificar hoje criaria um parâmetro "modo" que só existe
para manter duas coisas diferentes no mesmo lugar.
```

## 6.6 Constante compartilhada com significado de negócio

Reprovado — o mesmo conhecimento em dois lugares:

```
backend:  if (diasEmAtraso > 90) marcarComoGrave();
frontend: if (diasEmAtraso > 90) exibirAlertaVermelho();
```

Aprovado — um lugar, conforme `docs/09.1-estrutura-do-projeto.md`:

```
packages/shared: export const DIAS_PARA_INADIMPLENCIA_GRAVE = 90;
```

Sem isso, alterar a regra para 60 dias produz um backend que classifica de um jeito e uma interface que pinta de outro.

## 6.7 Código esperto contra código explícito

Reprovado:

```ts
const r = t.reduce((a, x) => ((a[x.s] ??= []).push(x), a), {} as Record<string, Titulo[]>);
```

Aprovado:

```ts
const titulosPorStatus = agruparPor(titulos, (titulo) => titulo.status);
```

A segunda versão diz o que acontece. A primeira exige decifração e é onde os defeitos se escondem.

# 7. Critérios de Revisão

Um código só é aprovado quando:

1. os nomes revelarem intenção e usarem o vocabulário do domínio;
2. nenhum nome estiver em desacordo com o que o código faz;
3. cada função tiver um propósito descritível em uma frase sem "e";
4. os passos internos de cada função estiverem em nível de abstração compatível;
5. o caminho principal não estiver enterrado em aninhamento;
6. condicionais compostas relevantes tiverem nome;
7. não houver número ou cadeia mágica com significado de negócio;
8. valores que variam por ambiente estiverem em configuração, não em constante;
9. regras de negócio determinísticas estiverem em funções puras e testáveis;
10. o relógio, a aleatoriedade e identificadores gerados estiverem injetados onde influenciam resultado;
11. efeitos colaterais estiverem anunciados pelo nome ou pelo contrato;
12. não houver duplicação de cálculo financeiro, autorização, escopo por empresa ou mapeamento externo;
13. toda abstração criada tiver caso de uso real e presente;
14. nenhuma indireção existir apenas para satisfazer um princípio;
15. nenhuma regra coesa tiver sido fragmentada a ponto de dificultar a leitura;
16. não houver código morto, código comentado ou resíduo de depuração;
17. nenhum erro estiver sendo silenciado;
18. os comentários existentes explicarem o porquê;
19. decisões que contrariam deliberadamente um princípio estarem registradas em comentário curto;
20. `lint`, `typecheck` e os testes relevantes passarem.

# 9. Diretriz Final

Código limpo, neste projeto, não é código que segue uma lista. É código que a próxima pessoa consegue **ler, entender e alterar com segurança** — e que, ao ser alterado, não produz um número financeiro errado nem um vazamento entre empresas.

Três frases resumem o padrão:

**O nome carrega a intenção; a função tem um propósito; o caminho principal fica visível.** Quase toda a legibilidade deste projeto vem dessas três coisas.

**Toda abstração precisa se pagar.** Se ela não resolve um problema presente, ela é apenas mais um lugar onde o comportamento pode estar escondido.

**Nenhum princípio justifica código mais difícil de entender.** Quando "Clean Code" e clareza divergirem, escolhe-se a clareza, registra-se o motivo em uma linha, e segue-se em frente.

Entre uma solução simples, explícita e um pouco repetitiva e uma solução elegante que exige percorrer quatro arquivos para entender de onde vem um número, o Dashboard Economização escolhe a primeira — todas as vezes.
