# Dashboard Economização

# 09.19 — Git

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define o padrão oficial de uso do Git no Dashboard Economização.

O histórico do repositório é tratado neste projeto como um **registro auditável de decisões**, e não como um efeito colateral do trabalho. A ADR-037 estabelece que a sequência obrigatória de desenvolvimento é documentação, decisão técnica, implementação, testes, auditoria, validação humana, commit e push. O Git ocupa as duas últimas posições dessa sequência por um motivo específico: um commit representa o momento em que uma mudança **já validada** passa a integrar o histórico oficial do produto.

Disso decorre a característica mais importante deste documento: no Dashboard Economização, commit e push **não são operações rotineiras de conveniência**. São atos de publicação, executados sob autorização explícita, conforme já estabelecido nos itens 39 a 44 de `docs/07-prompts-cursor.md`.

Este capítulo consolida, detalha e torna verificáveis aquelas regras, e responde de forma definitiva a:

- em que branch se trabalha;
- quando uma branch de trabalho é justificada;
- o que caracteriza um commit coerente;
- como se escreve uma mensagem de commit;
- o que deve ser verificado antes de commitar;
- o que nunca entra no repositório;
- quais operações são destrutivas e, portanto, proibidas sem autorização.

---

# 2. Escopo

Este documento regula:

- a branch principal e as branches de trabalho;
- a leitura obrigatória do estado do repositório antes de qualquer alteração relevante;
- a preservação de alterações pré-existentes do usuário;
- a granularidade e a coerência de um commit;
- o formato e o conteúdo das mensagens de commit;
- a separação entre autorização de commit e autorização de push;
- a revisão obrigatória do conteúdo antes de commitar;
- o tratamento de arquivos gerados, `node_modules`, artefatos de build e segredos;
- o tratamento do lockfile do pnpm;
- o tratamento de migrations do Prisma no histórico;
- o tratamento de alterações de documentação no histórico;
- as operações destrutivas proibidas sem autorização explícita.

Este documento **não** regula:

- o conteúdo técnico do código commitado — pertence aos demais capítulos da série 09;
- o processo de validação anterior ao commit — pertence a `docs/09.17-testes.md` e a `docs/07-prompts-cursor.md`;
- a infraestrutura de integração contínua e a automação de `.github/` — executores, imagens, segredos, cache de build e configuração dos workflows pertencem à documentação de infraestrutura; o **conteúdo** do portão de qualidade executado ali — quais verificações são obrigatórias e o que bloqueia a integração — pertence a `docs/09.17-testes.md` 4.13;
- política de versionamento de release e tags de produto — ainda não decidida por ADR.

# 3. Regras Obrigatórias

## 3.1 A branch principal é `main`

A branch oficial do repositório é `main`.

Ela representa o estado íntegro e validado do projeto. Todo commit presente em `main` deve corresponder a uma alteração que passou pelas validações aplicáveis à fase: testes relevantes, `lint`, `typecheck` e `build`, conforme `docs/07-prompts-cursor.md` §47.

Não é aceitável commitar em `main` código que se sabe quebrado com a intenção de corrigir em seguida.

## 3.2 Branches de trabalho quando aplicável

O projeto é desenvolvido em fases pequenas e sequenciais, conforme ADR-036. Em grande parte dessas fases, o trabalho direto em `main` com commits pequenos e validados é adequado e é o fluxo padrão.

Uma branch de trabalho passa a ser justificada quando ao menos uma destas condições ocorre:

- a mudança é ampla o suficiente para deixar o projeto temporariamente inconsistente entre commits;
- a mudança é experimental e pode ser descartada;
- a mudança precisa ser revisada isoladamente antes de integrar `main`;
- a mudança toca simultaneamente contrato de API, banco e frontend, exigindo integração conjunta;
- existe outra frente de trabalho em andamento cujo conflito precisa ser isolado.

Quando criada, a branch de trabalho:

- parte de `main` atualizada;
- possui nome descritivo em `kebab-case`, coerente com o restante do projeto — por exemplo `fase-0.5-banco-de-dados`, `sync-conta-azul-cursor`, `fix-inadimplencia-vencidos`;
- tem vida curta, medida em dias e não em semanas;
- é integrada a `main` somente após as validações aplicáveis;
- não é criada por iniciativa automática do executor sem que o prompt a autorize.

A escolha entre trabalhar em `main` ou em branch é uma decisão do prompt, e não do executor.

## 3.3 O estado do repositório é lido antes de alterar

Antes de qualquer alteração relevante, é obrigatório identificar:

- a branch atual;
- o estado da working tree;
- as alterações pré-existentes, versionadas ou não;
- se há divergência entre o local e o remoto.

Esta regra reproduz `docs/07-prompts-cursor.md` §42 e existe por uma razão concreta: o repositório pode conter trabalho humano em andamento que o executor não iniciou e não conhece.

## 3.4 Alterações pré-existentes são preservadas

Se houver arquivos modificados antes do início da tarefa, é obrigatório:

- preservá-los integralmente;
- não resetá-los;
- não descartá-los;
- não incluí-los no commit da tarefa sem necessidade real;
- informá-los no relatório final.

Um arquivo modificado que o executor não entende é motivo para **relatar**, nunca para limpar.

## 3.5 Commit exige autorização explícita

Por padrão, no Dashboard Economização:

```
NÃO FAZER COMMIT
NÃO FAZER PUSH
```

Commit só ocorre quando o prompt determina explicitamente que ele deve ocorrer, conforme `docs/07-prompts-cursor.md` §39.

Concluir uma implementação não autoriza commit. Passar em todos os testes não autoriza commit. Ser uma alteração pequena não autoriza commit.

## 3.6 Push é autorização independente do commit

Autorização de commit **nunca** implica autorização de push, conforme `docs/07-prompts-cursor.md` §41.

São duas permissões distintas, solicitadas separadamente, e a segunda nunca é inferida da primeira. O motivo é prático: um commit local é reversível com baixo custo; um push publica o histórico e passa a afetar qualquer outro ponto que consuma o repositório.

## 3.7 Um commit representa uma unidade coerente

Um commit deve corresponder a **uma** mudança compreensível isoladamente.

Um bom teste de coerência: se a mensagem do commit precisa da palavra "e" para descrever coisas não relacionadas, provavelmente deveria haver mais de um commit.

Não devem ser misturados no mesmo commit, sem necessidade real:

- funcionalidade nova e refatoração não relacionada;
- correção de defeito e mudança de estilo;
- documentação e implementação de outro assunto;
- configuração de ferramenta e regra de negócio;
- migration e alteração de interface que não depende dela.

A exceção legítima é a **coesão obrigatória**: quando duas alterações não fazem sentido separadas — uma migration e o código que passa a depender do novo campo, por exemplo — elas pertencem ao mesmo commit, porque separá-las produziria um commit intermediário quebrado.

## 3.8 O conteúdo é revisado antes de commitar

Antes de criar o commit é obrigatório revisar exatamente o que será incluído.

A revisão verifica, no mínimo:

- se todos os arquivos incluídos pertencem à tarefa;
- se nenhum arquivo não relacionado foi arrastado junto;
- se não há código de depuração, `console.log` temporário, credencial, token, caminho absoluto de máquina local ou trecho comentado deixado por engano;
- se não há arquivo gerado ou artefato de build incluído;
- se não há dado real de cliente em fixture, seed ou exemplo;
- se as validações da fase continuam válidas para o estado atual.

Adicionar tudo o que estiver modificado sem inspecionar o conteúdo é proibido por esta regra.

## 3.9 A working tree é reportada ao final

Após um commit autorizado, é obrigatório informar:

- branch;
- hash;
- mensagem;
- arquivos incluídos;
- estado final da working tree.

Se restarem alterações não commitadas, elas devem ser explicitamente listadas com o motivo pelo qual permaneceram fora — normalmente por serem pré-existentes, conforme §3.4.

## 3.10 Arquivos gerados não são versionados

Nunca são versionados:

- `node_modules/`;
- artefatos de build — incluindo `frontend/.next/`, saídas de `dist/`, `build/` e `.turbo/` caso venham a existir;
- caches de ferramenta — `.eslintcache`, `*.tsbuildinfo`, caches do pnpm;
- clientes gerados pelo Prisma;
- arquivos de sistema operacional e de editor — `.DS_Store`, diretórios de IDE;
- logs locais;
- dumps de banco;
- relatórios de cobertura;
- arquivos temporários de execução.

Nunca são versionados, sob nenhuma circunstância:

- `.env` e qualquer variante com valores reais;
- chaves privadas, certificados com chave privada;
- credenciais da Conta Azul;
- chaves de provedor de IA;
- qualquer segredo de produção.

O que **é** versionado nesse contexto é `.env.example`, contendo apenas nomes de variáveis e valores de exemplo evidentemente falsos, conforme `docs/09.8-seguranca.md`.

Quando um arquivo que deveria ser ignorado aparece no `git status`, a correção é ajustar o `.gitignore` — nunca commitar o arquivo "só desta vez".

Se um segredo real for commitado, a situação deixa de ser um problema de Git: o segredo é considerado comprometido, deve ser rotacionado imediatamente e o incidente registrado. Remover o arquivo em um commit posterior não desfaz a exposição.

## 3.11 O lockfile acompanha a mudança de dependência

O `pnpm-lock.yaml` é versionado e é a fonte de verdade das versões efetivamente instaladas.

Regras:

- toda alteração de dependência inclui o lockfile atualizado **no mesmo commit** que altera o `package.json` correspondente;
- o lockfile nunca é editado manualmente;
- o lockfile nunca é regenerado do zero "para limpar" — isso produz um diff enorme que esconde a mudança real e altera versões que ninguém pediu para alterar;
- um commit cujo diff do lockfile é desproporcional à mudança declarada é rejeitado em revisão;
- em conflito de merge no lockfile, a resolução correta é reaplicar a operação de dependência com o pnpm sobre a base atualizada, não resolver o conflito linha a linha.

Instalar dependência nova sem autorização continua proibido por `docs/07-prompts-cursor.md` §19, independentemente do lockfile.

## 3.12 Migrations entram no histórico como fatos imutáveis

Migrations do Prisma são artefatos históricos. Uma vez aplicadas fora da máquina de quem as criou, elas não podem ser reescritas.

Regras:

- a migration é commitada junto com o `schema.prisma` que a originou e com o código que depende dela;
- migration já integrada a `main` nunca é editada; uma correção é sempre uma **nova** migration;
- uma migration nunca é renomeada, reordenada ou removida do histórico após integrada;
- nenhum commit contém `schema.prisma` alterado sem a migration correspondente — isso produz divergência silenciosa entre modelo e banco.

Essa regra deriva de `docs/07-prompts-cursor.md` §20 e de `docs/09.5-banco-de-dados.md`.

## 3.13 Documentação tem commit próprio, salvo quando é parte do contrato da mudança

Alteração de documentação não é feita silenciosamente durante uma implementação, conforme `docs/07-prompts-cursor.md` §55.

Regras:

- alteração isolada de documentação recebe commit próprio, com tipo `docs`;
- quando a mudança de código **implementa** um contrato recém-documentado, o commit de documentação vem **antes** do commit de implementação, refletindo a ordem obrigatória da ADR-037;
- documentação nunca é ajustada dentro de um commit de funcionalidade apenas para "fazer bater" com o que foi implementado;
- quando uma implementação revela necessidade de mudança de contrato, o fluxo é interromper, apontar o documento afetado, aguardar a atualização formal e só então continuar.

## 3.14 Nenhuma operação destrutiva é executada por iniciativa própria

Toda operação capaz de destruir trabalho, reescrever histórico ou alterar o passado publicado exige autorização explícita e específica, conforme a seção 5 deste documento.

Na dúvida sobre se uma operação é destrutiva, ela é tratada como destrutiva.

# 4. Padrões Aprovados

## 4.1 Estilo de mensagem de commit

O projeto adota o estilo **Conventional Commits** como **convenção de escrita preferida**.

Formato:

```
<tipo>(<escopo>): <descrição no imperativo, em português, minúscula, sem ponto final>
```

Exemplos aprovados:

```
feat(auth): implementa login
fix(sync): evita duplicidade de parcelas
docs(api): registra filtros Conta Azul
chore(repo): configura workspace
```

## 4.2 A convenção é de escrita, não uma dependência técnica

Esta é uma distinção deliberada e importante.

O estilo é adotado porque **torna o histórico legível e filtrável por assunto**, o que tem valor direto em um projeto que será auditado fase a fase. Ele **não** é adotado como entrada de nenhum processo automatizado.

Em consequência, no Dashboard Economização:

- não há geração automática de changelog a partir das mensagens;
- não há versionamento semântico derivado das mensagens;
- não há release automatizado disparado por tipo de commit;
- não há validação de mensagem por hook, `commitlint` ou equivalente;
- nenhuma etapa de build, deploy ou CI depende do formato da mensagem.

Caso, no futuro, se deseje qualquer uma dessas automações, ela exigirá ADR própria — porque no momento em que o formato passa a alimentar automação, ele deixa de ser convenção e passa a ser contrato, com custo de manutenção correspondente.

Consequência prática: uma mensagem clara e correta que não siga exatamente o formato é preferível a uma mensagem que siga o formato e não explique nada. O formato serve à clareza; quando conflitar com ela, a clareza vence.

## 4.3 Tipos aprovados

| Tipo | Uso |
|---|---|
| `feat` | Nova funcionalidade ou comportamento visível |
| `fix` | Correção de defeito |
| `docs` | Documentação, incluindo a série 09 e as ADRs |
| `refactor` | Mudança de estrutura sem alteração de comportamento, conforme `09.22` |
| `test` | Criação ou ajuste de testes |
| `chore` | Configuração de repositório, ferramenta, dependência, script |
| `perf` | Otimização com ganho mensurável, conforme `09.18` |
| `build` | Docker, empacotamento, artefatos de construção |
| `ci` | Automação de `.github/` |
| `style` | Formatação sem efeito em comportamento |
| `revert` | Reversão explícita de commit anterior |

Não devem ser criados tipos novos sem necessidade real.

## 4.4 Escopos aprovados

O escopo identifica a área afetada. Escopos coerentes com a estrutura definida em `docs/09.1-estrutura-do-projeto.md` e com os módulos do produto:

`auth`, `tenants`, `admin`, `sync`, `conta-azul`, `dashboard`, `reports`, `insights`, `ai`, `jobs`, `queue`, `cache`, `db`, `prisma`, `api`, `frontend`, `backend`, `worker`, `shared`, `ui`, `infra`, `docker`, `repo`, `docs`.

Regras de escopo:

- o escopo é opcional quando a mudança é genuinamente transversal;
- um único escopo por commit; a necessidade de dois escopos normalmente indica dois commits;
- o escopo descreve **área do produto ou do repositório**, não nome de arquivo.

## 4.5 Conteúdo da descrição

A descrição responde **o que a mudança faz**, em uma linha:

- em português;
- no imperativo — "implementa", "corrige", "remove", "registra";
- iniciando em minúscula;
- sem ponto final;
- preferencialmente até cerca de 72 caracteres;
- concreta e verificável.

Descrições aprovadas:

```
feat(tenants): permite ativar e desativar empresa no painel administrativo
fix(reports): corrige período do relatório na virada de mês
fix(sync): evita duplicidade de parcelas
perf(dashboard): reduz consultas do painel principal de N+1 para consulta agregada
```

Descrições reprovadas:

```
ajustes
correções gerais
melhorias
wip
update
resolve problema
finaliza tarefa
```

Cada uma dessas obriga quem lê o histórico a abrir o diff para descobrir o que aconteceu — que é exatamente o custo que a convenção existe para evitar.

## 4.6 Corpo da mensagem

O corpo é opcional e é usado quando a mudança exige contexto que o diff não fornece.

O corpo deve explicar **por que**, não repetir **o que**. Casos em que o corpo é recomendado:

- a correção tem causa raiz não óbvia;
- houve uma alternativa descartada e a escolha merece registro;
- há impacto operacional — migration destrutiva, necessidade de reprocessamento, mudança de variável de ambiente;
- há relação com uma ADR ou com um requisito formal do PRD.

Formato: linha em branco após a descrição, texto em parágrafos curtos, referências ao final.

```
fix(sync): evita duplicidade de parcelas

A chave de deduplicação usava apenas o identificador do título,
o que permitia que parcelas distintas do mesmo título fossem
tratadas como o mesmo registro na reexecução da sincronização.

A chave passa a considerar título e número da parcela.

Requisito: SYNC-004
Referência: docs/04-api-conta-azul.md
```

## 4.7 Tamanho do commit

Commits pequenos e coerentes são o padrão, conforme ADR-036, que estabelece justamente "commits menores, revisões menores, maior previsibilidade".

Diretrizes:

- o commit é tão pequeno quanto permitir manter o projeto íntegro;
- um commit que ninguém consegue revisar em poucos minutos é um problema de granularidade, não de complexidade do assunto;
- um commit que só faz sentido junto com o próximo commit deveria ser um único commit;
- tamanho é consequência da coerência, não uma meta em si: dividir artificialmente uma mudança indivisível produz commits quebrados, o que é pior.

## 4.8 Sequência operacional de commit

Quando o commit for autorizado, a sequência é:

1. verificar a branch atual;
2. verificar o estado completo da working tree;
3. identificar alterações pré-existentes e mantê-las fora do commit;
4. revisar o diff do que será incluído, arquivo a arquivo;
5. reexecutar as validações aplicáveis se o estado mudou desde a última execução;
6. adicionar **explicitamente** os arquivos da tarefa;
7. criar o commit com a mensagem definida;
8. reportar branch, hash, mensagem, arquivos incluídos e working tree final.

Nesta sequência não há amend, rebase, merge, reset ou push, conforme `docs/07-prompts-cursor.md` §53.

## 4.9 Sequência operacional de push

Quando o push for autorizado separadamente:

1. confirmar a branch;
2. confirmar o HEAD;
3. confirmar o remoto;
4. confirmar a relação ahead/behind;
5. confirmar que a working tree está no estado esperado;
6. executar o push somente se o histórico permitir atualização segura;
7. reportar branch, HEAD, remoto e resultado.

Não se cria commit novo, não se faz amend, rebase, merge ou force push nesta etapa, conforme `docs/07-prompts-cursor.md` §54.

Se o remoto estiver à frente, o push **não é forçado**. A divergência é relatada e a decisão pertence ao responsável pelo projeto.

## 4.10 Relatório de Git

Todo relatório final informa a seção de Git no formato de `docs/07-prompts-cursor.md` §48:

```
### Git
- Branch: main
- Commit: não realizado
- Push: não realizado
- Working tree: 4 arquivos criados, não adicionados ao índice
- Alterações pré-existentes preservadas: docs/06-roadmap.md (modificado antes da tarefa)
```

Ausência de commit é informação, não omissão: ela é declarada explicitamente.

# 5. Padrões Proibidos

## 5.1 Operações proibidas sem autorização explícita

É proibido executar, por iniciativa própria:

1. `git reset --hard`, em qualquer referência;
2. `git reset` que descarte trabalho não commitado;
3. `git clean` em modo destrutivo, com ou sem diretórios;
4. `git checkout` ou `git restore` que descarte alterações locais;
5. `git rebase` em qualquer forma, interativo ou não;
6. `git push --force` e `git push --force-with-lease`;
7. `git commit --amend`;
8. `git revert` sem autorização, ainda que não seja destrutivo do histórico;
9. `git merge` não solicitado;
10. `git stash drop`, `git stash clear` ou descarte de stash existente;
11. remoção massiva de arquivos versionados;
12. exclusão de branch, local ou remota;
13. remoção ou movimentação de tags;
14. alteração de configuração do Git — usuário, e-mail, remoto, hooks;
15. instalação ou modificação de hooks de repositório;
16. qualquer operação que reescreva histórico já publicado;
17. qualquer operação destrutiva no banco de dados associada a uma operação de Git.

Esta lista consolida `docs/07-prompts-cursor.md` §44 e a amplia.

Os itens 7 e 5 merecem menção específica porque frequentemente parecem inofensivos: `--amend` **substitui** um commit existente, e `rebase` **reescreve** commits. Ambos destroem estado que pode já ter sido revisado ou publicado.

## 5.2 Práticas proibidas de conteúdo

É proibido:

1. commitar sem autorização explícita;
2. fazer push com base em uma autorização que era apenas de commit;
3. incluir no commit arquivos não relacionados à tarefa;
4. incluir alterações pré-existentes do usuário sem necessidade e sem menção;
5. adicionar tudo o que estiver modificado sem revisar o diff;
6. commitar `.env`, credencial, token, chave privada ou qualquer segredo;
7. commitar `node_modules/`, `.next/`, `dist/`, cache de ferramenta ou artefato de build;
8. commitar dump de banco ou dado real de cliente;
9. commitar código sabidamente quebrado em `main`;
10. commitar com testes relevantes falhando, `lint` falhando ou `typecheck` falhando;
11. alterar `schema.prisma` sem a migration correspondente no mesmo commit;
12. editar, renomear ou remover migration já integrada a `main`;
13. editar `pnpm-lock.yaml` manualmente;
14. regenerar o lockfile inteiro sem necessidade declarada;
15. misturar refatoração ampla com correção de defeito no mesmo commit;
16. misturar reformatação automática de arquivos não relacionados com mudança funcional;
17. alterar documentação silenciosamente dentro de um commit de implementação;
18. escrever mensagem vaga do tipo "ajustes", "correções", "wip" ou "melhorias";
19. escrever mensagem em desacordo com o que o diff realmente contém;
20. usar o histórico do Git como registro de decisão arquitetural — isso pertence às ADRs em `docs/08-decisoes-tecnicas.md`.

O item 19 é o mais grave da lista em termos de auditoria: um histórico com mensagens incorretas é pior do que um histórico com mensagens genéricas, porque induz ativamente ao erro quem investiga um defeito meses depois.

# 6. Exemplos Conceituais

## 6.1 Commit coerente e commit incoerente

Incoerente:

```
feat(admin): cria cadastro de empresas, ajusta lint, atualiza README,
renomeia funções do módulo de relatórios e sobe versão do Prisma
```

Coerente, dividido:

```
chore(repo): ajusta regra de lint para arquivos de configuração
feat(tenants): implementa cadastro de empresa no painel administrativo
feat(tenants): implementa ativação e desativação de empresa
docs(repo): atualiza README com o fluxo de cadastro de empresa
```

A renomeação em `reports` e a atualização do Prisma não pertencem a esta tarefa e não deveriam ter sido feitas — ver `docs/09.22-refatoracao.md`.

## 6.2 Sequência de uma fase típica

Fase 0.5 — Banco de Dados, com autorização de commit e sem autorização de push:

```
docs(db): registra modelagem inicial das entidades de empresa e usuário
feat(prisma): define schema inicial de tenants e usuários
feat(prisma): adiciona migration inicial
test(db): adiciona testes de escopo por empresa nas consultas base
```

Relatório final:

```
### Git
- Branch: main
- Commits: 4 (hashes listados)
- Push: não realizado — não autorizado neste prompt
- Working tree: limpa
```

## 6.3 Migration e código dependente

Correto — coesão obrigatória em um commit:

```
feat(sync): adiciona cursor de sincronização por empresa

Inclui migration que cria a coluna, o campo no schema
e o uso do cursor no planejamento da sincronização.
Separar produziria um commit intermediário em que o código
referencia coluna inexistente.
```

Incorreto:

```
feat(prisma): altera schema com cursor de sincronização
(sem migration; o banco de qualquer outro ambiente diverge silenciosamente)
```

## 6.4 Correção de migration já integrada

Incorreto:

```
editar a migration 20260801_add_sync_cursor para corrigir o tipo da coluna
```

Correto:

```
fix(prisma): corrige tipo da coluna de cursor de sincronização

Nova migration incremental. A migration original permanece
inalterada por já ter sido aplicada fora do ambiente local.
```

## 6.5 Alteração pré-existente encontrada no início da tarefa

Situação: ao iniciar a Fase 3, existem alterações não commitadas em `docs/06-roadmap.md`, feitas pelo usuário.

Conduta correta:

```
- não adicionar o arquivo ao commit da fase;
- não descartar as alterações;
- não executar reset, clean ou checkout sobre ele;
- concluir a fase normalmente;
- relatar:

### Git
- Alterações pré-existentes preservadas: docs/06-roadmap.md
  (modificado antes do início da tarefa; fora do escopo desta fase)
```

Conduta proibida:

```
- "limpar" a working tree para começar do zero;
- incluir o arquivo no commit "já que estava modificado".
```

## 6.6 Push com remoto à frente

Situação: ao preparar o push autorizado, `main` local está 2 commits à frente e 1 commit atrás do remoto.

Conduta correta:

```
BLOQUEIO
O que falta: decisão sobre como integrar o commit remoto.
Por que é necessário: o push exigiria rebase ou merge,
ambos fora da autorização concedida.
O que foi concluído: os 2 commits locais estão criados e validados.
```

Conduta proibida:

```
git pull --rebase
git push --force
```

Ambas reescrevem ou integram histórico sem autorização.

## 6.8 Segredo commitado por engano

Conduta correta:

```
1. tratar o segredo como comprometido;
2. rotacionar imediatamente a credencial na origem;
3. remover o valor do repositório e ajustar o .gitignore;
4. registrar o incidente;
5. não tentar reescrever o histórico por iniciativa própria.
```

Conduta proibida:

```
- fazer amend do commit anterior para "apagar" o segredo;
- executar rebase ou filtro de histórico sem autorização;
- considerar o problema resolvido por o valor não estar mais no HEAD.
```

O histórico é apenas um dos lugares em que o segredo passou a existir.

# 7. Critérios de Revisão

Um trabalho envolvendo Git só é aprovado quando:

1. a branch de trabalho for `main` ou uma branch de trabalho justificada e autorizada;
2. o estado do repositório tiver sido verificado antes das alterações;
3. alterações pré-existentes tiverem sido preservadas e relatadas;
4. nenhum commit tiver sido criado sem autorização explícita;
5. nenhum push tiver sido executado sem autorização própria e separada;
6. cada commit representar uma unidade coerente e compreensível isoladamente;
7. o diff de cada commit tiver sido revisado antes da criação;
8. nenhum arquivo não relacionado à tarefa estiver incluído;
9. nenhum segredo, credencial ou dado real de cliente estiver incluído;
10. nenhum arquivo gerado, `node_modules` ou artefato de build estiver incluído;
11. as mensagens descreverem com precisão o que o diff contém;
12. as mensagens seguirem o estilo aprovado, ou o superarem em clareza;
13. nenhuma mensagem for genérica ou vazia de conteúdo verificável;
14. alteração de dependência estiver acompanhada do lockfile no mesmo commit;
15. o diff do lockfile for proporcional à mudança declarada;
16. alteração de `schema.prisma` estiver acompanhada da migration correspondente;
17. nenhuma migration já integrada tiver sido editada, renomeada ou removida;
18. alterações de documentação estiverem em commit próprio, salvo coesão obrigatória;
19. nenhuma operação destrutiva da seção 5.1 tiver sido executada;
20. as validações aplicáveis estiverem verdes no estado commitado;
21. o relatório final informar branch, commit, push e working tree.

# 9. Diretriz Final

No Dashboard Economização, o Git não registra o que foi digitado. Registra o que foi **decidido, validado e aceito**.

Três regras resumem este documento e prevalecem sobre qualquer conveniência:

**Commit e push são autorizações separadas, e nenhuma delas é presumida.** Terminar o trabalho não é permissão para publicá-lo.

**O que entra no commit é escolhido, nunca varrido.** Cada arquivo incluído é uma decisão consciente de quem commita.

**O passado não se reescreve por iniciativa própria.** Reset destrutivo, rebase, amend e force push apagam trabalho e apagam evidência — em um projeto que se desenvolve por fases auditáveis, essa evidência é justamente o que permite entender como o produto chegou onde está.

Um histórico em que cada commit é pequeno, coerente, honesto na mensagem e validado antes de existir vale mais para a manutenção deste produto do que qualquer sofisticação de fluxo de branches.
