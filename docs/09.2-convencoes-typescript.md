Status: Ativo

# 1. Objetivo

Este documento define o padrão oficial de TypeScript do Dashboard Economização.

TypeScript é a única linguagem de aplicação do projeto. Ele é utilizado no `frontend/` (Next.js), no `backend/` (Fastify), no `worker/` (BullMQ) e em todos os pacotes de `packages/`.

O objetivo deste padrão é que o compilador funcione como a primeira camada de defesa da plataforma. Em um sistema que manipula dados financeiros de múltiplas empresas, um tipo frouxo é um risco de negócio: ele permite que um valor ausente se transforme em zero em um indicador, que um `tenantId` opcional atravesse uma consulta, ou que um campo renomeado pela API da Conta Azul passe silenciosamente para o domínio interno.

A regra central deste documento: **o tipo deve descrever a realidade, não a conveniência**.

---

# 2. Escopo

Este documento regula:

- a configuração obrigatória do compilador;
- tipagem em fronteiras (HTTP, banco, filas, integrações, IA);
- o tratamento de `any` e `unknown`;
- a validação de dados externos;
- nomenclatura de tipos, arquivos e símbolos;
- escolha entre `interface`, `type`, `enum` e união literal;
- uso de genéricos;
- a política oficial de `null` versus `undefined`;
- imutabilidade e `readonly`;
- funções assíncronas e tratamento de erro;
- padrões de `export` e `import`;
- tipos de bibliotecas externas;
- as exceções em que `any` é excepcionalmente tolerado.

Este documento não regula:

- organização de diretórios — ver `09.1-estrutura-do-projeto.md`;
- arquitetura de camadas do backend — ver `09.3-backend.md`;
- padrões de componente React — ver `09.4-frontend.md`;

# 3. Regras Obrigatórias

## 3.1 Configuração do compilador

Todo pacote deverá herdar de `tsconfig.base.json` na raiz. As seguintes opções são obrigatórias e não podem ser desativadas em nenhum pacote:

```json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "noUncheckedIndexedAccess": true,
    "forceConsistentCasingInFileNames": true,
    "isolatedModules": true
  }
}
```

Significado prático de cada opção neste projeto:

**`strict`** — habilita o conjunto completo de verificações estritas. É o piso do projeto, não uma meta futura.

**`noImplicitAny`** — nenhum parâmetro, propriedade ou retorno pode adquirir `any` por omissão. Se o tipo não é conhecido, ele deve ser declarado como `unknown` e estreitado.

**`strictNullChecks`** — ausência de valor é sempre explícita. Em dados financeiros, "sem valor" e "valor zero" são fatos diferentes: uma empresa sem títulos vencidos não é a mesma coisa que uma empresa cuja sincronização ainda não ocorreu.

**`noUncheckedIndexedAccess`** — acesso por índice retorna o tipo com `| undefined`. Esta opção existe para proteger o Motor Analítico, que trabalha intensamente com séries temporais, agregações por período e agrupamentos por categoria, onde a chave consultada frequentemente não existe.

**`forceConsistentCasingInFileNames`** — evita divergência entre macOS (desenvolvimento) e Linux da VPS (produção), onde o sistema de arquivos diferencia maiúsculas.

**`isolatedModules`** — garante que cada arquivo seja transpilável isoladamente, requisito do pipeline do Next.js e do build do backend.

Recomendações adicionais aprovadas, a serem habilitadas por pacote conforme viabilidade:

- `noImplicitOverride`;
- `noFallthroughCasesInSwitch`;
- `exactOptionalPropertyTypes` no `backend/` e em `packages/types`;
- `verbatimModuleSyntax` no `backend/` e no `worker/`.

Desabilitar qualquer opção obrigatória exige ADR. Reduzir rigor localmente por conveniência é proibido.

## 3.2 Proibição de supressão de erro do compilador

São proibidos:

- `@ts-ignore`;
- `@ts-nocheck`;
- `eslint-disable` de regras de tipagem sem justificativa;
- casts encadeados do tipo `as unknown as T` para forçar compatibilidade.

`@ts-expect-error` é tolerado exclusivamente em código de teste que verifica intencionalmente uma falha de tipagem, e sempre com comentário explicando o que se espera falhar.

Erro de compilação é informação. Silenciá-lo transfere o defeito para produção.

## 3.3 Tipagem explícita nas fronteiras

Fronteira é todo ponto onde o dado entra ou sai de um limite de confiança ou de um limite de módulo.

São fronteiras obrigatoriamente tipadas de forma explícita:

- requisição e resposta HTTP do backend;
- payload de job publicado e consumido no BullMQ;
- resposta da API da Conta Azul;
- entrada e saída do provedor de IA;
- retorno público de repositório;
- assinatura pública de serviço e caso de uso;
- retorno de função exportada de `packages/*`;
- variáveis de ambiente;
- resultado de leitura de cache no Redis.

Nessas fronteiras, o tipo de retorno é sempre escrito, mesmo quando a inferência funcionaria.

```ts
// Fronteira: assinatura pública de caso de uso — tipo explícito obrigatório
export async function getDashboardIndicators(
  input: GetDashboardIndicatorsInput,
): Promise<DashboardIndicators> {
  // ...
}
```

Dentro do corpo de uma função, a inferência é preferida. Anotar `const total: number = 0` é ruído.

```ts
// Interno: inferência é preferida
const total = entries.reduce((sum, entry) => sum + entry.amount, 0);
```

## 3.4 `unknown` antes de `any`

Todo dado de origem externa entra no sistema como `unknown` e só adquire tipo depois de validação.

```ts
// Proibido
const payload = await response.json() as ContaAzulInvoice[];

// Obrigatório
const raw: unknown = await response.json();
const payload = contaAzulInvoiceListSchema.parse(raw);
```

`as` não valida nada. Ele apenas instrui o compilador a parar de verificar. Usar `as` sobre dado externo transforma um erro detectável em corrupção silenciosa do banco.

## 3.5 Validação obrigatória de dados externos

Todo dado que atravessa a fronteira do processo deverá ser validado em runtime por schema antes de ser utilizado.

Aplica-se obrigatoriamente a:

- body, query, params e headers relevantes das requisições do backend;
- toda resposta da API da Conta Azul;
- todo payload de job consumido de fila;
- toda resposta estruturada do provedor de IA;
- variáveis de ambiente, validadas uma única vez na inicialização do processo;
- todo valor desserializado do Redis.

Regras de validação:

1. O tipo estático deverá ser derivado do schema, e não declarado em paralelo. Declarar tipo e schema separadamente cria duas fontes de verdade que divergem silenciosamente.
2. Falha de validação de entrada HTTP resulta em erro de requisição inválida, nunca em exceção não tratada.
3. Falha de validação de resposta externa da Conta Azul é tratada como erro de integração e registrada com contexto suficiente para diagnóstico, sem vazar credencial.
4. O schema de validação do dado externo pertence ao módulo de integração e não deve ser reutilizado como tipo de domínio.

O último ponto é decisivo: o schema descreve o formato da Conta Azul; o tipo de domínio descreve o modelo interno do Dashboard Economização. A tradução entre os dois é responsabilidade do normalizador (ARQ-006).

```ts
// integrations/conta-azul/schemas/invoice.schema.ts
export const contaAzulInvoiceSchema = z.object({ /* formato externo */ });
export type ContaAzulInvoice = z.infer<typeof contaAzulInvoiceSchema>;

// integrations/conta-azul/normalizer/invoice.normalizer.ts
export function normalizeInvoice(external: ContaAzulInvoice): ReceivableEntry {
  // tradução explícita para o modelo interno
}
```

Nomes de campo originados da Conta Azul nunca devem aparecer fora do diretório de integração.

## 3.6 Validação do ambiente

Variáveis de ambiente nunca são lidas diretamente por meio de `process.env` no corpo da aplicação.

Cada processo (`backend/`, `worker/`, `frontend/`) valida seu ambiente uma única vez na inicialização e exporta um objeto de configuração tipado e imutável.

```ts
// Proibido em qualquer ponto da aplicação
const url = process.env.DATABASE_URL;

// Obrigatório
import { env } from '../config/env';
const url = env.DATABASE_URL;
```

Se uma variável obrigatória estiver ausente ou inválida, o processo deverá falhar na inicialização com mensagem clara. Nunca deverá iniciar com configuração incompleta.

Segredo validado nunca é registrado em log, nem em mensagem de erro de validação.

## 3.7 Tipos nominais para identificadores

Identificadores de domínio deverão utilizar tipos nominais (branded types) para impedir troca acidental.

```ts
// packages/types/src/ids.ts
declare const brand: unique symbol;
type Brand<T, B extends string> = T & { readonly [brand]: B };

export type TenantId = Brand<string, 'TenantId'>;
export type UserId = Brand<string, 'UserId'>;
export type SyncRunId = Brand<string, 'SyncRunId'>;
export type InsightId = Brand<string, 'InsightId'>;
```

Motivo: em uma plataforma multiempresa, `string` como tipo de `tenantId` permite que um `userId` seja passado no lugar de um `tenantId` sem que o compilador reclame. Com tipo nominal, essa troca é erro de compilação.

Aplicação mínima obrigatória: `TenantId`. Os demais identificadores deverão adotar o padrão progressivamente.

## 3.8 Valores monetários

Valores monetários nunca deverão ser representados por `number` de ponto flutuante em cálculo financeiro.

A representação oficial deverá ser inteira em centavos ou decimal exato, conforme definido em `09.5-banco-de-dados.md`, e deverá possuir tipo próprio em `packages/types`.

```ts
export type Cents = Brand<number, 'Cents'>;
```

Conversão entre centavos e representação de exibição ocorre apenas na camada de apresentação, utilizando as funções de `packages/shared/src/money/`.

## 3.9 Proibição de tipo estrutural implícito em resposta de API

Nenhuma rota deverá retornar um objeto cuja forma seja definida apenas pela inferência do que o serviço devolveu.

O contrato de resposta é declarado explicitamente em `packages/types`, e a rota declara esse tipo como retorno.

Motivo: sem declaração explícita, uma alteração interna no repositório altera silenciosamente o contrato público consumido pelo frontend, e nenhum erro de compilação aponta a quebra.

# 4. Padrões Aprovados

## 4.1 Nomenclatura

| Elemento | Convenção | Exemplo |
|---|---|---|
| Arquivo | `kebab-case` | `get-dashboard-indicators.ts` |
| Arquivo com sufixo de papel | `kebab-case.papel.ts` | `invoice.normalizer.ts`, `tenant.repository.ts`, `sync.schema.ts` |
| Componente React (arquivo) | `kebab-case` | `delinquency-card.tsx` |
| Componente React (símbolo) | `PascalCase` | `DelinquencyCard` |
| Tipo, interface, classe, enum | `PascalCase` | `DashboardIndicators` |
| Função, variável, propriedade | `camelCase` | `resolvePeriodRange` |
| Constante de módulo | `SCREAMING_SNAKE_CASE` | `MAX_SYNC_RETRIES` |
| Tipo genérico | `PascalCase` descritivo | `TPayload`, `TEntity` |
| Booleano | prefixo de predicado | `isActive`, `hasPendingSync`, `canAccessTenant` |
| Função assíncrona | verbo de ação | `fetchInvoices`, `runTenantSync` |

Regras adicionais:

- proibido prefixo `I` em interface (`IUser` é reprovado; use `User`);
- proibido sufixo `Interface`, `Type` ou `Model` como decoração (`UserType` só é aceito se representar de fato o *tipo* de um usuário como dado de domínio);
- proibido nome abreviado sem significado (`tmp`, `d`, `res2`, `aux`, `x1`);
- `res` e `req` são aceitos apenas em handlers HTTP, onde são convenção do Fastify;
- nomes de domínio deverão usar o vocabulário do PRD em português quando o conceito for de negócio (`inadimplencia` só é aceito em rótulo exibido; identificadores de código permanecem em inglês técnico — `delinquency`).

Padrão oficial de idioma: identificadores de código em inglês; conteúdo exibido ao usuário, comentários e documentação em português do Brasil.

Observação: exemplos de outros capítulos da série podem usar termos em português como pseudocódigo ilustrativo. O código do repositório permanece com identificadores em inglês, conforme esta regra.

## 4.2 `interface` versus `type`

Regra prática:

**Use `interface`** para formas de objeto que representam entidades, contratos de dependência e pontos de extensão.

```ts
export interface TenantRepository {
  findById(id: TenantId): Promise<Tenant | null>;
  findActiveByOwner(userId: UserId): Promise<readonly Tenant[]>;
}
```

**Use `type`** para uniões, interseções, tipos utilitários, tipos derivados, funções e aliases.

```ts
export type SyncTrigger = 'scheduled' | 'manual' | 'oauth-connected' | 'reconciliation';
export type IndicatorResolver = (input: AnalyticsQuery) => Promise<IndicatorValue>;
export type PartialTenantBranding = Partial<TenantBranding>;
```

Não é permitido misturar os dois estilos para o mesmo conceito no mesmo módulo.

## 4.3 Uniões literais em vez de `enum`

O padrão oficial do projeto é **união de literais de string**, não `enum`.

```ts
// Aprovado
export type SyncStatus =
  | 'pending'
  | 'running'
  | 'completed'
  | 'failed'
  | 'cancelled';

export const SYNC_STATUSES = [
  'pending',
  'running',
  'completed',
  'failed',
  'cancelled',
] as const satisfies readonly SyncStatus[];
```

Motivos:

- serializa naturalmente em JSON, sem tradução na fronteira HTTP;
- não gera código em runtime, respeitando `isolatedModules`;
- é legível em log, em payload de fila e em coluna do banco;
- permite estreitamento exaustivo em `switch`;
- evita a incompatibilidade entre `enum` do TypeScript e enum do Prisma.

Exceção aprovada: os enums gerados pelo Prisma são utilizados dentro da camada de persistência do backend. Eles não devem ser reexportados para `packages/types` nem para o frontend; a fronteira converte para união literal.

`enum` numérico é proibido em todo o projeto.

## 4.4 Exaustividade obrigatória

Todo `switch` sobre união literal de domínio deverá ser exaustivo e garantido por verificação no caso `default`.

```ts
function describeSeverity(severity: InsightSeverity): string {
  switch (severity) {
    case 'info':
      return 'Informativo';
    case 'warning':
      return 'Atenção';
    case 'critical':
      return 'Crítico';
    default:
      return assertNever(severity);
  }
}

export function assertNever(value: never): never {
  throw new Error(`Valor não tratado: ${String(value)}`);
}
```

Benefício direto: quando um novo status de sincronização ou uma nova severidade de insight for adicionada, o compilador aponta todos os pontos que precisam de tratamento.

## 4.5 Genéricos

Genéricos são permitidos quando removem duplicação real e preservam informação de tipo.

Regras:

1. todo parâmetro genérico deverá ter nome descritivo (`TPayload`, `TEntity`, `TResult`), não `T`, `U`, `V` isolados, exceto em utilitários de uma linha amplamente convencionais;
2. genérico sem restrição (`extends`) deverá ser justificado; a maioria dos casos do projeto exige restrição;
3. proibido genérico que só existe para permitir um cast interno;
4. proibido genérico com mais de três parâmetros — isso indica abstração equivocada;
5. proibida programação de tipos elaborada (recursão condicional profunda, manipulação de template literal complexa) fora de `packages/types`, e mesmo lá somente com comentário explicando a intenção.

Exemplo aprovado — contrato de job de fila:

```ts
export interface JobDefinition<TPayload> {
  readonly name: string;
  readonly schema: Schema<TPayload>;
  handle(payload: TPayload, context: JobContext): Promise<void>;
}
```

Critério de legibilidade: se um genérico exige que o revisor pare para decifrá-lo, ele deve ser substituído por dois tipos concretos.

## 4.6 `null` versus `undefined` — política oficial

A ambiguidade entre `null` e `undefined` é fonte recorrente de defeito. O projeto adota a seguinte política, obrigatória em todas as camadas:

**`null` significa ausência conhecida e intencional de valor.**

Uso: colunas nuláveis do banco, campos de configuração deliberadamente não definidos, resultado de busca que não encontrou registro.

```ts
async function findById(id: TenantId): Promise<Tenant | null>;
```

**`undefined` significa "não informado" ou "não aplicável naquele contexto".**

Uso: propriedade opcional de objeto, parâmetro opcional de função, campo omitido em requisição de atualização parcial.

```ts
interface UpdateTenantBrandingInput {
  primaryColor?: string;
  logoUrl?: string;
}
```

Regras derivadas:

1. repositório que busca um registro retorna `T | null`, nunca `T | undefined`, nunca lança exceção por ausência;
2. propriedade opcional usa `?`, nunca `| null` combinado com `?`;
3. `T | null | undefined` é proibido em API pública; se apareceu, a modelagem está errada;
4. na resposta HTTP, ausência é representada por `null` explícito quando o campo pertence ao contrato, e pela omissão do campo quando ele é opcional no contrato;
5. em dado financeiro, `null` nunca deverá ser convertido silenciosamente em `0`; a conversão, quando necessária, é decisão explícita do domínio e deve estar documentada no código.

A regra 5 é crítica para a integridade dos indicadores. Um período sem dados sincronizados não é um período com receita zero.

## 4.7 Imutabilidade e `readonly`

Padrões obrigatórios:

- todas as propriedades de tipos que representam contrato de API, payload de job e valor de domínio deverão ser `readonly`;
- coleções expostas em retorno público deverão ser `readonly T[]`;
- constantes de módulo deverão usar `as const`;
- objeto de configuração deverá ser imutável após a inicialização.

```ts
export interface DashboardIndicators {
  readonly tenantId: TenantId;
  readonly period: AnalyticsPeriod;
  readonly revenue: Cents;
  readonly expenses: Cents;
  readonly delinquency: Cents;
  readonly series: readonly IndicatorPoint[];
}
```

Proibido:

- mutar parâmetro recebido por função;
- mutar objeto retornado por repositório;
- usar `push` sobre coleção recebida de outra camada.

Transformações devem produzir novo valor. Em cálculo analítico, mutação compartilhada torna o resultado dependente da ordem de execução e inviabiliza recálculo confiável.

## 4.8 Acesso indexado sob `noUncheckedIndexedAccess`

Com a opção habilitada, acesso por índice retorna `T | undefined`. A ausência deverá ser tratada, nunca eliminada por cast.

```ts
// Proibido
const first = entries[0] as ReceivableEntry;

// Aprovado
const first = entries[0];
if (first === undefined) {
  return emptyIndicators(tenantId, period);
}

// Aprovado para mapas de agregação
const bucket = totalsByCategory.get(category) ?? 0;
```

Para agregações do Motor Analítico, prefira `Map` com valor padrão explícito a objeto indexado por string.

## 4.9 Funções assíncronas

Regras:

1. toda função que retorna `Promise` deverá ser declarada `async` ou ter retorno `Promise<T>` explícito;
2. `Promise` nunca deverá ser criada e ignorada; toda promessa é aguardada ou explicitamente entregue a um mecanismo que a gerencia;
3. `void` sobre promessa é proibido como forma de silenciar aviso de promessa não tratada;
4. operações independentes deverão usar `Promise.all`; operações que podem falhar parcialmente sem invalidar as demais deverão usar `Promise.allSettled`;
5. `try/catch` só deverá existir onde há decisão real a tomar; capturar e relançar sem alterar nada é ruído;
6. o valor capturado em `catch` é `unknown` e deverá ser estreitado antes de uso;
7. em código de integração e de job, toda operação de rede deverá ter timeout definido.

```ts
try {
  await connector.fetchInvoices(page);
} catch (error: unknown) {
  if (error instanceof ContaAzulRateLimitError) {
    throw new RetryableIntegrationError('Limite da API atingido', { cause: error });
  }
  throw error;
}
```

Erros de domínio deverão ser classes próprias que estendem `Error`, permitindo estreitamento por `instanceof`. Lançar string ou objeto literal é proibido.

## 4.10 `exports`

Padrões obrigatórios:

- `export` nomeado é o padrão do projeto;
- `export default` é proibido, com a única exceção dos arquivos em que o framework exige, como páginas e layouts do Next.js;
- cada arquivo deverá exportar um conceito principal;
- `export *` é proibido, exceto no arquivo de índice público de um pacote de `packages/`;
- reexportação em cascata dentro de uma aplicação é proibida, porque oculta a origem real do símbolo.

Motivo da proibição de `export default`: dificulta busca por nome no repositório, permite que o mesmo símbolo seja importado com nomes diferentes em arquivos diferentes, e prejudica refatoração automática.

## 4.11 `imports`

Ordem obrigatória, com linha em branco entre grupos:

1. módulos nativos do Node (`node:` prefixado obrigatoriamente);
2. dependências externas;
3. pacotes internos do workspace (`@dashboard-economizacao/*`);
4. imports relativos do próprio pacote;
5. imports de tipo, quando separados.

```ts
import { randomUUID } from 'node:crypto';

import type { FastifyInstance } from 'fastify';

import type { TenantId } from '@dashboard-economizacao/types';
import { formatCurrency } from '@dashboard-economizacao/shared';

import { tenantRepository } from './tenant.repository';
```

Regras adicionais:

- import de tipo deverá usar `import type`;
- import relativo é permitido apenas dentro do mesmo pacote;
- proibido import relativo atravessando fronteira de pacote (ver `09.1`, seção 3.4);
- proibido import circular; se ocorreu, a responsabilidade dos módulos está mal distribuída;
- módulos nativos do Node deverão usar o prefixo `node:` (`node:crypto`, não `crypto`).

## 4.12 Tipos de bibliotecas externas

Regras:

1. preferir bibliotecas que distribuam tipos próprios;
2. quando os tipos vierem de `@types/*`, a dependência deverá ser declarada em `devDependencies` com versão compatível;
3. biblioteca sem tipo só poderá ser adotada com justificativa; nesse caso, uma declaração local mínima deverá ser criada em `types/` do pacote consumidor, tipando apenas o que é efetivamente utilizado;
4. proibido declarar `declare module 'x'` vazio, o que equivale a tipar a biblioteca como `any`;
5. tipos de biblioteca externa não deverão ser reexportados como tipo de domínio; o domínio possui seus próprios tipos e a fronteira faz a tradução;
6. tipo inferido de biblioteca externa não deverá vazar para assinatura pública de serviço — em especial tipos do Prisma, do Fastify e do BullMQ.

A regra 6 protege o desacoplamento: se o retorno de um caso de uso é o tipo gerado pelo Prisma, uma alteração de schema quebra o contrato consumido pelo frontend.

## 4.13 Tipagem no Fastify

O backend deverá tipar rotas por meio de schemas de validação, e não por generics manuais preenchidos à mão.

O tipo de `request.body`, `request.query` e `request.params` deverá ser derivado do schema declarado na rota. Declarar o tipo manualmente e o schema separadamente é proibido, pelo mesmo motivo da seção 3.5.

O objeto de contexto autenticado (usuário, papel, `TenantId` validado) deverá possuir tipo próprio, declarado uma única vez, e deverá ser preenchido exclusivamente por hook de autenticação do backend.

Detalhes de implementação em `09.3-backend.md` e `09.6-api.md`.

## 4.14 Quando `any` é excepcionalmente permitido

`any` é proibido por padrão. Ele é tolerado apenas nas seguintes situações, e sempre com as três condições obrigatórias abaixo.

Situações toleradas:

1. **Interoperabilidade com biblioteca externa sem tipos adequados**, quando o cast é confinado a um único arquivo adaptador na camada de infraestrutura.
2. **Utilitário genérico interno de baixo nível** em `packages/types` ou `packages/shared`, cuja assinatura pública é totalmente tipada e cujo `any` é estritamente interno à implementação.
3. **Código de teste** que constrói deliberadamente um valor inválido para verificar comportamento de validação.
4. **Migração temporária** de um trecho legado, com prazo e responsável registrados.

Condições obrigatórias, cumulativas:

- **Confinamento**: o `any` nunca atravessa a fronteira pública. A função exportada tem tipo preciso.
- **Justificativa escrita**: comentário imediatamente acima explicando por que `unknown` com estreitamento não resolve o caso.
- **Aprovação em revisão**: a revisão menciona explicitamente a introdução do `any`.

```ts
// `any` justificado: o SDK do provedor de IA não expõe o tipo do stream parcial.
// `unknown` não resolve porque a leitura ocorre dentro do próprio SDK, antes do
// nosso ponto de acesso. O valor é validado por schema imediatamente abaixo e o
// retorno público desta função é totalmente tipado.
function readStreamChunk(chunk: any): AdvisorStreamChunk {
  return advisorStreamChunkSchema.parse(chunk);
}
```

`any` é **sempre proibido**, sem exceção, em:

- contrato de requisição ou resposta da API;
- payload de job de fila;
- retorno de repositório;
- assinatura pública de serviço ou caso de uso;
- qualquer tipo que participe de decisão de autorização ou de escopo de tenant;
- qualquer tipo que represente valor monetário ou resultado de indicador;
- tipos exportados por `packages/types`.

# 5. Padrões Proibidos

1. Desabilitar `strict`, `noImplicitAny`, `strictNullChecks` ou `noUncheckedIndexedAccess` em qualquer pacote.
2. `@ts-ignore` e `@ts-nocheck`.
3. `as unknown as T` para forçar compatibilidade.
4. `as` sobre dado externo em lugar de validação por schema.
5. `any` fora das exceções da seção 4.14.
6. `any` em contrato de API, payload de fila, retorno de repositório, valor monetário, indicador ou decisão de tenant.
7. `object` e `Function` como tipos.
8. `enum` numérico.
9. `enum` do TypeScript como padrão de domínio.
10. `switch` não exaustivo sobre união literal de domínio.
11. `T | null | undefined` em API pública.
12. Converter `null` financeiro em `0` implicitamente.
13. Repositório lançando exceção para representar "não encontrado".
14. `process.env` fora do módulo de configuração validada.
15. Tipo declarado em paralelo ao schema de validação (duas fontes de verdade).
16. Tipo do Prisma, do Fastify ou do BullMQ em assinatura pública de serviço.
17. Reexportar tipos do Prisma via `packages/types`.
18. Nome de campo da Conta Azul fora do diretório de integração.
19. `export default` fora de arquivo exigido pelo Next.js.
20. `export *` fora do índice público de pacote de `packages/`.
21. Import circular.
22. Import relativo atravessando fronteira de pacote.
23. Módulo nativo do Node sem prefixo `node:`.
24. Promessa criada e não aguardada; `void promise` para silenciar aviso.
25. `catch` que captura e relança sem alterar nada.
26. Erro lançado como string ou objeto literal.
27. Mutação de parâmetro ou de objeto recebido de outra camada.
28. Prefixo `I` em interface.
29. Abreviação sem significado em identificador.
30. Programação de tipos elaborada fora de `packages/types`.
31. `declare module 'x'` vazio.
32. `string` puro como tipo de `tenantId` em novo código.
33. `number` de ponto flutuante em cálculo monetário.

# 6. Exemplos Conceituais

## 6.1 Fronteira completa: da Conta Azul ao indicador

```ts
// 1. Schema do formato externo — vive na integração
export const contaAzulReceivableSchema = z.object({
  id: z.string(),
  valor: z.number(),
  data_vencimento: z.string(),
  situacao: z.string(),
});
export type ContaAzulReceivable = z.infer<typeof contaAzulReceivableSchema>;

// 2. Conector: entrada é unknown, saída é validada
async function fetchReceivables(page: number): Promise<readonly ContaAzulReceivable[]> {
  const raw: unknown = await httpClient.get(`/receivables?page=${page}`);
  return contaAzulReceivableListSchema.parse(raw);
}

// 3. Normalizador: traduz para o modelo interno
export function normalizeReceivable(external: ContaAzulReceivable): ReceivableEntry {
  return {
    externalId: external.id,
    amount: toCents(external.valor),
    dueDate: parseIsoDate(external.data_vencimento),
    status: mapReceivableStatus(external.situacao),
  };
}

// 4. Domínio: nenhum nome da Conta Azul sobreviveu
export interface ReceivableEntry {
  readonly externalId: string;
  readonly amount: Cents;
  readonly dueDate: Date;
  readonly status: ReceivableStatus;
}
```

## 6.2 Ausência de dado versus valor zero

```ts
// Proibido: apaga a diferença entre "sem sincronização" e "sem receita"
const revenue = indicators.revenue ?? 0;

// Aprovado: a ausência é um estado do contrato
export type IndicatorValue =
  | { readonly kind: 'available'; readonly value: Cents }
  | { readonly kind: 'no-data'; readonly reason: NoDataReason };

export type NoDataReason = 'never-synced' | 'period-outside-history' | 'sync-failed';
```

O frontend renderiza estados distintos para `available` e `no-data`, e o Consultor Financeiro trata `no-data` como falta de informação, nunca respondendo por inferência (seção 27 de `02-arquitetura.md`).

## 6.3 Tenant tipado nominalmente

```ts
// Sem tipo nominal: compila, e vaza dados entre empresas
async function getIndicators(tenantId: string, userId: string) { /* ... */ }
getIndicators(userId, tenantId); // ← erro silencioso

// Com tipo nominal: erro de compilação
async function getIndicators(tenantId: TenantId, userId: UserId) { /* ... */ }
getIndicators(userId, tenantId); // ← Type 'UserId' is not assignable to type 'TenantId'
```

O `TenantId` só é produzido após validação de autorização no backend. Nunca é construído a partir de valor recebido do frontend sem essa validação (ARQ-002).

## 6.4 Payload de job tipado e validado

```ts
export const syncTenantJobSchema = z.object({
  tenantId: tenantIdSchema,
  trigger: z.enum(['scheduled', 'manual', 'oauth-connected', 'reconciliation']),
  fullReload: z.boolean(),
});

export type SyncTenantJobPayload = z.infer<typeof syncTenantJobSchema>;
```

O consumidor valida o payload na entrada. Um job persistido no Redis antes de um deploy pode ter formato antigo; sem validação, ele entraria no domínio com forma inesperada.

# 7. Critérios de Revisão

Um commit em `main` (ou a integração de branch de trabalho) deverá ser recusado quando:

1. reduzir o rigor do compilador em qualquer pacote;
2. conter `@ts-ignore` ou `@ts-nocheck`;
3. introduzir `any` fora das exceções da seção 4.14, ou sem as três condições obrigatórias;
4. usar `as` sobre dado externo em lugar de validação por schema;
5. não validar dado de fronteira (HTTP, Conta Azul, fila, IA, Redis, ambiente);
6. declarar tipo em paralelo ao schema em lugar de derivá-lo;
7. ler `process.env` fora do módulo de configuração validada;
8. omitir tipo explícito em fronteira pública;
9. usar `enum` do TypeScript como padrão de domínio, ou qualquer `enum` numérico;
10. deixar `switch` de união literal sem verificação de exaustividade;
11. violar a política de `null` versus `undefined` da seção 4.6;
12. converter `null` financeiro em `0` sem decisão documentada;
13. expor tipo do Prisma, do Fastify ou do BullMQ em assinatura pública;
14. permitir que nome de campo da Conta Azul saia do diretório de integração;
15. usar `export default` fora de arquivo exigido pelo Next.js;
16. introduzir import circular ou import relativo entre pacotes;
17. criar promessa não aguardada, ou silenciá-la com `void`;
18. lançar valor que não seja instância de `Error`;
19. mutar parâmetro ou objeto recebido de outra camada;
20. omitir `readonly` em contrato de API, payload de job ou valor de domínio;
21. usar `string` puro como `tenantId` em código novo;
22. usar `number` de ponto flutuante em cálculo monetário.

Checklist objetivo de revisão de tipagem:

- [ ] `pnpm typecheck` passa em todos os pacotes.
- [ ] `pnpm lint` passa sem supressões novas.
- [ ] Nenhum `any` novo, ou `any` novo devidamente justificado e confinado.
- [ ] Todo dado externo é validado por schema antes do uso.
- [ ] Tipos derivados do schema, sem duplicação de fonte de verdade.
- [ ] Fronteiras públicas com tipo explícito.
- [ ] `null` e `undefined` conforme a política oficial.
- [ ] `readonly` aplicado em contratos e valores de domínio.
- [ ] Uniões literais no lugar de `enum`.
- [ ] Exaustividade garantida nos `switch` de domínio.
- [ ] Nenhum tipo de biblioteca externa em assinatura pública.

# 9. Diretriz Final

O Dashboard Economização manipula dados financeiros de empresas distintas em um mesmo sistema. Nesse contexto, tipagem não é preferência estilística: é controle de risco.

Cada uso de `any`, cada `as` sobre dado externo e cada `null` convertido silenciosamente em zero remove uma verificação que o compilador faria de graça, em troca de alguns segundos de conveniência.

O padrão do projeto é explícito: o dado externo entra como `unknown`, é validado por schema, é traduzido para o modelo interno e só então circula com tipo preciso. Fronteiras são declaradas; interiores são inferidos. Ausência é modelada, não mascarada.

Quando houver dúvida entre uma tipagem precisa e uma tipagem conveniente, prevalece a precisa.
