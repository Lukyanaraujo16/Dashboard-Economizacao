# Dashboard Economização

# 09.5 — Banco de Dados

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define o padrão oficial de implementação do banco de dados do Dashboard Economização.

A plataforma utiliza PostgreSQL como banco relacional e Prisma como ORM, conforme ADR-007 e ADR-008 do documento 08.

O objetivo deste padrão é garantir que a camada de persistência:

- represente fielmente o domínio interno definido no documento 03;
- preserve integralmente o isolamento multiempresa;
- armazene valores financeiros com exatidão decimal;
- mantenha rastreabilidade da origem externa dos dados sincronizados;
- possua histórico de migrations confiável e reproduzível;
- suporte crescimento de volume sem degradação;
- permaneça independente do formato de qualquer ERP externo.

Enquanto o documento 03 define o modelo conceitual e lógico, este documento define como esse modelo é materializado tecnicamente.

# 3. Regras Obrigatórias

## 3.1 O domínio interno não copia o Conta Azul

O modelo de dados representa o domínio do Dashboard Economização.

É obrigatório normalizar dados externos para o modelo interno durante a sincronização.

O schema não deverá:

- reproduzir a estrutura de resposta da API do Conta Azul;
- utilizar nomes de campos herdados do fornecedor;
- criar tabelas espelho por fornecedor para conceitos financeiros equivalentes;
- depender de formatos de status ou enumerações externas sem normalização.

Conforme a diretriz final do documento 03: a API do Conta Azul alimenta o domínio, ela não define o domínio.

## 3.2 Nomenclatura conceitual em inglês

As entidades utilizam nomenclatura conceitual em inglês, exatamente como definido no documento 03.

Exemplos oficiais:

`tenants`, `users`, `user_sessions`, `integrations`, `integration_credentials`, `sync_runs`, `receivables`, `payables`, `financial_transactions`, `financial_categories`, `customers`, `suppliers`, `metric_definitions`, `metric_snapshots`, `analytical_events`, `ai_insights`, `rules`, `reports`, `notifications`, `audit_logs`, `support_sessions`.

Regras:

- nomes de tabela em `snake_case` e plural;
- nomes de coluna em `snake_case` e singular;
- modelos Prisma em `PascalCase` singular, mapeados para o nome físico;
- campos Prisma em `camelCase`, mapeados para o nome físico.

O mapeamento entre convenção do Prisma e convenção física do PostgreSQL é obrigatório e explícito.

## 3.3 Identificador interno próprio

Toda entidade principal deverá possuir identificador interno próprio, gerado pela plataforma.

Identificadores externos de ERPs jamais serão utilizados como chave primária.

A estratégia de identificador deverá ser única e consistente em todo o schema. Não deverão coexistir estratégias diferentes para entidades equivalentes.

## 3.4 Isolamento por tenant

Toda tabela que contenha dado pertencente a uma empresa deverá possuir coluna `tenant_id`.

Regras obrigatórias:

- `tenant_id` deverá ser chave estrangeira para `tenants`;
- `tenant_id` deverá ser obrigatório sempre que o dado pertencer necessariamente a uma empresa;
- `tenant_id` deverá participar dos índices das consultas do domínio;
- `tenant_id` deverá participar das constraints de unicidade quando o conceito for único apenas dentro da empresa;
- nenhuma consulta de domínio poderá ser executada sem filtro de tenant.

Entidades globais da plataforma, como `platform_branding` e `platform_settings`, não possuem tenant.

Entidades que possam ser globais ou específicas, como `rules` e `files`, deverão documentar explicitamente o significado da ausência de tenant.

## 3.5 Valores monetários com decimal exato

Valores monetários deverão utilizar tipo decimal exato do PostgreSQL, com precisão e escala explícitas.

É proibido armazenar valores financeiros em tipos de ponto flutuante binário, como `float`, `double precision` ou `real`.

Regras:

- precisão e escala deverão ser idênticas para todos os campos monetários do domínio financeiro;
- a escala deverá ser suficiente para representar centavos sem arredondamento implícito;
- a moeda deverá ser conhecida e consistente no contexto do registro;
- conversões para tipos imprecisos não deverão ocorrer em nenhuma camada de leitura ou agregação.

Esta regra materializa a decisão DATA-017 do documento 03.

## 3.6 Datas com semântica preservada

Datas financeiras de emissão, vencimento, previsão, recebimento e pagamento deverão permanecer colunas semanticamente distintas.

Regras:

- instantes deverão ser armazenados com fuso horário;
- datas de competência puramente civis deverão utilizar tipo de data quando não houver componente de hora relevante;
- nenhuma coluna deverá acumular significados diferentes conforme o estado do registro.

## 3.7 Timestamps padrão

Toda tabela de domínio deverá possuir `created_at`.

Toda tabela que possa ser alterada deverá possuir `updated_at`.

Entidades sincronizadas deverão possuir, adicionalmente:

- `external_created_at` quando disponível;
- `external_updated_at` quando disponível;
- `synced_at`, indicando a última sincronização bem-sucedida do registro.

Datas de origem externa não deverão sobrescrever os timestamps internos da plataforma.

## 3.8 Chaves estrangeiras obrigatórias

Todo relacionamento deverá possuir chave estrangeira real no banco.

Regras:

- integridade referencial não deverá depender exclusivamente da aplicação;
- o comportamento de exclusão deverá ser declarado explicitamente;
- exclusão em cascata somente será permitida quando o registro filho não possuir valor histórico ou de auditoria;
- registros de auditoria não deverão ser destruídos por cascata de operações administrativas.

## 3.9 Identificadores externos

Dados sincronizados deverão preservar `external_id`, sempre interpretado no contexto da integração de origem.

Regras:

- `external_id` nunca substitui o identificador interno;
- `external_id` deverá ser tratado como texto opaco;
- a unicidade deverá considerar a combinação de integração, tipo de recurso e identificador externo;
- não deverá existir premissa de que identificadores externos sejam numéricos, sequenciais ou estáveis entre fornecedores.

## 3.10 Migrations imutáveis após aplicadas

Uma migration já aplicada em qualquer ambiente compartilhado é considerada imutável.

É proibido:

- editar o conteúdo de uma migration existente;
- renomear uma migration existente;
- remover uma migration do histórico;
- reordenar migrations;
- alterar o schema de produção manualmente fora do fluxo de migrations.

Toda correção deverá ser realizada por meio de uma nova migration.

## 3.11 Schema como fonte única

O schema Prisma é a fonte única de definição do modelo físico.

Alterações estruturais deverão sempre gerar migration correspondente e versionada junto ao código.

O banco de produção jamais deverá ser modificado por comandos ad hoc.

## 3.12 Segredos protegidos

Credenciais de integração deverão ser armazenadas exclusivamente em `integration_credentials`, em formato protegido.

Regras:

- valores nunca deverão ser armazenados em texto puro;
- valores nunca deverão aparecer em logs;
- valores nunca deverão ser expostos pela API;
- senhas de usuário deverão ser armazenadas apenas como hash.

# 4. Padrões Aprovados

## 4.1 Organização do schema

O schema deverá ser organizado por domínio, em blocos claramente identificados e na mesma ordem lógica do documento 03:

1. núcleo da plataforma;
2. branding e arquivos;
3. integrações;
4. sincronização;
5. domínio financeiro normalizado;
6. dados analíticos;
7. Consultor Financeiro;
8. motor de regras;
9. relatórios;
10. notificações;
11. auditoria e suporte;
12. configurações.

## 4.2 Nomenclatura de objetos

| Objeto | Padrão | Exemplo |
|--------|--------|---------|
| Tabela | `snake_case` plural | `receivables` |
| Coluna | `snake_case` singular | `open_amount` |
| Chave estrangeira | `<entidade>_id` | `tenant_id` |
| Índice | `idx_<tabela>_<colunas>` | `idx_receivables_tenant_due_date` |
| Unicidade | `uq_<tabela>_<colunas>` | `uq_receivables_integration_external_id` |
| Modelo Prisma | `PascalCase` singular | `Receivable` |
| Campo Prisma | `camelCase` | `openAmount` |
| Enum Prisma | `PascalCase` | `ReceivableStatus` |

## 4.3 Estrutura mínima de uma entidade de domínio

```
id                  identificador interno
tenant_id           vínculo com a empresa
...                 campos do domínio
created_at
updated_at
```

Estrutura adicional para entidade sincronizada:

```
integration_id
external_id
external_created_at
external_updated_at
synced_at
```

## 4.4 Índices

Deverão existir índices para:

- `tenant_id` isolado ou como primeira coluna de índices compostos;
- colunas de data utilizadas em filtros de período, como `due_date`, `issue_date`, `transaction_date`;
- colunas de status frequentemente filtradas;
- chaves estrangeiras utilizadas em junções;
- combinações reais utilizadas pelas consultas da dashboard.

Diretrizes:

- índices compostos deverão respeitar a ordem de seletividade das consultas reais;
- índices deverão ser criados a partir de necessidade observada, não por suposição genérica;
- índices redundantes deverão ser evitados, pois penalizam escrita e sincronização.

## 4.5 Constraints de unicidade

Constraints obrigatórias, conforme seção 18 do documento 03:

- unicidade de e-mail de usuário conforme a regra de autenticação adotada;
- unicidade de `external_id` por integração e tipo de recurso;
- uma configuração de branding por tenant;
- uma configuração principal do Consultor por tenant;
- chave de deduplicação de regras conforme a janela definida.

Unicidade que dependa de contexto de empresa deverá sempre incluir `tenant_id`.

## 4.6 Enumerações

Estados normalizados do domínio, como status de contas a receber, tipos de sincronização e severidades, deverão utilizar enumeração controlada.

Regras:

- valores em inglês, coerentes com a nomenclatura do documento 03;
- estado desconhecido deverá ser representado explicitamente quando a fonte externa não permitir classificação confiável;
- estados externos deverão ser mapeados para o enum interno na camada de sincronização, nunca persistidos como recebidos.

## 4.7 Transações

Deverão ser executadas em transação:

- criação de entidades relacionadas que precisem existir em conjunto;
- persistência de um lote de sincronização que precise ser consistente;
- operações que atualizem simultaneamente dado de domínio e cursor de sincronização;
- alterações administrativas com registro obrigatório de auditoria.

Diretrizes:

- transações deverão ser curtas e delimitadas;
- chamadas de rede a sistemas externos não deverão ocorrer dentro de uma transação aberta;
- lotes grandes deverão ser divididos em blocos transacionais menores.

## 4.8 Idempotência da sincronização

A persistência de dados sincronizados deverá ser idempotente.

Padrão aprovado:

- identificação do registro por integração e identificador externo;
- inserção ou atualização condicional apoiada em constraint de unicidade;
- atualização de `synced_at` a cada sincronização bem-sucedida;
- nenhuma duplicação de registro após reexecução do mesmo lote.

## 4.9 Exclusão lógica

A exclusão lógica é o padrão para dados que possuam valor histórico ou de auditoria.

Padrões aprovados:

- coluna de status ou de data de desativação, como `deactivated_at`;
- consultas de domínio filtrando registros ativos por padrão;
- preservação de registros necessários para auditoria e rastreabilidade.

Diretrizes:

- exclusão lógica não deverá ser aplicada indiscriminadamente a todas as tabelas;
- tabelas de eventos e logs não necessitam exclusão lógica, apenas política de retenção;
- desativação de tenant não deverá destruir imediatamente seus dados financeiros.

## 4.10 Seeds

Seeds são permitidos exclusivamente para dados estruturais necessários ao funcionamento da plataforma.

Padrões aprovados:

- definições oficiais de métricas;
- regras globais do sistema;
- branding padrão da plataforma;
- usuário administrativo inicial em ambiente de desenvolvimento.

Regras:

- seeds deverão ser idempotentes;
- seeds não deverão criar dados financeiros fictícios;
- seeds de desenvolvimento deverão ser claramente separados de seeds estruturais;
- seeds jamais deverão ser executados automaticamente contra produção sem decisão explícita.

## 4.11 Paginação

Toda listagem potencialmente extensa deverá ser paginada no banco.

Padrões aprovados:

- paginação por cursor para listagens grandes, sequenciais ou com ordenação estável;
- paginação por deslocamento aceitável apenas para conjuntos pequenos e limitados;
- limite máximo de página definido e imposto pelo servidor;
- ordenação determinística, incluindo critério de desempate.

A forma exposta ao cliente é definida no documento 09.6.

## 4.12 Consultas de grande volume

Para as entidades de maior crescimento — `receivables`, `payables`, `financial_transactions`, `sync_runs`, `ai_messages`, `ai_runs`, `audit_logs`, `notifications`, `analytical_events` — aplicam-se as diretrizes:

- agregações deverão ser realizadas pelo banco, não em memória da aplicação;
- consultas deverão sempre restringir tenant e período;
- processamento pesado deverá ocorrer em background, conforme ADR-011;
- materialização de métricas por meio de `metric_snapshots` deverá ser considerada quando o custo de cálculo em tempo real for comprovadamente alto;
- políticas de retenção deverão ser definidas para tabelas de evento.

## 4.13 Evolução do schema

Padrões aprovados para alterações estruturais:

- adição de coluna opcional, seguida de preenchimento controlado, seguida de tornar obrigatória em migration posterior;
- criação de nova coluna e migração de dados antes de remover a antiga;
- remoção somente após o código deixar de utilizar o campo;
- alterações destrutivas registradas de forma explícita e revisadas antes da aplicação.

## 4.14 Versionamento de cálculo

Quando uma alteração de regra puder modificar resultados históricos, a plataforma deverá identificar a versão utilizada, por meio de `metric_definitions`, `calculation_version` ou metadados de snapshot, conforme seção 21 do documento 03.

# 5. Padrões Proibidos

É proibido:

1. armazenar valores monetários em ponto flutuante binário;
2. utilizar identificador externo como chave primária;
3. criar tabela de domínio financeiro sem `tenant_id` quando o dado pertencer a uma empresa;
4. executar consulta de domínio sem filtro de tenant;
5. reproduzir a estrutura da API do Conta Azul no schema interno;
6. criar tabelas separadas por ERP para conceitos financeiros equivalentes;
7. utilizar nomenclatura em português ou mista para entidades e colunas;
8. editar, renomear, remover ou reordenar migrations já aplicadas;
9. alterar o schema de produção manualmente;
10. relacionar entidades sem chave estrangeira real;
11. aplicar exclusão em cascata sobre dados de auditoria;
12. armazenar credenciais ou tokens em texto puro;
13. armazenar senha sem hash;
14. persistir status externos sem normalização;
15. retornar listagens ilimitadas sem paginação;
16. realizar agregações financeiras carregando grandes volumes em memória;
17. criar seeds que gerem dados financeiros fictícios;
18. executar seeds de desenvolvimento em produção;
19. abrir transações longas contendo chamadas externas;
20. utilizar `tenant_settings` ou `platform_settings` como armazenamento genérico sem contrato definido.

# 6. Exemplos Conceituais

## 6.1 Normalização, não cópia

Correto:

```
Conta Azul (formato externo)
        ↓ sincronização
Normalização para o domínio interno
        ↓
receivables / payables / financial_transactions
```

Incorreto:

```
Conta Azul (formato externo)
        ↓
conta_azul_contas_receber (espelho da API)
```

## 6.2 Entidade financeira sincronizada

```
receivables
  id
  tenant_id            → tenants.id
  integration_id       → integrations.id
  external_id
  customer_id          opcional
  category_id          opcional
  description
  issue_date
  due_date
  expected_date        opcional
  original_amount      decimal exato
  open_amount          decimal exato
  received_amount      decimal exato
  status               enum interno
  received_at          opcional
  external_created_at
  external_updated_at
  synced_at
  created_at
  updated_at
```

## 6.3 Índices e unicidade

```
uq_receivables_integration_external_id  (integration_id, external_id)
idx_receivables_tenant_due_date         (tenant_id, due_date)
idx_receivables_tenant_status           (tenant_id, status)
```

## 6.4 Valor monetário

Correto:

```
original_amount   decimal com precisão e escala explícitas
```

Incorreto:

```
original_amount   double precision
```

## 6.5 Isolamento em consulta

Correto:

```
buscar recebíveis
  onde tenant_id = tenant da sessão validada
  e due_date entre início e fim do período
```

Incorreto:

```
buscar recebíveis
  onde due_date entre início e fim do período
```

## 6.6 Correção de schema

Correto:

```
migration 20260812_add_expected_date
migration 20260814_fix_expected_date_nullability
```

Incorreto:

```
editar migration 20260812_add_expected_date já aplicada
```

## 6.7 Sincronização idempotente

```
para cada registro externo do lote:
  localizar por (integration_id, external_id)
  se existir → atualizar campos normalizados e synced_at
  se não existir → criar com identificador interno próprio
```

Reexecutar o mesmo lote não deverá produzir duplicidade.

# 7. Critérios de Revisão

Uma alteração de banco de dados somente poderá ser aprovada quando:

1. possuir migration versionada correspondente;
2. não modificar migration já aplicada;
3. utilizar nomenclatura conceitual em inglês compatível com o documento 03;
4. possuir `tenant_id` em toda entidade pertencente a uma empresa;
5. possuir chaves estrangeiras reais com comportamento de exclusão declarado;
6. utilizar decimal exato para todo valor monetário;
7. preservar a semântica distinta das datas financeiras;
8. possuir `created_at` e, quando aplicável, `updated_at` e campos de sincronização;
9. possuir índices compatíveis com as consultas reais previstas;
10. possuir constraints de unicidade adequadas, incluindo tenant quando necessário;
11. normalizar estados externos em enumerações internas;
12. não reproduzir a estrutura de nenhum ERP;
13. não expor nem armazenar segredos em texto puro;
14. tratar exclusão preservando auditoria;
15. suportar paginação nas listagens potencialmente grandes;
16. possuir seeds idempotentes, quando houver;
17. não introduzir consulta sem filtro de tenant;
18. estar coerente com as decisões consolidadas DATA-001 a DATA-018 do documento 03.

# 9. Diretriz Final

O banco de dados do Dashboard Economização é a memória oficial da plataforma.

Ele deverá permanecer exato nos valores, íntegro nos relacionamentos, isolado por empresa e independente de qualquer fornecedor externo.

Precisão financeira, isolamento multiempresa e histórico confiável de migrations não são preferências de implementação.

São requisitos inegociáveis do produto.
