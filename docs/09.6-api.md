# Dashboard Economização

# 09.6 — API

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define o padrão oficial do contrato da API interna do Dashboard Economização.

A API interna é implementada em Node.js com TypeScript utilizando Fastify, executada como processo independente do frontend, conforme ADR-006 e ADR-032 do documento 08.

O objetivo deste padrão é garantir que a API:

- possua contrato previsível, consistente e estável entre módulos;
- seja a autoridade sobre regras de negócio, autorização e cálculos financeiros;
- imponha isolamento multiempresa em todas as operações;
- valide integralmente toda entrada recebida;
- retorne erros em formato uniforme e interpretável pelo frontend;
- nunca exponha segredos, tokens externos ou detalhes internos de infraestrutura;
- permaneça a única superfície de acesso a dados utilizada pelo frontend.

Este documento define o contrato.

A organização interna de camadas, serviços e repositórios pertence ao documento 09.3.

---

# 2. Escopo

Este documento se aplica a toda rota exposta pela API interna.

Estão dentro do escopo:

- estilo de contrato e uso de REST;
- versionamento;
- métodos HTTP;
- códigos de status;
- parâmetros de rota;
- query strings;
- filtros;
- ordenação;
- paginação;
- formato de resposta;
- formato de erro;
- validação;
- autenticação;
- contexto de tenant;
- idempotência;
- limites e proteção de superfície.

Está fora do escopo deste documento:

- estrutura interna de módulos e camadas do backend, definida no documento 09.3;
- mecanismos criptográficos e política de sessão, definidos no documento 09.7;
- formato de logs, definido no documento 09.11;
- integração com Conta Azul, definida no documento 04.

# 3. Regras Obrigatórias

## 3.1 A API é a autoridade

A API interna é a única autoridade sobre:

- autenticação e autorização;
- resolução do tenant efetivo;
- cálculos financeiros oficiais;
- normalização de dados sincronizados;
- validação de entrada;
- regras de negócio.

Nenhuma decisão crítica poderá ser delegada ao cliente.

## 3.2 tenantId do cliente nunca é confiável

Esta é a regra mais crítica deste documento.

O contexto de tenant deverá ser derivado da sessão autenticada no servidor.

Nas rotas do painel do cliente, o identificador de empresa não é aceito no caminho, na query nem no corpo da requisição. Caso ele apareça, deverá ser ignorado, e o tenant efetivo permanecerá o derivado da sessão, conforme o documento 09.9.

Nas rotas administrativas, o identificador de empresa pode aparecer no caminho, e nesse caso deverá ser tratado como solicitação, nunca como autorização, exigindo validação completa de autorização antes de qualquer uso.

O servidor deverá obrigatoriamente:

1. identificar o usuário autenticado;
2. determinar os tenants aos quais esse usuário tem acesso legítimo;
3. verificar se o tenant solicitado pertence a esse conjunto;
4. rejeitar a requisição quando não pertencer;
5. aplicar o tenant validado em todas as consultas subsequentes.

Nunca deverá existir consulta de domínio filtrada por um `tenantId` recebido do cliente sem essa validação.

Quando o acesso ocorrer em modo suporte, o tenant efetivo deverá derivar da sessão de suporte registrada, e a operação deverá ser auditada com a identidade real do operador.

## 3.3 Nenhum token externo exposto

A API jamais deverá retornar, em qualquer resposta:

- access token ou refresh token do Conta Azul;
- credenciais de integração, mesmo parcialmente mascaradas;
- chaves de provedores de IA;
- segredos de sessão, banco, Redis ou storage.

Endpoints de integração deverão expor apenas informações operacionais, como status da conexão, empresa externa identificada, data da última sincronização bem-sucedida e resumo do último erro.

## 3.4 Validação obrigatória de toda entrada

Toda entrada deverá ser validada no servidor antes de qualquer uso: corpo, parâmetros de rota, query string e cabeçalhos relevantes.

Regras:

- campos desconhecidos não deverão ser aceitos silenciosamente em operações de escrita;
- tipos deverão ser validados e convertidos explicitamente;
- limites numéricos, tamanhos de texto e intervalos de data deverão ser verificados;
- valores validados deverão ser tipados para uso interno seguro.

Validação existente no frontend nunca substitui validação no servidor.

## 3.5 Autenticação obrigatória por padrão

Toda rota é autenticada por padrão.

Rotas públicas constituem exceção explícita e limitada, restrita a login, recuperação de senha, redefinição de senha, verificação de saúde e retorno de OAuth do backend.

Toda rota autenticada deverá adicionalmente verificar autorização, considerando perfil do usuário e tenant efetivo.

## 3.6 Formato de erro consistente

Toda resposta de erro deverá utilizar o mesmo formato conceitual, definido na seção 4.9.

Não deverão existir formatos distintos por módulo.

## 3.7 Nenhum vazamento de detalhe interno

Respostas de erro não deverão conter:

- stack trace;
- mensagem bruta de exceção de banco de dados;
- nome de tabela, coluna ou constraint;
- caminho de arquivo;
- consulta SQL;
- segredo, mesmo parcial.

O detalhe técnico pertence ao log estruturado, conforme documento 09.11.

## 3.8 Semântica correta dos métodos e status

Métodos HTTP e códigos de status deverão respeitar sua semântica padrão.

Não é permitido responder erro com status 200, tampouco utilizar `POST` para operações que representam leitura simples.

## 3.9 Paginação obrigatória em listagens

Toda listagem potencialmente extensa deverá ser paginada, com limite máximo imposto pelo servidor.

Nenhum endpoint deverá retornar coleção ilimitada de dados financeiros.

## 3.10 Valores monetários sem perda de precisão

Valores monetários deverão trafegar em formato que preserve exatidão decimal.

É proibido serializar valores financeiros de modo que dependam de aritmética de ponto flutuante binário para reconstrução do valor correto.

O formato adotado deverá ser único e consistente em toda a API.

## 3.11 Determinismo

Dado o mesmo tenant, o mesmo período e os mesmos filtros, um endpoint analítico deverá retornar o mesmo resultado enquanto os dados de origem não mudarem.

# 4. Padrões Aprovados

## 4.1 Estilo do contrato

A API adota estilo REST orientado a recursos sempre que o conceito for naturalmente um recurso.

Quando a operação representar um comando de domínio que não corresponde a um recurso, é permitido expor uma ação explícita sob o recurso relacionado.

Exemplos conceituais:

```
GET    /receivables
POST   /integrations/{integrationId}/sync
POST   /auth/login
```

Nas rotas administrativas, o identificador de empresa é aceito no caminho, sempre com validação completa de autorização:

```
PATCH  /admin/tenants/{tenantId}/branding
```

A ação deverá permanecer subordinada ao recurso e possuir nome verbal claro.

## 4.2 Nomenclatura de rotas

- caminhos em minúsculas;
- substantivos no plural para coleções;
- separação por hífen quando houver mais de uma palavra;
- nomenclatura conceitual em inglês, coerente com os documentos 03 e 09.5;
- sem extensão de arquivo e sem verbos em rotas de leitura.

## 4.3 Versionamento

O versionamento por prefixo de caminho deverá ser adotado quando houver necessidade real de coexistência de contratos.

Diretrizes:

- durante o MVP, com frontend e backend evoluindo juntos, o versionamento poderá ser omitido;
- quando adotado, o prefixo deverá ser aplicado de forma uniforme a toda a API;
- alterações compatíveis, como adição de campo opcional, não exigem nova versão;
- alterações incompatíveis exigem nova versão ou período documentado de convivência;
- remoção de campo deverá ser precedida de depreciação registrada.

## 4.4 Métodos HTTP

| Método | Uso |
|--------|-----|
| `GET` | Leitura, sem efeito colateral |
| `POST` | Criação ou execução de comando de domínio |
| `PUT` | Substituição completa de recurso |
| `PATCH` | Atualização parcial de recurso |
| `DELETE` | Remoção ou desativação, conforme política da entidade |

`GET` deverá ser sempre seguro e idempotente.

## 4.5 Códigos de status

| Código | Uso |
|--------|-----|
| 200 | Sucesso com corpo |
| 201 | Recurso criado |
| 202 | Processamento assíncrono aceito |
| 204 | Sucesso sem corpo |
| 400 | Requisição malformada |
| 401 | Ausência de autenticação válida |
| 403 | Autenticado, porém sem permissão sobre o recurso ou tenant |
| 404 | Recurso inexistente no contexto do tenant efetivo |
| 409 | Conflito de estado |
| 422 | Entrada sintaticamente válida, porém semanticamente inválida |
| 429 | Excesso de requisições |
| 500 | Falha inesperada do servidor |
| 503 | Dependência indisponível |

Diretriz de segurança: quando um recurso pertencer a outro tenant, a resposta preferencial é 404, evitando confirmar a existência do recurso a quem não deveria conhecê-lo. O uso de 403 fica reservado a situações em que o usuário legitimamente enxerga o recurso, mas não possui permissão para a operação.

## 4.6 Parâmetros de rota

Parâmetros de rota deverão identificar recursos, jamais transportar filtros.

Todo parâmetro deverá ser validado quanto ao formato e resolvido dentro do tenant efetivo.

## 4.7 Query string

A query string deverá concentrar filtros, período, ordenação e paginação.

Convenções aprovadas:

```
?startDate=2026-08-01
&endDate=2026-08-31
&status=overdue
&customerId=...
&sort=-dueDate
&limit=50
&cursor=...
```

Diretrizes:

- nomes em `camelCase`, coerentes com o documento 09.2;
- múltiplos valores para o mesmo filtro representados de forma consistente em toda a API;
- parâmetros desconhecidos deverão ser ignorados ou rejeitados, de acordo com política única aplicada uniformemente;
- período deverá ser sempre validado quanto à ordem e à amplitude máxima permitida.

## 4.8 Ordenação e paginação

Ordenação:

- parâmetro único `sort`;
- prefixo `-` indica ordem descendente;
- somente campos explicitamente permitidos por endpoint;
- ordenação sempre determinística, com critério de desempate estável.

Paginação:

- paginação por cursor é o padrão para listagens grandes;
- paginação por deslocamento é aceitável apenas para conjuntos pequenos e limitados;
- `limit` possui valor padrão e máximo definidos pelo servidor;
- metadados de paginação acompanham a resposta da coleção.

Formato aprovado para coleções:

```
{
  "data": [ ... ],
  "pagination": {
    "limit": 50,
    "nextCursor": "...",
    "hasMore": true
  }
}
```

## 4.9 Formato de erro

Formato conceitual único para toda a API:

```
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Período informado é inválido.",
    "details": [
      { "field": "endDate", "issue": "must_be_after_start_date" }
    ],
    "requestId": "..."
  }
}
```

Regras:

- `code` é estável, em maiúsculas, e destinado ao consumo programático;
- `message` é destinada a exibição ao usuário, redigida em português e livre de detalhe técnico;
- `details` é opcional e utilizada principalmente em erros de validação;
- `requestId` permite correlacionar a resposta com o log estruturado;
- o código HTTP deverá ser coerente com o `code` retornado.

Códigos iniciais aprovados:

`VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `INTEGRATION_UNAVAILABLE`, `SYNC_IN_PROGRESS`, `INTERNAL_ERROR`.

Novos códigos deverão ser adicionados apenas quando representarem situação realmente distinta para o cliente.

## 4.10 Formato de resposta de sucesso

Não é obrigatório envelopar toda resposta bem-sucedida.

Padrão aprovado:

- coleções retornam objeto com `data` e `pagination`, pois a paginação exige metadados;
- recurso único retorna diretamente o objeto do recurso;
- operações sem retorno relevante respondem 204 sem corpo;
- operações assíncronas respondem 202 com identificador do processamento e status inicial.

Envelope genérico do tipo `{ "success": true, "data": ... }` não deverá ser adotado sem benefício claro, por adicionar profundidade sem informação útil.

A escolha deverá ser consistente: recursos equivalentes respondem no mesmo formato em toda a API.

## 4.11 Convenções de payload

- campos em `camelCase`;
- datas e instantes em formato ISO 8601;
- instantes com fuso horário explícito;
- enumerações em valores estáveis, em inglês, coerentes com o documento 09.5;
- ausência de valor representada como `null` explícito quando o campo fizer parte do contrato;
- nenhum campo interno de infraestrutura exposto.

## 4.12 Autenticação e contexto

A autenticação deverá ser verificada antes de qualquer lógica de domínio.

O contexto derivado da requisição deverá conter, no mínimo:

- usuário autenticado;
- perfil ou tipo de usuário;
- tenant efetivo já validado;
- indicação de modo suporte, quando aplicável;
- identificador de correlação da requisição.

Esse contexto deverá ser propagado às camadas internas em vez de reconstruído em cada serviço.

## 4.13 Autorização

A autorização deverá ser avaliada em duas dimensões:

1. o usuário pode executar esta operação, considerando seu perfil;
2. o usuário pode executá-la sobre este tenant e sobre este recurso.

Ambas as verificações são obrigatórias.

Verificar apenas o perfil, sem verificar o vínculo com o recurso, é falha de segurança.

## 4.14 Idempotência

Deverão ser naturalmente idempotentes: `GET`, `PUT`, `DELETE`.

Para operações `POST` sensíveis a repetição, deverá ser adotada estratégia de idempotência quando houver risco real de duplicidade, tais como:

- disparo manual de sincronização;
- solicitação de geração de relatório;
- operações administrativas críticas.

Padrões aprovados:

- chave de idempotência informada pelo cliente e associada ao tenant;
- reaproveitamento do resultado da primeira execução dentro da janela definida;
- retorno de conflito quando já existir execução equivalente em andamento;
- deduplicação natural apoiada em estado do domínio, quando suficiente.

## 4.15 Operações assíncronas

Operações longas deverão ser delegadas às filas, conforme ADR-010 e ADR-011.

Padrão aprovado:

- resposta 202 com identificador do processamento;
- endpoint de consulta de status;
- estados explícitos de processamento, sucesso e falha;
- ausência de bloqueio da requisição HTTP aguardando conclusão.

## 4.16 Limites e proteção

Padrões aprovados:

- limite de tamanho de corpo da requisição;
- limite de requisições por sessão e por origem em rotas sensíveis;
- limite máximo de intervalo de período em consultas analíticas;
- limite máximo de itens por página;
- tempo limite para dependências externas.

## 4.17 Saúde e diagnóstico

A API deverá expor endpoint de verificação de saúde.

Ele não deverá expor versões detalhadas de componentes, variáveis de ambiente, informações de infraestrutura nem dados de tenants.

# 5. Padrões Proibidos

É proibido:

1. utilizar `tenantId` recebido do cliente sem validar o vínculo com a sessão autenticada;
2. retornar tokens ou credenciais do Conta Azul em qualquer resposta;
3. expor chaves de IA, segredos de sessão ou credenciais de infraestrutura;
4. confiar em validação realizada no frontend;
5. responder erro com status 200;
6. utilizar formatos de erro distintos entre módulos;
7. retornar stack trace, SQL, nome de tabela ou caminho de arquivo ao cliente;
8. expor rota autenticada sem verificação de autorização sobre o recurso;
9. retornar listagem sem paginação;
10. permitir intervalo de período ilimitado em consultas analíticas;
11. utilizar `GET` com efeito colateral;
12. utilizar `POST` para leitura simples apenas para acomodar parâmetros extensos;
13. serializar valor monetário com perda de precisão;
14. criar endpoint que devolva dados de mais de um tenant sem que a operação seja explicitamente administrativa e devidamente autorizada;
15. duplicar regra de negócio entre rotas em vez de concentrá-la em serviço;
16. executar processamento pesado dentro do ciclo da requisição;
17. adicionar envelope genérico de sucesso sem benefício demonstrado;
18. alterar contrato existente de forma incompatível sem versionamento ou depreciação registrada;
19. expor endpoint de proxy que repasse chamadas diretamente ao Conta Azul;
20. registrar em log corpo de requisição contendo credenciais ou dados sensíveis.

# 6. Exemplos Conceituais

## 6.1 Resolução correta de tenant

Correto:

```
requisição chega
  ↓
sessão autenticada identificada
  ↓
tenants permitidos ao usuário resolvidos no servidor
  ↓
tenant solicitado verificado contra essa lista
  ↓
consulta executada com o tenant validado
```

Incorreto:

```
requisição chega
  ↓
tenantId lido do parâmetro
  ↓
consulta executada diretamente
```

## 6.2 Listagem paginada

Requisição:

```
GET /receivables?startDate=2026-08-01&endDate=2026-08-31&status=overdue&sort=-dueDate&limit=50
```

Resposta:

```
{
  "data": [
    {
      "id": "...",
      "description": "...",
      "dueDate": "2026-08-12",
      "originalAmount": "1250.00",
      "openAmount": "1250.00",
      "status": "overdue",
      "customer": { "id": "...", "name": "..." }
    }
  ],
  "pagination": { "limit": 50, "nextCursor": "...", "hasMore": true }
}
```

```
GET /integrations/{integrationId}
```

```
{
  "id": "...",

  "status": "connected",
  "externalCompanyName": "...",
  "lastSuccessfulSyncAt": "2026-08-12T18:40:00-03:00",
```

## 6.4 Erro de validação

```
HTTP 422

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "A data final deve ser posterior à data inicial.",
    "details": [ { "field": "endDate", "issue": "must_be_after_start_date" } ],
```

```
HTTP 404

{
  "error": {
    "code": "NOT_FOUND",
    "message": "Registro não encontrado.",

  }
}
```

```

HTTP 202

{
  "reportId": "...",

```


## 6.7 Erro interno

Ao cliente:

```
HTTP 500

{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Não foi possível concluir a operação. Tente novamente.",
    "requestId": "..."
  }
}
```

No log estruturado permanece o detalhe técnico completo, correlacionado pelo mesmo `requestId`.

# 7. Critérios de Revisão

Um endpoint somente poderá ser aprovado quando:

1. derivar o tenant efetivo da sessão autenticada e validar qualquer identificador recebido;
2. verificar autenticação e autorização antes de qualquer lógica de domínio;
3. validar integralmente corpo, parâmetros e query string;
4. utilizar método HTTP e código de status semanticamente corretos;
5. utilizar o formato de erro único definido neste documento;
6. não vazar detalhe técnico interno em respostas;
7. não expor tokens, credenciais ou segredos;
8. paginar toda listagem potencialmente extensa e impor limite máximo;
9. permitir ordenação apenas em campos explicitamente autorizados;
10. limitar a amplitude de período em consultas analíticas;
11. preservar exatidão decimal em valores monetários;
12. delegar processamento pesado às filas e responder 202 quando aplicável;
13. adotar idempotência quando houver risco real de duplicidade;
14. manter consistência de formato com endpoints equivalentes já existentes;
15. concentrar regra de negócio em serviço, mantendo a rota fina;
16. registrar log estruturado correlacionado por identificador de requisição;
17. auditar operações administrativas e ações executadas em modo suporte;
18. permanecer compatível ou possuir estratégia explícita de versionamento e depreciação.

# 9. Diretriz Final

A API interna do Dashboard Economização é a fronteira de confiança da plataforma.

Tudo que vem do cliente é solicitação.

Tudo que sai do servidor é decisão.

Nenhum identificador de empresa recebido do frontend poderá substituir a verificação de acesso feita no servidor, e nenhuma credencial de fornecedor externo poderá atravessar essa fronteira.

Contrato previsível, isolamento verificado e erro consistente valem mais para este produto do que qualquer sofisticação adicional de formato.

# 10. GET /dashboard/overview (Fase 10A)

Status: CONCLUÍDA.

Rota autenticada (`requireAuthentication`). Sem prefixo `/api/v1`.

Tenant operacional: exclusivamente da sessão (USER → `auth.tenantId`) ou do Support Mode ativo. Query `tenantId` é rejeitada (400). ADMIN/SUPER_ADMIN sem Support Mode → 403.

Não há body. Header de sucesso: `Cache-Control: private, no-store`.

Resposta 200 (valores financeiros em string via `Decimal.toString()`; fórmulas em docs/11, não duplicadas aqui):

- `today`: `YYYY-MM-DD` (mesma data civil `America/Sao_Paulo` do snapshot analítico)
- `receivables` / `payables`: `open`, `overdue`, `upcoming`
- `delinquency`: `overdueUnpaid`, `openUnpaid`, `rate` (`string | null`)
- `integration`: `status` (`CONNECTED | DISCONNECTED | ERROR`), `lastSuccessfulSyncAt` (ISO-8601 ou null), `lastErrorCode` (código público ou null)

Ausência de Integration Conta Azul: `DISCONNECTED` + freshness null. Disconnect/ERROR não apagam KPIs persistidos. UI (10B/10C) não faz parte deste contrato.

# 11. GET /dashboard/upcoming e GET /dashboard/cash-flow-forecast (Fase 10C)

Status: IMPLEMENTADA / HOMOLOGADA VISUALMENTE (10C). E1 (`summary`) IMPLEMENTADA / AGUARDANDO HOMOLOGAÇÃO.

Mesma autenticação e tenant operacional de §10. Query `tenantId` rejeitada (400).
Header de sucesso: `Cache-Control: private, no-store`. Decimais em string.
Fórmulas: docs/11 (motor 9C). Sem bloco `integration` (freshness permanece em overview).

## GET /dashboard/upcoming?days=N

`days` obrigatório. Aceitos somente `7`, `15` e `30` (contrato de produto da Dashboard).
Ausente ou outro valor → 400. Sem default no backend. O motor analítico continua
sem default implícito (`nDays` informado pelo caller).

Resposta 200:

- `today`, `from`, `to`: `YYYY-MM-DD`
- `nDays`: 7 | 15 | 30
