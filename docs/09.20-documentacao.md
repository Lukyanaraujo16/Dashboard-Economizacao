# Dashboard Economização

# 09.20 — Documentação

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define o padrão oficial de documentação do Dashboard Economização: o que é documentado, onde, por quem, em que momento e sob quais garantias de veracidade.

O projeto adota, desde a ADR-031 e a ADR-037, o princípio de **documentação antes da implementação**. Isso significa que a documentação deste projeto não descreve o que o código faz — ela **determina** o que o código deve fazer. Um documento da série 00 a 09 não é um relato: é um contrato.

Essa escolha tem uma consequência direta e desconfortável: **documentação divergente do sistema é um defeito**, da mesma natureza de um cálculo financeiro errado. Um número errado leva o cliente a uma decisão errada; um contrato errado leva a implementação inteira a uma decisão errada, com custo multiplicado por todas as fases seguintes.

Este documento existe para impedir três falhas específicas, todas comuns e todas caras:

1. **implementar antes de decidir** — o comportamento é escolhido por quem digita o código e nunca é revisado;
2. **decidir sem registrar** — a decisão vive apenas no histórico de conversas e se perde;
3. **registrar e divergir** — o documento continua existindo, continua sendo lido e passou a mentir.

A terceira é a mais perigosa das três, porque é a única que produz confiança falsa.

---

# 2. Escopo

Este documento regula:

- a hierarquia de fontes de verdade do projeto;
- a responsabilidade de cada documento e de cada série;
- quando um documento deve ser criado, atualizado ou marcado como superado;
- o fluxo obrigatório de mudança de contrato;
- o registro de decisões técnicas por meio de ADRs;
- o conteúdo e os limites do `README.md`;
- a documentação de API e de contratos de integração;
- o uso de comentários no código;
- a documentação obrigatória de jobs, filas, migrations e integrações externas;
- a linguagem, o formato e a nomenclatura dos documentos;
- os critérios de revisão de documentação.

Este documento **não** regula:

- o conteúdo funcional do produto — pertence a `docs/00-visao-do-produto.md` e `docs/01-prd.md`;
- os padrões de código em si — pertencem aos demais capítulos da série 09;
- documentação voltada ao usuário final do produto — não faz parte do MVP e será definida quando existir;
- documentação operacional de infraestrutura — pertence à série 10.

# 3. Regras Obrigatórias

## 3.1 Hierarquia oficial de fontes de verdade

O projeto possui uma hierarquia explícita. Quando dois documentos divergem, prevalece o de maior autoridade sobre o assunto em questão.

| Camada | Documentos | Autoridade |
|---|---|---|
| Produto | `00-visao-do-produto.md`, `01-prd.md` | O que o produto é e quais requisitos existem |
| Arquitetura e contratos | `02-arquitetura.md`, `03-modelagem-banco.md`, `04-api-conta-azul.md`, `05-ui-ux.md` | Como o sistema é estruturado e quais são os contratos |
| Planejamento | `06-roadmap.md` | O que é implementado em qual fase |
| Execução | `07-prompts-cursor.md` | Como uma tarefa é executada e autorizada |
| Decisão técnica | `08-decisoes-tecnicas.md` | Qual tecnologia e qual abordagem foram escolhidas, e por quê |
| Padrões de desenvolvimento | `09-padroes-de-codigo.md` e série `09.x` | Como o código deve ser escrito |
| Infraestrutura | Série `10.x` | Como o sistema é operado |

Regras de precedência:

- documentos 00 a 08 definem **o comportamento esperado do produto**;
- documentos 09.x definem **como implementar esse comportamento**;
- um documento 09.x nunca altera requisito funcional;
- em conflito entre um documento e o código existente, prevalece o documento — e o código é corrigido ou o documento é formalmente alterado, nunca ignorado;
- em conflito entre um documento e uma sugestão automática de ferramenta, exemplo da internet ou preferência pessoal, prevalece o documento, conforme `docs/09-padroes-de-codigo.md` §3.

## 3.2 O código nunca é a fonte de verdade do comportamento

O que o sistema **faz hoje** não é o que ele **deve fazer**.

Quando o código diverge do documento, existem exatamente duas conclusões possíveis, e nenhuma outra:

- o código está errado e será corrigido; **ou**
- a decisão mudou, o documento será formalmente atualizado e o código será ajustado ao novo contrato.

Nunca é aceitável concluir que "o documento está desatualizado, então vale o código". Essa conclusão, repetida algumas vezes, transforma toda a documentação em ficção — e o projeto passa a não ter contrato nenhum.

## 3.3 Toda mudança de comportamento segue o fluxo de contrato

Esta é a regra central deste documento.

```
mudança de comportamento
        ↓
atualizar o contrato (documento)
        ↓
implementar conforme o contrato
        ↓
validar contra o contrato
```

Nenhuma etapa é pulada e nenhuma é reordenada.

Aplica-se sempre que a mudança afetar:

- um requisito funcional ou uma regra de negócio;
- um contrato de API — rota, entrada, saída, código de status, erro, paginação;
- o modelo de dados — entidade, campo, relacionamento, restrição, índice com efeito semântico;
- uma regra de isolamento entre empresas ou de autorização;
- a fórmula de um indicador financeiro;
- o comportamento de um job, de uma fila ou de uma sincronização;
- a integração com a Conta Azul;
- o comportamento da IA — escopo de contexto, limites, uso do resultado;
- uma escolha tecnológica estrutural.

Fora do fluxo ficam apenas mudanças que **comprovadamente** não alteram comportamento: refatoração interna conforme `docs/09.22-refatoracao.md`, formatação, correção de erro de digitação, ajuste de log sem dado novo.

Na dúvida sobre se algo é mudança de comportamento, trata-se como mudança de comportamento.

## 3.4 Implementação não altera documentação silenciosamente

Durante uma implementação, é proibido alterar documento de contrato sem autorização, conforme `docs/07-prompts-cursor.md` §55.

Quando a implementação revela que o contrato está errado, incompleto ou impossível, o procedimento obrigatório é:

1. interromper **apenas** a parte conflitante do trabalho;
2. identificar o documento afetado e a seção específica;
3. explicar o conflito de forma concreta — o que o documento diz, o que a realidade impõe, por que são incompatíveis;
4. registrar a pendência no relatório;
5. aguardar a atualização formal do documento;
6. só então retomar a implementação.

Não é aceitável escolher sozinho qual comportamento prevalece, conforme `docs/07-prompts-cursor.md` §4.

O formato de registro é o de bloqueio previsto em `docs/07-prompts-cursor.md` §45.

## 3.5 Decisão técnica relevante vira ADR

Nenhuma decisão arquitetural relevante permanece apenas no histórico de conversas, conforme `docs/08-decisoes-tecnicas.md` §1.

Exige ADR:

- escolha ou substituição de framework, biblioteca estrutural ou serviço externo;
- mudança na estrutura do repositório ou na estratégia de monorepositório;
- mudança na divisão de processos — API, worker, scheduler;
- escolha de estratégia de autenticação, sessão ou autorização;
- escolha de provedor ou modelo de IA e política de custo;
- escolha de estratégia de storage, backup ou retenção;
- decisão de observabilidade;
- qualquer decisão que seja cara de reverter depois de implementada.

A ADR contém, quando aplicável: Status, Contexto, Decisão, Alternativas avaliadas, Escolha, Motivos e Consequências positivas e negativas.

Uma ADR aprovada nunca é alterada silenciosamente. Quando substituída, permanece historicamente identificável como substituída, depreciada ou cancelada, e a nova ADR explica a mudança.

Os itens listados em `docs/08-decisoes-tecnicas.md` §3 como pendentes devem receber ADR **antes** da fase que depende deles — nunca durante a implementação, e jamais por escolha implícita de quem estiver codificando.

## 3.6 Documento com divergência conhecida não permanece silencioso

É proibido saber que um documento diverge do sistema e não registrar isso.

Ao identificar divergência, é obrigatório, no mínimo:

- registrar a divergência no relatório da tarefa, com documento, seção e descrição concreta;
- não implementar nada que dependa da parte divergente sem decisão;
- não corrigir o documento por conta própria, salvo autorização.

Se a divergência não puder ser resolvida imediatamente, o documento afetado recebe marcação explícita na seção correspondente:

```
> **Divergência conhecida (2026-08-12):** esta seção descreve X;
> a implementação atual em `backend/...` faz Y.
> Decisão pendente. Não implementar nada novo com base nesta seção.
```

Um leitor que encontra essa marcação sabe que está diante de terreno instável. Um leitor que encontra um documento aparentemente íntegro e silenciosamente falso não sabe de nada.

## 3.7 O README é ponto de entrada, não duplicata

O `README.md` da raiz é a porta de entrada do repositório e nada além disso.

Deve conter:

- o que é o Dashboard Economização, em poucas linhas;
- pré-requisitos reais e verificáveis — versão de Node conforme `engines`, pnpm conforme `packageManager`, Docker;
- como subir o ambiente de desenvolvimento;
- os comandos oficiais do repositório: `lint`, `typecheck`, `test`, `build`, `format`, `format:check`;
- a estrutura de primeiro nível, em uma frase por diretório;
- como configurar variáveis de ambiente a partir de `.env.example`;
- um índice apontando para `docs/`.

Não deve conter:

- requisitos funcionais;
- regras de negócio;
- contratos de API;
- decisões arquiteturais;
- explicação de modelagem de dados;
- qualquer conteúdo que já exista em `docs/`, reescrito de outra forma.

O motivo é simples: conteúdo duplicado diverge. Sempre. A única defesa confiável contra divergência é **não duplicar**, e sim referenciar.

O README também nunca contém segredo, credencial, URL de produção com token, IP de servidor real ou senha de exemplo que seja uma senha real.

## 3.8 Contrato de API é documentado antes de existir

Nenhuma rota é implementada sem que seu contrato esteja definido em `docs/09.6-api.md` ou no documento de contrato aplicável.

O contrato define, no mínimo:

- método, caminho e propósito;
- autenticação e perfil exigidos;
- escopo por empresa e como o tenant efetivo é resolvido;
- entrada, com tipos, obrigatoriedade e validações;
- saída de sucesso, com formato e códigos de status;
- erros possíveis, com códigos e semântica, conforme `docs/09.10-tratamento-de-erros.md`;
- paginação e ordenação, quando houver coleção;
- efeitos colaterais — escrita, job disparado, auditoria gerada.

Mudança em contrato existente segue integralmente o fluxo de §3.3. Alteração incompatível exige registro explícito do impacto sobre o frontend e sobre qualquer consumidor.

## 3.9 Integração externa é documentada a partir da fonte, nunca de suposição

Para a Conta Azul, vale integralmente `docs/04-api-conta-azul.md` e a proibição de `docs/07-prompts-cursor.md` §23: é proibido presumir endpoint, campo, limite, comportamento de paginação ou existência de webhook.

Quando um comportamento externo for descoberto durante a implementação e não estiver documentado, ele é:

1. registrado como descoberta, com evidência concreta — resposta observada, código de status, formato real;
2. levado à atualização formal de `docs/04-api-conta-azul.md`;
3. só então usado como base de implementação.

Comportamento externo observado uma única vez e não documentado não é conhecimento do projeto: é lembrança de uma pessoa.

## 3.10 Comentário no código explica o porquê, nunca o quê

O código já diz o que faz. Um comentário que repete isso envelhece, diverge e passa a mentir sem que nenhum teste falhe.

Comentário é obrigatório quando existe uma **razão não óbvia** que o código não pode expressar:

- uma restrição imposta por sistema externo — limite da Conta Azul, formato inesperado, comportamento não documentado do fornecedor;
- uma decisão deliberada que parece errada à primeira vista, com o motivo;
- uma regra de negócio cuja fórmula não é autoevidente, com referência ao requisito;
- uma armadilha conhecida — precisão monetária, fuso horário, ordenação instável, condição de corrida;
- uma referência a ADR ou requisito que explica a escolha;
- uma limitação temporária consciente, com o que a resolve.

Comentário é proibido quando apenas narra o código, quando explica sintaxe da linguagem, quando descreve o óbvio ou quando guarda código morto.

Comentário nunca contém segredo, token, credencial, dado real de cliente, caminho absoluto de máquina pessoal ou nome próprio associado a culpa por um defeito.

## 3.11 A documentação é escrita em português do Brasil

Todo documento do projeto é escrito em português do Brasil, com terminologia consistente.

Consistência obrigatória de vocabulário:

- **empresa** e **tenant** referem-se ao mesmo conceito; o documento é explícito sobre qual termo usa em cada contexto e não alterna sem motivo;
- **sincronização** refere-se ao processo de importação da Conta Azul;
- **job**, **fila** e **worker** seguem o vocabulário de `docs/09.14-filas.md` e `docs/09.15-jobs.md`;
- **indicador** refere-se a valor calculado exibido ao usuário;
- **insight** refere-se ao conteúdo interpretativo gerado com apoio de IA.

Nomes de tecnologia, comandos, identificadores de código e caminhos de arquivo permanecem em sua forma original.

## 3.12 Todo documento da série 09 segue a mesma estrutura

Todo capítulo da série 09 possui o cabeçalho oficial e as nove seções canônicas: Objetivo, Escopo, Regras Obrigatórias, Padrões Aprovados, Padrões Proibidos, Exemplos Conceituais, Critérios de Revisão, Relação com Outros Documentos e Diretriz Final.

Nomenclatura de arquivo: `NN.N-assunto-em-kebab-case.md`, dentro de `docs/`.

Um número reservado no índice de `docs/09-padroes-de-codigo.md` só é ocupado quando o documento correspondente for efetivamente criado, e o índice é atualizado na mesma ocasião.

# 4. Padrões Aprovados

| Documento | Responsabilidade exclusiva |
|---|---|
| `00-visao-do-produto.md` | Por que o produto existe, para quem, qual problema resolve |
| `01-prd.md` | Requisitos formais, identificados e rastreáveis |
| `02-arquitetura.md` | Componentes, responsabilidades e fluxos entre eles |
| `03-modelagem-banco.md` | Entidades, relacionamentos e restrições de dados |

Cada assunto tem **um** dono. Quando um conteúdo cabe em dois documentos, ele mora no mais específico e o outro apenas referencia.

## 4.2 Fluxo aprovado de mudança de contrato

Exemplo concreto — inclusão de um filtro por status no relatório de recebíveis:

```
1. Identificar o documento dono do contrato:
   docs/09.6-api.md (contrato da rota)
   docs/01-prd.md   (o requisito, se for comportamento novo de produto)

2. Atualizar o contrato:
   - novo parâmetro de consulta, tipo e valores aceitos;
   - comportamento na ausência do parâmetro;
   - erro para valor inválido;
   - efeito sobre paginação e ordenação;
   - efeito sobre o escopo por empresa (nenhum: o escopo permanece na sessão).

3. Commit de documentação, separado (ver docs/09.19-git.md).

4. Implementar exatamente o contrato atualizado.

5. Validar contra o contrato:
   - teste do valor válido;
   - teste do valor inválido;
   - teste da ausência do parâmetro;
   - teste de isolamento entre empresas mantido.
```

O passo 5 verifica o documento, não a intenção de quem implementou. É isso que torna o contrato executável.

## 4.3 Estrutura aprovada de ADR

```
# ADR-0NN — <título curto>

## Status
Aprovada | Parcialmente aprovada | Pendente | Substituída | Depreciada | Cancelada

## Contexto
O problema real, as restrições e o que motivou a decisão agora.

## Decisão
Uma frase inequívoca do que foi decidido.

## Alternativas avaliadas
Cada alternativa com vantagens e desvantagens concretas.

## Escolha
A alternativa escolhida.

## Motivos
Por que ela, e não as outras.

## Consequências
Positivas e negativas. As negativas são obrigatórias:
uma ADR sem consequência negativa quase sempre é uma ADR incompleta.
```

Uma ADR é escrita **antes** de a decisão ser implementada, não como justificativa posterior do que já foi feito.

## 4.5 Documentação obrigatória por tipo de artefato

**Job** — documentado em `docs/09.15-jobs.md` com: gatilho, payload, escopo de empresa, estratégia de idempotência, política de retentativa, classificação de erros, efeitos observáveis e o que acontece em falha final.

**Fila** — documentada em `docs/09.14-filas.md` com: propósito, produtor, consumidor, concorrência, prioridade e política de retentativa.

**Migration** — a intenção é documentada quando não for evidente pelo nome: o motivo, o efeito sobre dados existentes, se é destrutiva e como reverter.

**Cálculo financeiro** — a fórmula, as exclusões, o tratamento de casos de borda e a referência ao requisito, conforme `docs/09.17-testes.md` §3.5.

**Uso de IA** — o escopo do contexto enviado, os limites e o que a IA **não** decide, conforme `docs/09.24-convencoes-ia.md`.

## 4.6 Padrão aprovado de comentário

Aprovado — restrição externa:

```ts
// A Conta Azul retorna a data de vencimento sem fuso. Tratamos como
// America/Sao_Paulo porque é o fuso da conta do cliente; sem isso,
// títulos vencendo no dia 1º caem no mês anterior.
```

Aprovado — decisão deliberada que parece errada:

```ts
// Consulta sem índice de propósito: o volume por empresa é limitado
// pelo período do relatório e o índice adicional degradaria a escrita
// da sincronização, que é o caminho quente. Ver docs/09.18-performance.md.
```

Aprovado — armadilha conhecida:

```ts
// Comparação em centavos inteiros. Ponto flutuante acumula erro
// e o total do relatório passa a divergir do somatório exibido.
```

Aprovado — limitação temporária consciente:

```ts
// A paginação da Conta Azul não expõe total de registros.
// Percorremos até página vazia. Reavaliar se o fornecedor
// publicar o total — ver docs/04-api-conta-azul.md.
```

Reprovado:

```ts
// incrementa o contador
contador++;

// função que busca os títulos
async function buscarTitulos() { ... }

// pega o tenant
const tenant = sessao.tenant;

// TODO: melhorar isso depois
```

O último é reprovado por ser um comentário que não informa nada verificável: não diz o que está errado, por que importa, nem o que resolveria.

## 4.7 Anotações de pendência

Quando uma pendência precisar ficar registrada no código, o formato aprovado informa **o quê**, **por quê** e **o que a destrava**:

```ts
// PENDENTE: aplicar limite de taxa por empresa quando a política de
// custo da IA for definida (ADR-028 está parcialmente aprovada).
// Hoje o limite é global, o que permite que uma empresa consuma a cota.
```

Pendência com impacto real de produto ou de segurança não fica apenas no código: é levada ao relatório da tarefa e, quando aplicável, ao documento correspondente.

## 4.8 Referências entre documentos

Documentos referenciam uns aos outros por caminho relativo ao repositório e, quando útil, por seção:

```
conforme `docs/09.9-multiempresa.md` §4.2
```

É preferível uma referência precisa a uma cópia do conteúdo. Cópia diverge; referência não.

## 4.9 Formato

- Markdown;
- títulos hierárquicos coerentes;
- tabelas para conjuntos enumeráveis curtos, com a explicação no texto ao redor;
- blocos de código para exemplos, contratos e comandos;
- exemplos conceituais preferidos a código completo, quando a decisão for independente de biblioteca;
- ausência de linguagem promocional — "robusto", "moderno", "premium", "incrível" não descrevem nada verificável, conforme `docs/07-prompts-cursor.md` §49.

# 5. Padrões Proibidos

É proibido:

1. implementar mudança de comportamento sem atualizar antes o contrato correspondente;
2. alterar documento de contrato durante uma implementação sem autorização;
3. escolher sozinho qual comportamento prevalece quando código e documento divergem;
4. concluir que "o documento está desatualizado, então vale o código";
5. manter divergência conhecida entre documento e sistema sem registrá-la;
6. deixar decisão técnica relevante apenas no histórico de conversas;
7. alterar ADR aprovada silenciosamente, sem registrar substituição, depreciação ou cancelamento;
8. escrever ADR depois da implementação, como justificativa do que já foi feito;
9. implementar rota sem contrato previamente documentado;
10. presumir endpoint, campo, limite ou comportamento da Conta Azul e documentá-lo como fato;
11. duplicar em `README.md` conteúdo que pertence a `docs/`;
12. colocar requisito, regra de negócio ou decisão arquitetural no `README.md`;
13. incluir segredo, credencial, token, IP real ou URL com token em qualquer documento;
14. incluir dado real de cliente em exemplo de documentação;
15. escrever comentário que apenas narra o que a linha de código faz;
16. manter comentário desatualizado que descreve comportamento que não existe mais;
17. deixar código comentado no lugar de removê-lo — o histórico do Git já guarda o passado;
18. usar anotação de pendência vazia, sem motivo e sem critério de resolução;
19. documentar comportamento futuro como se já existisse;
20. criar documento novo para um assunto que já tem dono declarado;
21. criar capítulo da série 09 fora da estrutura de nove seções e do cabeçalho oficial;
22. ocupar número reservado do índice sem atualizar `docs/09-padroes-de-codigo.md`;
23. introduzir variável de ambiente sem registrá-la em `.env.example`;
24. usar linguagem promocional ou vaga em documento técnico;
25. alternar terminologia para o mesmo conceito dentro do mesmo documento.

O item 16 merece destaque: um comentário desatualizado é mais nocivo do que a ausência de comentário, porque é lido com confiança e nenhum teste o contradiz.

# 6. Exemplos Conceituais

## 6.1 Mudança de comportamento — fluxo correto

Situação: durante a Fase 4, percebe-se que o indicador de inadimplência deveria excluir títulos cancelados.

Correto:

```
1. Isso é mudança de regra de negócio → é mudança de contrato.
2. Interromper a implementação da parte afetada.
3. Registrar: docs/01-prd.md define inadimplência sem mencionar
   títulos cancelados; a base contém títulos cancelados vencidos.
4. Aguardar decisão e atualização formal do PRD.
5. Implementar conforme a nova redação.
6. Adicionar teste com título cancelado e vencido,
   verificando exclusão do cálculo.
```

Incorreto:

```
Excluir títulos cancelados no código "porque obviamente é isso
que se espera" e seguir para a próxima tarefa.
```

O comportamento até pode ser o correto. O problema é que ninguém decidiu, ninguém revisou e nada garante que o relatório, o dashboard e o insight da IA passarão a aplicar a mesma exclusão.

# 7. Critérios de Revisão

Uma entrega só é aprovada, do ponto de vista de documentação, quando:

1. nenhuma mudança de comportamento tiver sido implementada sem contrato previamente atualizado;
2. nenhum documento de contrato tiver sido alterado silenciosamente durante a implementação;
3. todo conflito entre código e documento tiver sido registrado, e não resolvido por conta própria;
4. toda divergência conhecida estiver registrada no relatório e, quando aplicável, marcada no documento;
5. toda decisão técnica relevante possuir ADR anterior à implementação;
6. nenhuma ADR aprovada tiver sido alterada sem registro de substituição;
7. toda rota nova possuir contrato documentado com entrada, saída, erros, escopo e autorização;
8. toda descoberta sobre a Conta Azul estiver documentada com evidência antes de virar código;
9. todo job e toda fila novos estarem documentados com gatilho, idempotência e política de erro;
10. toda variável de ambiente nova estar em `.env.example` e no documento aplicável;
11. o `README.md` continuar sendo ponto de entrada, sem duplicar conteúdo de `docs/`;
12. nenhum documento conter segredo, credencial, IP real ou dado real de cliente;
13. os comentários adicionados explicarem o porquê, e não o quê;
14. nenhum comentário desatualizado ter permanecido no código alterado;
15. nenhum código comentado ter sido deixado no lugar de removido;
16. as pendências registradas informarem motivo e critério de resolução;
17. a terminologia estar consistente com o restante do projeto;
18. capítulos novos da série 09 seguirem o cabeçalho e as nove seções;
19. o índice em `docs/09-padroes-de-codigo.md` refletir os documentos existentes;
20. o relatório final listar explicitamente os documentos criados e alterados.

# 9. Diretriz Final

Neste projeto, a documentação vem antes por uma razão prática, e não por formalismo: **decidir é mais barato do que desfazer**.

Três frases resumem o padrão:

**O documento é o contrato; o código é a implementação do contrato.** Quando divergem, o código está errado ou a decisão mudou — e mudar a decisão é um ato explícito, registrado, nunca um efeito colateral de uma implementação.

**Comportamento muda no documento primeiro.** Atualizar o contrato, implementar, validar contra o contrato. Nessa ordem, sempre.

**Documentação divergente conhecida e não registrada é a pior falha possível deste documento.** Um documento ausente obriga a perguntar. Um documento errado convence.

Se, ao final de qualquer fase, um leitor novo puder confiar integralmente nos documentos de `docs/` para entender o que o Dashboard Economização faz e por quê, este padrão cumpriu seu papel. Se precisar abrir o código para descobrir a verdade, não cumpriu.
