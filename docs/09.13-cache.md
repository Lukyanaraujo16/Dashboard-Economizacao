# Dashboard Economização

# 09.13 — Cache

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define o padrão oficial de uso de cache no Dashboard Economização.

A plataforma utiliza Redis, conforme ADR-009, com responsabilidades de infraestrutura para as filas, cache, coordenação de jobs e apoio a bloqueios e estados efêmeros. A mesma ADR estabelece que o Redis não será fonte definitiva de dados financeiros.

Cache existe para reduzir processamento repetido e melhorar o tempo de resposta de indicadores, gráficos e listagens. Ele não existe para guardar verdade.

Este documento estabelece:

- que o cache é otimização, e o PostgreSQL permanece a fonte persistente de verdade;
- a obrigatoriedade do tenant em toda chave;
- as regras de TTL, invalidação e proteção contra avalanche de recomputação;
- quais dados são apropriados e quais são inapropriados para cache;
- o comportamento obrigatório quando o cache falha, esvazia ou é perdido.

As duas regras centrais deste documento são:

> **Cache é otimização. O banco de dados permanece a fonte de verdade, conforme ARQ-024.**

> **Toda chave de cache que contenha dado de empresa deverá incluir o tenant, conforme `docs/09.9-multiempresa.md`.**

Perder o Redis inteiro deverá custar desempenho, e jamais correção.

# 3. Regras Obrigatórias

## 3.1 Cache é otimização

Regras obrigatórias, conforme ARQ-024 e `docs/02-arquitetura.md` §44:

1. Cache poderá ser utilizado para reduzir processamento e melhorar o tempo de resposta.
2. Cache nunca poderá ser a única fonte persistente de qualquer dado.
3. Nenhuma funcionalidade poderá depender da existência de uma entrada de cache para funcionar corretamente.
4. Toda leitura com cache deverá possuir caminho de origem funcional, capaz de produzir o mesmo resultado sem o cache.
5. O sistema deverá permanecer íntegro caso o Redis seja perdido, reiniciado ou esvaziado, conforme `docs/02-arquitetura.md` §44.
6. Nenhum dado deverá existir exclusivamente no cache; escrita de negócio vai para o PostgreSQL.
7. Cache nunca deverá ser utilizado como fila de trabalho improvisada; filas são responsabilidade do BullMQ, conforme ADR-010.
8. Cache não é banco de sessão de negócio nem repositório de estado crítico; estados efêmeros permitidos estão descritos em 3.15.

## 3.2 O banco permanece a fonte de verdade

Regras obrigatórias:

1. O PostgreSQL é a fonte autoritativa de todo dado financeiro, cadastral, analítico e de auditoria.
2. Divergência entre cache e banco resolve-se sempre a favor do banco.
3. Um número apresentado ao usuário deverá ser reproduzível a partir do banco, com as mesmas regras do Motor Analítico, conforme `docs/09.6-api.md` 3.11.
4. Reprocessamento, recálculo, reconciliação e conferência deverão ler do banco, e nunca do cache.
5. Relatórios oficiais e exportações deverão derivar dos dados persistidos; o cache poderá acelerar etapas intermediárias, sem alterar o resultado.
6. Auditoria e histórico de sincronização nunca poderão residir no cache.
7. Uma resposta servida do cache deverá ser indistinguível, em conteúdo, da resposta calculada na origem, exceto pela idade permitida pelo TTL.

## 3.3 Tenant obrigatório na chave

Esta seção aplica `docs/09.9-multiempresa.md` 3.10, documento prevalente.

Regras obrigatórias:

1. Toda chave que contenha dado de empresa deverá incluir o `tenantId`.
2. A composição da chave deverá ser centralizada em função utilitária; escrever chave manualmente é proibido.
3. A chave deverá incluir todos os fatores que alteram o resultado: recurso, período, filtros, ordenação, granularidade, versão do formato e perfil quando relevante.
4. Cache de dado financeiro nunca poderá ser compartilhado entre empresas, mesmo quando os valores coincidirem.
5. A invalidação deverá ser possível por empresa, sem afetar as demais.
6. Uma colisão de chave nunca poderá, em nenhuma hipótese, expor dados de outra empresa.
7. Entradas de cache que não pertençam a nenhuma empresa — como configuração global da plataforma — deverão viver em namespace próprio, explicitamente global, jamais misturado ao namespace de tenants.
8. Em modo suporte, a chave utilizada é a do tenant acessado; o operador nunca deverá possuir cache próprio contendo dados daquela empresa.

## 3.4 Estrutura da chave

Formato obrigatório, da esquerda para a direita:

```
{app}:{env}:{schemaVersion}:t:{tenantId}:{dominio}:{recurso}:{discriminadores}
```

Regras obrigatórias:

1. `app` e `env` isolam ambientes que porventura compartilhem instância; produção e homologação nunca poderão colidir.
2. `schemaVersion` deverá ser incrementada sempre que o formato serializado mudar, tornando entradas antigas inalcançáveis sem necessidade de limpeza manual.
3. O segmento `t:{tenantId}` deverá aparecer sempre na mesma posição, permitindo varredura e invalidação por prefixo de empresa.
4. Discriminadores longos, como conjuntos extensos de filtros, deverão ser reduzidos por resumo determinístico, e nunca por concatenação livre de entrada do usuário.
5. Entrada de usuário nunca poderá compor chave sem sanitização, conforme `docs/09.8-seguranca.md` 3.14.
6. A chave não deverá conter dado pessoal, nome de empresa, documento fiscal, valor financeiro ou qualquer conteúdo sensível legível.
7. Chaves deverão ser previsíveis para a aplicação e opacas para o usuário; nenhum valor de chave deverá ser exposto pela API.
8. Comando de varredura bloqueante sobre todo o espaço de chaves é proibido em produção; a remoção por prefixo deverá usar iteração incremental.

## 3.5 TTL

Regras obrigatórias:

1. Toda entrada deverá possuir TTL; entrada sem expiração é proibida, salvo estados efêmeros de coordenação com expiração própria definida em 3.15.
2. O TTL deverá ser escolhido a partir da tolerância de desatualização do dado, e não por conveniência.
3. Dados que mudam apenas após sincronização poderão ter TTL maior; dados que mudam por ação direta do usuário deverão ter TTL curto e invalidação explícita.
4. O TTL nunca deverá exceder o intervalo em que uma desatualização seria percebida como erro pelo usuário.
5. TTL deverá receber variação aleatória quando muitas chaves forem criadas no mesmo instante, evitando expiração em bloco.
6. Prolongar TTL indefinidamente para "melhorar o desempenho" é proibido: isso transforma cache em fonte de dado.
7. Valores de TTL deverão ser definidos em configuração central por tipo de recurso, e não espalhados por literais no código.

TTLs de referência aprovados:

| Conteúdo | TTL de referência | Justificativa |
|---|---|---|
| Indicadores consolidados da dashboard | 5 a 15 minutos | Mudam apenas após sincronização |
| Séries temporais de gráficos | 5 a 15 minutos | Mesmo ciclo dos indicadores |
| Agregações de período fechado | Horas | Dado histórico estável |
| Listagens paginadas | 1 a 5 minutos | Alta variação e baixo ganho |
| Configuração de branding do tenant | 5 a 30 minutos, com invalidação na alteração | Muda por ação administrativa |
| Estado operacional da integração | 1 a 5 minutos | Precisa refletir a realidade rapidamente |
| Resultado de contagem para badge | 1 a 5 minutos | Tolerante a leve atraso |

## 3.6 Invalidação

Regras obrigatórias:

1. Toda escrita que altere dado refletido em cache deverá invalidar as entradas correspondentes daquela empresa.
2. A invalidação deverá ocorrer após a confirmação da transação no banco, e nunca antes.
3. A invalidação deverá ser feita por função utilitária central, coerente com a função de composição de chave.
4. Deverá existir invalidação por empresa, capaz de limpar todo o namespace de um tenant.
5. O cache analítico daquela empresa deverá ser invalidado quando o recálculo analítico terminar, e não meramente ao fim da sincronização: a conclusão da sincronização apenas enfileira a análise, e é `AnalyticsCompleted`, conforme `docs/09.16-eventos.md` 4.8.2, que torna os indicadores em cache obsoletos. Sincronização concluída sem mudança relevante não encadeia recálculo e, portanto, não invalida o cache analítico.
6. Alteração de branding, de configuração do Consultor, de usuário e de integração deverá invalidar as entradas relacionadas daquela empresa.
7. Quando a invalidação precisa for complexa, é preferível reduzir o TTL ou versionar o namespace do recurso a manter entrada possivelmente incorreta.
8. Falha na invalidação deverá ser registrada, conforme `docs/09.11-logs.md`, e nunca ignorada silenciosamente.
9. Invalidação nunca poderá atravessar empresas: limpar o cache de uma empresa jamais deverá afetar outra.
10. Esvaziar todo o Redis nunca deverá ser procedimento de rotina da aplicação; é operação de infraestrutura, consciente e registrada.

## 3.7 Recomputação simultânea

Quando uma chave popular expira, muitas requisições simultâneas podem tentar recalcular o mesmo resultado, sobrecarregando o banco no pior momento possível.

Regras obrigatórias:

1. Cálculos caros — indicadores consolidados, séries temporais, agregações amplas — deverão ser protegidos contra recomputação simultânea.
2. A proteção deverá utilizar bloqueio de curta duração por chave, com expiração própria, garantindo que um bloqueio esquecido não trave a funcionalidade.
3. A chave do bloqueio deverá incluir o tenant, conforme `docs/09.9-multiempresa.md` 3.11.
4. Requisições concorrentes deverão aguardar por tempo limitado e, esgotado esse tempo, seguir para a origem em vez de falhar.
5. Quando aceitável para o produto, deverá ser possível servir o valor expirado enquanto a recomputação ocorre em segundo plano, desde que a idade do dado seja conhecida e limitada.
6. O TTL de conjuntos grandes de chaves criados simultaneamente deverá receber variação aleatória.
7. Falha ao obter bloqueio nunca poderá resultar em erro para o usuário; o caminho de origem permanece disponível.
8. O aquecimento de cache, quando existir, deverá ser executado por job por empresa, e nunca por varredura global compartilhando estado, conforme `docs/09.9-multiempresa.md` 3.11.

## 3.8 Dados apropriados

São apropriados para cache:

1. indicadores consolidados da dashboard, por empresa e período;
2. séries temporais de gráficos já calculadas;
3. agregações de períodos fechados;
4. resultados determinísticos e caros de recalcular;
5. configuração de branding resolvida do tenant;
6. metadados de listas estáveis, como categorias e formas de recebimento;
7. estado operacional da integração, com TTL curto;
8. contagens para indicadores visuais, como notificações não lidas;
9. resultados de consultas repetidas com alta taxa de acerto e baixa volatilidade;
10. controle de limitação de requisições e bloqueios de coordenação, com regras próprias descritas em 3.15.

Critério geral: o dado é caro de produzir, é lido muitas vezes e tolera uma janela conhecida de desatualização.

## 3.9 Dados inapropriados

São inapropriados para cache:

1. qualquer dado que exista somente no cache;
2. registros de auditoria;
3. histórico de sincronizações;
4. resultado destinado a relatório oficial ou exportação, quando o TTL puder torná-lo inconsistente com o dado apresentado na tela;
5. decisão de autorização, vínculo de usuário com empresa e perfil efetivo, conforme 3.12;
6. tokens do Conta Azul, segredos e chaves de API, conforme 3.13;
7. senha, hash de senha e qualquer credencial;
8. conteúdo integral de conversas com o Consultor, quando o histórico persistido for a fonte;
9. dados de baixa reutilização, cuja produção é barata;
10. resultados que dependam de horário corrente sem discriminador de tempo na chave;
11. estados intermediários de escrita, que induzam decisão de negócio a partir de valor não confirmado;
12. qualquer estrutura sem tenant que possa vir a conter dado de empresa.

Regra final desta seção: na dúvida, não cachear. O custo de não cachear é desempenho; o custo de cachear errado pode ser correção ou isolamento.

## 3.10 Perda, indisponibilidade e cache frio

Regras obrigatórias:

1. A indisponibilidade do Redis nunca poderá impedir a leitura de dado financeiro; a aplicação deverá recorrer à origem, conforme `docs/09.10-tratamento-de-erros.md` 3.16.
2. Toda operação de cache deverá possuir tempo máximo de espera curto; o cache jamais poderá ser mais lento do que a origem que ele deveria evitar.
3. Falha ao ler do cache deverá ser tratada como ausência de valor, registrada em nível de atenção e nunca propagada como erro ao usuário.
4. Falha ao gravar no cache deverá ser registrada e ignorada quanto ao resultado da operação, que já foi produzido pela origem.
5. Reinício, esvaziamento ou perda total do Redis deverão produzir apenas degradação de desempenho.
6. Operações que dependem estruturalmente do Redis, como enfileiramento de jobs e bloqueios, deverão informar indisponibilidade temporária de forma explícita, e nunca simular sucesso.
7. O sistema deverá suportar partida com cache frio sem tempestade de recomputação, aplicando as proteções da seção 3.7.
8. Nenhum procedimento de recuperação de incidente poderá depender de dados presentes apenas no cache.

## 3.11 Serialização e limites

Regras obrigatórias:

1. O valor armazenado deverá ser serializado em formato estável e versionado pelo segmento `schemaVersion` da chave.
2. Valores monetários deverão preservar exatidão decimal, conforme `docs/09.6-api.md` 3.10; serializar dinheiro como número de ponto flutuante binário é proibido.
3. Datas e instantes deverão ser serializados em ISO 8601 com fuso explícito.
4. Toda leitura deverá validar a forma do valor desserializado antes do uso; conteúdo inesperado deverá ser tratado como ausência de cache.
5. Valores muito grandes não deverão ser armazenados; quando o resultado for extenso, deverá ser cacheada a agregação, e não a coleção completa.
6. Deverá existir política de memória definida na infraestrutura, com remoção previsível de entradas quando o limite for atingido.
7. A aplicação deverá funcionar corretamente quando uma entrada for removida antes do TTL por pressão de memória.
8. Estruturas de dados do Redis deverão ser escolhidas conscientemente; nenhuma estrutura deverá crescer indefinidamente sem expiração ou limite.

## 3.12 Cache nunca é mecanismo de autorização

Regras obrigatórias:

1. Cache nunca poderá ser utilizado como mecanismo de autorização.
2. A presença de uma chave, o acerto de cache ou o conhecimento de um identificador jamais poderão substituir a verificação de acesso no backend.
3. A resolução do contexto de tenant deverá ocorrer antes de qualquer consulta ao cache, e a chave deverá ser composta com o tenant já validado.
4. É proibido armazenar decisão de autorização, lista de permissões, vínculo de usuário com empresa ou perfil efetivo como verdade de cache.
5. Se, por necessidade comprovada de desempenho, um dado de sessão for mantido em cache, ele deverá ter validade curta, ser invalidado imediatamente em alteração de perfil, desativação de usuário, desativação de empresa, logout e revogação de sessão, e nunca prevalecer sobre o estado do banco.
6. Revogação de acesso nunca poderá depender apenas da expiração natural de uma entrada de cache.
7. Cache nunca deverá ser consultado antes da autorização de modo que a resposta seja servida a quem não teria direito de obtê-la da origem.
8. Em qualquer conflito entre desempenho e verificação de acesso, a verificação prevalece; a regra pertence a `docs/09.9-multiempresa.md`, documento prevalente.

## 3.13 Segredos e cache

Regras obrigatórias:

1. Segredo nunca deverá ser colocado em chave nem em valor de cache sem necessidade real e justificada.
2. É proibido armazenar em cache: senha, hash de senha, `client_secret`, chave de API do provedor de IA e credenciais de infraestrutura.
3. `access token` e `refresh token` do Conta Azul pertencem ao armazenamento protegido definido em `docs/09.8-seguranca.md` 3.4, e não ao cache de aplicação.
4. Se, por decisão técnica justificada, um token de curta duração for mantido em memória compartilhada, ele deverá ter validade menor que a do próprio token, ser vinculado explicitamente à empresa, jamais aparecer em log, jamais compor chave legível e ser invalidado na desconexão da integração.
5. Nenhum valor de chave e nenhum conteúdo de cache poderá ser exposto pela API, nem por endpoint administrativo, nem por telemetria.
6. Painéis e ferramentas de inspeção do Redis nunca deverão ser expostos publicamente, conforme `docs/09.8-seguranca.md` 3.7.
7. Se um segredo for encontrado no cache, ele deverá ser considerado comprometido e rotacionado.

## 3.14 Cache no frontend e estado do cliente

Regras obrigatórias:

1. Cache do navegador, cache de biblioteca de dados, memória de componente e estado global deverão ser tratados com o mesmo rigor do cache distribuído, conforme `docs/09.9-multiempresa.md` 3.10.
2. Nenhum dado financeiro deverá ser persistido em armazenamento local do navegador sem necessidade, conforme `docs/09.8-seguranca.md` 3.12.
3. A chave de cache do cliente deverá incluir a empresa em contexto, evitando que a troca de contexto exiba dados anteriores.
4. Logout, entrada em modo suporte e saída de modo suporte deverão descartar integralmente o estado do cliente.
5. O frontend nunca deverá utilizar cache local para contornar erro de autorização retornado pela API.
6. Respostas contendo dados de empresa não deverão ser armazenadas por camadas intermediárias de rede; a resposta deverá indicar que é privada e não armazenável.
7. Indicadores exibidos a partir de cache local deverão respeitar o mesmo princípio de correção: na dúvida, buscar novamente.

## 3.15 Coordenação, bloqueios e estados efêmeros

O Redis também sustenta filas, bloqueios e estados efêmeros, conforme ADR-009 e ADR-010. Esses usos não são cache, mas compartilham a mesma infraestrutura.

Regras obrigatórias:

1. Chaves de bloqueio, idempotência, deduplicação e limitação de requisições deverão incluir o tenant, conforme `docs/09.9-multiempresa.md` 3.11.
2. Todo bloqueio deverá possuir expiração própria, garantindo liberação mesmo após falha do processo detentor.
3. Bloqueio nunca deverá ser utilizado como garantia transacional de dado financeiro; consistência de escrita pertence ao PostgreSQL.
4. Estados efêmeros do fluxo OAuth deverão ser de uso único, de validade curta e vinculados à empresa, conforme `docs/09.8-seguranca.md` 3.5.
5. Namespaces de cache, de filas e de coordenação deverão ser separados, para que uma limpeza de cache jamais afete filas ou bloqueios.
6. Nenhum job poderá depender de uma entrada de cache para saber o que processar; o payload e o banco definem o trabalho.
7. Contadores de limitação de requisições poderão viver no Redis; sua perda deverá resultar em liberação temporária, e nunca em bloqueio permanente indevido.

## 3.16 Observabilidade e testes

Regras obrigatórias:

1. Deverão ser observáveis, conforme `docs/09.11-logs.md`: indisponibilidade do cache, invalidações relevantes e falhas de leitura ou escrita.
2. Taxa de acerto por tipo de recurso deverá poder ser acompanhada; cache com taxa de acerto baixa é custo sem benefício e deverá ser removido ou revisto.
3. Registro de operação de cache nunca deverá conter o conteúdo cacheado nem a chave completa quando ela contiver discriminadores sensíveis.
4. Deverá existir teste que verifique que a mesma consulta, executada por duas empresas diferentes, produz chaves distintas e resultados distintos.
5. Deverá existir teste que verifique que a funcionalidade produz o mesmo resultado com o cache desabilitado.
6. Deverá existir teste que verifique a invalidação após escrita relevante.
7. A base de teste deverá conter pelo menos duas empresas, conforme `docs/09.9-multiempresa.md` 3.15.
8. Ambiente de desenvolvimento deverá permitir desligar o cache por configuração, sem alteração de código.

# 4. Padrões Aprovados

## 4.1 Decisões vigentes

| Item | Padrão aprovado | Origem |
|---|---|---|
| Tecnologia | Redis | ADR-009 |
| Papel | Cache, coordenação de jobs, bloqueios e estados efêmeros | ADR-009 |
| Autoridade | Redis não é fonte definitiva de dados financeiros | ADR-009, ARQ-024 |
| Integridade | Sistema íntegro após perda do cache | `02` §44 |
| Isolamento | Toda chave com dado de empresa contém o tenant | `02` §45, `09.9` 3.10 |
| Colisão | Colisão de chave jamais poderá expor outra empresa | `02` §45 |
| Filas | BullMQ sobre Redis, em namespace próprio | ADR-010 |
| Exposição | Redis nunca exposto publicamente | `09.8` 3.7 |

## 4.2 Composição de chave

```ts
type PartesDaChave = {
  tenantId: string;
  dominio: 'analytics' | 'config' | 'integracao' | 'notificacoes';
  recurso: string;
  discriminadores?: Record<string, string | number | boolean | undefined>;
};

const PREFIXO = `deco:${config.env}:v${CACHE_SCHEMA_VERSION}`;

export function chaveDoTenant(partes: PartesDaChave): string {
  const base = `${PREFIXO}:t:${partes.tenantId}:${partes.dominio}:${partes.recurso}`;
  const discriminador = resumirDeterministicamente(partes.discriminadores); // ordenado e sanitizado
  return discriminador ? `${base}:${discriminador}` : base;
}

export function prefixoDoTenant(tenantId: string): string {
  return `${PREFIXO}:t:${tenantId}:`;
}

export function chaveGlobal(dominio: string, recurso: string): string {
  return `${PREFIXO}:global:${dominio}:${recurso}`; // namespace explicitamente sem tenant
}
```

O tenant é parâmetro obrigatório do tipo. Não existe caminho conveniente para esquecê-lo.

## 4.3 Leitura com origem sempre disponível

```ts
export async function comCache<T>(
  chave: string,
  ttlSegundos: number,
  origem: () => Promise<T>,
  validar: (valor: unknown) => valor is T,
): Promise<T> {
  try {
    const bruto = await redis.get(chave); // cliente com timeout curto
    if (bruto) {
      const valor = desserializar(bruto);
      if (validar(valor)) return valor;      // forma inesperada é tratada como ausência
    }
  } catch (causa) {
    logger.warn({ err: causa, recurso: 'cache' }, 'cache_indisponivel'); // nunca propaga
  }

  const valor = await origem();               // a origem é sempre capaz de responder

  try {
    const ttl = ttlSegundos + Math.floor(Math.random() * Math.min(60, ttlSegundos * 0.1));
    await redis.set(chave, serializar(valor), 'EX', ttl);
  } catch (causa) {
    logger.warn({ err: causa, recurso: 'cache' }, 'cache_escrita_falhou');
  }

  return valor;
}
```

Falha de cache é atenção, nunca erro do usuário.

## 4.6 Proteção contra recomputação simultânea

```ts
export async function comCacheProtegido<T>(
  chave: string,
  ttlSegundos: number,
  origem: () => Promise<T>,
): Promise<T> {
  const emCache = await lerComSeguranca<T>(chave);
  if (emCache) return emCache;

  const chaveDeBloqueio = `${chave}:lock`;          // mesmo prefixo, logo mesmo tenant
  const obteveBloqueio = await redis.set(chaveDeBloqueio, '1', 'NX', 'EX', 30);

  if (!obteveBloqueio) {
    const valorTardio = await aguardarValor<T>(chave, { tempoMaximoMs: 2_000 });
    if (valorTardio) return valorTardio;
    return origem();                                 // nunca falha por causa do bloqueio
  }

  try {
    const valor = await origem();
    await gravarComSeguranca(chave, valor, ttlSegundos);
    return valor;
  } finally {
    await redis.del(chaveDeBloqueio);                // e o bloqueio ainda expira sozinho
  }
}
```

## 4.7 Matriz de decisão

| Pergunta | Se a resposta for não |
|---|---|
| O dado é caro de produzir? | Não cachear |
| Ele é lido muitas vezes? | Não cachear |
| Ele tolera desatualização por um TTL conhecido? | Não cachear |
| A chave inclui o tenant e todos os discriminadores? | Corrigir antes de cachear |
| Existe caminho de origem funcional sem o cache? | Não cachear |
| A invalidação é possível por empresa? | Reduzir TTL ou versionar o namespace |
| O conteúdo está livre de segredo e de decisão de autorização? | Não cachear |

# 5. Padrões Proibidos

É proibido:

1. utilizar cache como fonte definitiva de dado, contrariando ARQ-024;
2. manter qualquer dado exclusivamente no Redis;
3. depender de entrada de cache para que uma funcionalidade produza resultado correto;
4. compor chave de cache sem o `tenantId` quando houver dado de empresa;
5. escrever chave manualmente, fora da função utilitária central;
6. compartilhar entrada de cache entre empresas, ainda que os valores coincidam;
7. invalidar cache de uma empresa afetando outra;
8. criar chave sem ambiente e sem versão de formato no prefixo;
9. compor chave com entrada de usuário sem sanitização;
10. incluir dado pessoal, nome de empresa, valor financeiro ou segredo na chave;
11. armazenar entrada sem TTL, fora dos estados efêmeros previstos;
12. prolongar TTL para mascarar consulta lenta;
13. definir TTL por literal espalhado pelo código, sem configuração central;
14. criar grande volume de chaves com TTL idêntico, sem variação aleatória;
15. invalidar cache antes da confirmação da transação no banco;
16. ignorar silenciosamente falha de invalidação;
17. executar varredura bloqueante do espaço de chaves em produção;
18. esvaziar todo o Redis como procedimento de rotina da aplicação;
19. permitir recomputação simultânea de cálculo caro sem proteção;
20. fazer o usuário falhar porque não foi possível obter bloqueio;
21. usar bloqueio de cache como garantia transacional de dado financeiro;
22. utilizar cache como mecanismo de autorização;
23. armazenar decisão de autorização, perfil efetivo ou vínculo de usuário com empresa como verdade de cache;
24. consultar cache antes de resolver e validar o contexto de tenant;
25. depender da expiração natural de cache para revogar acesso;
26. armazenar senha, hash, `client_secret` ou chave de API em cache;
27. armazenar tokens do Conta Azul no cache de aplicação em lugar do armazenamento protegido;
28. expor valor de chave, conteúdo de cache ou painel de inspeção do Redis;
29. cachear registros de auditoria ou histórico de sincronização;
30. cachear coleções extensas em vez de agregações;
31. serializar valor monetário com perda de precisão;
32. usar valor desserializado sem validar sua forma;
33. deixar operação de cache sem tempo máximo de espera;
34. propagar falha de cache como erro ao usuário;
35. usar o mesmo namespace para cache, filas e bloqueios;
36. usar o Redis como fila improvisada em vez do BullMQ;
37. manter dados da empresa anterior no cliente após logout ou saída do modo suporte;
38. usar cache local do navegador para contornar erro de autorização da API;
39. aquecer cache com varredura global compartilhando estado entre empresas;
40. entregar funcionalidade com cache sem teste que a valide com o cache desabilitado.

# 7. Critérios de Revisão

Uma alteração somente poderá ser aprovada quando todos os itens aplicáveis forem verdadeiros.

## 7.1 Eliminatórios

1. Nenhuma chave com dado de empresa dispensa o `tenantId`.
2. Nenhuma chave é composta fora da função utilitária central.
3. Nenhum dado existe exclusivamente no cache.
4. Cache não é utilizado como mecanismo de autorização.
5. Nenhum segredo, token ou credencial foi colocado em chave ou valor de cache.

## 7.2 Papel e fonte de verdade

6. Existe caminho de origem funcional sem o cache.
7. O resultado servido do cache é equivalente ao calculado na origem.
8. Relatórios, auditoria e histórico não dependem do cache.
9. A perda total do Redis causa apenas degradação de desempenho.

## 7.3 Chave e TTL

10. A chave contém aplicação, ambiente, versão de formato, tenant, domínio, recurso e discriminadores.
11. Todos os fatores que alteram o resultado estão na chave.
12. A entrada possui TTL, definido em configuração central.
13. TTL de criação em massa recebe variação aleatória.
14. Nenhum dado sensível é legível na chave.

## 7.4 Invalidação e concorrência

15. Escritas relevantes invalidam o cache correspondente, após a confirmação da transação.
16. A invalidação é possível por empresa e nunca atravessa empresas.
17. Falha de invalidação é registrada.
18. Cálculos caros estão protegidos contra recomputação simultânea, com bloqueio expirável por tenant.
19. Falha ao obter bloqueio não gera erro para o usuário.

## 7.5 Resiliência e conteúdo

20. Operações de cache possuem tempo máximo de espera curto.
21. Falha de leitura ou escrita não é propagada ao usuário.
22. O valor desserializado é validado antes do uso.
23. Valores monetários preservam exatidão decimal.
24. Coleções extensas não são cacheadas integralmente.

## 7.6 Frontend e testes

25. O estado do cliente é descartado em logout e em troca de contexto de empresa.
26. Existe teste verificando chaves e resultados distintos entre duas empresas.
27. Existe teste verificando o mesmo resultado com o cache desabilitado.
28. Existe teste de invalidação após escrita relevante.

# 9. Diretriz Final

O Dashboard Economização apresenta números que orientam decisões financeiras. Esses números precisam estar certos antes de estarem rápidos.

O cache é bem-vindo enquanto for o que ele é: uma cópia temporária, descartável e reconstruível de algo que o banco de dados já sabe.

Três compromissos deverão ser mantidos durante toda a evolução do produto:

1. **Apagar o Redis inteiro deverá custar desempenho, nunca correção.** Se alguma funcionalidade quebrar, o cache havia se tornado banco de dados, e isso é defeito.
2. **Toda chave carrega o tenant.** Uma colisão de chave jamais poderá mostrar a uma empresa o número de outra, e a forma correta de compor a chave deverá ser a única forma disponível.
3. **Cache nunca autoriza nada.** A verificação de acesso acontece antes, no backend, sobre o contexto validado; um acerto de cache não é permissão, e a expiração de uma entrada não é revogação.

Cache é um detalhe de desempenho.

Correção e isolamento são a razão de o produto existir.

Quando os dois entrarem em conflito, o cache cede.
