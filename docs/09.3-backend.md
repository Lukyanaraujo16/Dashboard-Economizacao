# Dashboard Economização

# 09.3 — Backend

Status: Ativo
Projeto: Dashboard Economização
Tipo: Padrão Oficial de Desenvolvimento

---

# 1. Objetivo

Este documento define a arquitetura interna oficial do backend do Dashboard Economização.

O backend é o **componente de autoridade** da plataforma. Ele é o único autorizado a decidir autorização, escopo de tenant, regra de negócio e cálculo de indicador financeiro. Nenhuma outra parte do sistema — nem o frontend, nem o worker, nem o Consultor Financeiro Inteligente — pode assumir essas responsabilidades.

O framework oficial é **Fastify com TypeScript**, conforme ADR-032.

O backend é uma aplicação **separada do Next.js**, conforme ADR-006. As API Routes do Next.js não constituem o núcleo da aplicação.

Este documento define as camadas internas, o fluxo obrigatório de uma requisição, a fronteira de cada camada e o que cada camada tem proibido conhecer.

---

# 2. Escopo

Este documento regula:

- a estrutura interna de `backend/` e de cada módulo;
- as camadas: rotas/controllers, serviços/casos de uso, domínio, repositórios, schemas, DTOs, adapters, integrações, infraestrutura;
- o fluxo conceitual obrigatório de uma requisição;
- a responsabilidade e as proibições de cada camada;
- o isolamento das integrações externas, em especial a Conta Azul;
- a relação entre o backend e o processo de worker;
- o ponto obrigatório de validação de tenant;
- a inicialização, o encerramento e a observabilidade do processo.

Este documento não regula:

- o formato dos contratos HTTP e o versionamento da API — ver `09.6-api.md`;

# 3. Regras Obrigatórias

## 3.1 Framework único

O backend utilizará Fastify. Nenhum framework HTTP adicional deverá ser introduzido.

É proibido:

- adicionar Express, Koa, Hapi ou NestJS ao lado do Fastify;
- introduzir contêiner de injeção de dependência (`tsyringe`, `inversify`) sem ADR;
- introduzir camada de mediator, event bus interno, CQRS ou event sourcing sem ADR;
- introduzir um segundo ORM ao lado do Prisma;
- introduzir GraphQL sem ADR.

O motivo da escolha do Fastify na ADR-032 foi explicitamente evitar excesso de abstração. Reintroduzir abstração de framework por conta própria anula a decisão.

Plugins do ecossistema Fastify são permitidos quando resolvem um problema concreto e são registrados como dependência explícita.

## 3.2 Fluxo conceitual obrigatório

Toda requisição protegida deverá seguir exatamente esta ordem:

```
Requisição HTTP
    ↓
Validação de entrada (schema)
    ↓
Autenticação (identidade do operador)
    ↓
Autorização + resolução do escopo de tenant
    ↓
Serviço / Caso de uso
    ↓
Domínio (regra de negócio)
    ↓
Repositório / Integração / Fila
    ↓
Mapeamento para DTO de resposta
    ↓
Resposta HTTP
```

Nenhuma etapa deverá ser saltada. Em particular:

- não existe acesso a repositório antes da resolução do escopo de tenant;
- não existe execução de regra de negócio antes da autorização;
- não existe resposta que devolva entidade de persistência sem passar por mapeamento.

## 3.3 Validação de tenant sempre no backend

O escopo de tenant é resolvido exclusivamente no backend, a partir da identidade autenticada, conforme ARQ-002 e seção 4.3 de `02-arquitetura.md`.

Regras:

1. um `tenantId` recebido do frontend nunca é confiável; ele é sempre verificado contra as autorizações da identidade autenticada;
2. a resolução produz um `TenantId` validado, disponível no contexto da requisição;
3. toda consulta a dado pertencente a empresa deverá ser filtrada por esse `TenantId` validado;
4. nenhuma camada abaixo do serviço pode "escolher" o tenant; ela apenas recebe o escopo já resolvido;
5. operações de superadministrador que atravessam a fronteira de tenant deverão ser explícitas, nomeadas como tal e auditadas (ARQ-019, ARQ-021);
6. em modo suporte, o contexto deverá preservar a identidade real do operador, além do tenant acessado (ARQ-020).

Uma rota que não declara seu requisito de escopo é considerada erro de implementação, não descuido.

Em qualquer questão de isolamento entre empresas, `09.9-multiempresa.md` é o documento prevalente; esta seção descreve como o backend o implementa e nunca o flexibiliza.

## 3.4 Controller não contém regra de negócio

O controller (handler de rota) tem exatamente quatro responsabilidades:

1. receber a entrada já validada pelo schema da rota;
2. montar o objeto de entrada do caso de uso, incluindo o contexto autenticado;
3. invocar um único caso de uso;
4. mapear o resultado para o DTO de resposta e definir o código de status.

O controller **não pode**:

- executar condicional de negócio;
- calcular valor financeiro;
- decidir permissão;
- acessar Prisma;
- acessar Redis;
- enfileirar job diretamente;
- chamar dois ou mais casos de uso para compor um resultado;
- montar consulta.

Se um handler precisa de mais de uma chamada de caso de uso para responder, a composição pertence a um novo caso de uso. Orquestração é regra, e regra não vive no controller.

Limite operacional de revisão: um handler com mais de aproximadamente 25 linhas ou com qualquer `if` de negócio deverá ser refatorado.

## 3.5 Repositório não decide autorização

O repositório executa persistência e leitura. Ele não interpreta permissão.

O repositório **não pode**:

- verificar papel de usuário;
- decidir se o operador pode acessar um tenant;
- aplicar regra de negócio;
- calcular indicador;
- lançar erro de autorização.

O repositório **deve**:

- receber o `TenantId` validado como parâmetro explícito e aplicá-lo como filtro obrigatório;
- retornar `T | null` para busca que não encontrou registro;
- retornar tipos de domínio, não entidades brutas do Prisma, em sua interface pública;
- ser o único ponto do módulo que conhece o Prisma Client.

A distinção é fundamental: o repositório **aplica** o escopo de tenant recebido; ele não **decide** qual escopo é permitido. A decisão pertence à camada de autorização; a aplicação é obrigação de toda consulta.

## 3.6 Serviço não conhece HTTP

O serviço / caso de uso coordena a execução de uma operação de negócio.

Ele **não deve** conhecer, quando isso for evitável:

- objetos `request` e `reply` do Fastify;
- códigos de status HTTP;
- headers, cookies, query strings;
- formato de rota.

O serviço recebe um objeto de entrada tipado e devolve um resultado tipado ou lança um erro de domínio. A tradução entre erro de domínio e status HTTP é responsabilidade da camada de rota e do handler global de erro.

Motivo prático: o mesmo caso de uso é invocado por uma rota HTTP e por um job do worker (ADR-011). Se o serviço conhece HTTP, ele não é reutilizável pelo worker, e a regra acaba duplicada.

```ts
// Proibido
export async function runTenantSync(request: FastifyRequest, reply: FastifyReply) { /* ... */ }

// Obrigatório
export async function runTenantSync(input: RunTenantSyncInput): Promise<RunTenantSyncResult> { /* ... */ }
```

## 3.7 Integrações externas isoladas

Toda comunicação com sistema externo vive na camada de integração do módulo correspondente e é isolada em duas partes distintas e obrigatoriamente separadas:

**Conector** — fala o protocolo do sistema externo.

Responsabilidades: autorização OAuth, renovação de credencial, chamadas HTTP, paginação, respeito a limites da API, interpretação de erro externo, retentativa de falha transitória.

Proibições: gerar KPI, calcular indicador, executar análise financeira, conhecer regra de dashboard, persistir dado de domínio.

**Normalizador** — traduz o formato externo para o modelo interno.

Responsabilidades: mapear campos, converter unidades e formatos, mapear estados externos para uniões literais internas, decidir a forma interna do dado.

Proibições: fazer chamada de rede, conhecer o cliente HTTP, conhecer credencial.

Regra de vazamento: nenhum nome de campo, código de estado ou particularidade estrutural da Conta Azul pode existir fora do diretório de integração (ARQ-005, ARQ-006).

Todo conector de origem financeira deverá implementar o contrato interno comum `ExternalERPConnector` (seção 53 de `02-arquitetura.md`), para que a plataforma possa receber outros ERPs sem alteração do restante da aplicação.

## 3.8 Worker é processo separado

Tarefa pesada não é executada no ciclo da requisição HTTP quando pode ser processada em background, conforme ADR-011 e ADR-012.

Divisão obrigatória:

- **backend**: valida, autoriza, resolve escopo de tenant, decide que o trabalho deve ocorrer e enfileira o job com payload tipado e validado;
- **worker**: consome o job e invoca o caso de uso do backend.

Regras:

1. o payload do job contém o `TenantId` já validado e nunca depende de sessão HTTP;
2. o job é idempotente sempre que tecnicamente possível (ARQ-009, ADR-011);
3. o worker não reimplementa regra de negócio — ele orquestra e registra resultado;
4. o backend não aguarda a conclusão de um job para responder ao usuário; ele responde com o estado de aceitação e o identificador de acompanhamento;
5. sincronizações incompatíveis do mesmo tenant deverão ser coordenadas para não executar simultaneamente (seção 16 de `02-arquitetura.md`).

Operações que **devem** ser assíncronas: sincronização da Conta Azul, recálculo analítico amplo, geração de insight, geração de relatório pesado, entrega de notificação, tarefa de manutenção.

Operações que **devem** permanecer síncronas: autenticação, leitura de indicador já calculado, operação administrativa de configuração, consulta paginada de dado já persistido.

## 3.9 Nenhuma chamada síncrona à Conta Azul para renderizar tela

Rota que serve a dashboard, relatório ou Consultor Financeiro nunca deverá chamar a API da Conta Azul de forma síncrona (ARQ-003).

Essas rotas leem exclusivamente o modelo interno já sincronizado. Indisponibilidade da Conta Azul não deverá tornar indisponível dado previamente sincronizado (ARQ-023, seção 66 de `02-arquitetura.md`).

## 3.10 Fonte única de cálculo analítico

O cálculo oficial de cada indicador existe uma única vez, no domínio do módulo `analytics`.

Dashboard, relatórios e Consultor Financeiro consomem o mesmo domínio analítico (ARQ-010, ARQ-011).

É proibido:

- recalcular indicador em uma rota;
- recalcular indicador no módulo de relatórios;
- recalcular indicador ao montar contexto da IA;
- recalcular indicador no worker;
- recalcular indicador no frontend.

## 3.11 O Consultor Financeiro não decide acesso

O contexto enviado ao provedor de IA é composto **após** a validação do tenant pelo backend (ARQ-013, ARQ-014, seção 58 de `02-arquitetura.md`).

É proibido:

- enviar ao modelo dados de mais de um tenant para que ele escolha;
- permitir que prompt configurado ou base de conhecimento amplie o nível de acesso;
- deixar o modelo montar consulta livre ao banco;
- delegar cálculo financeiro determinístico ao modelo.

O módulo do Consultor recebe dados já autorizados e já calculados. Ele compõe contexto; não obtém permissão.

# 4. Padrões Aprovados

## 4.1 Estrutura de `backend/`

```
backend/
  src/
    app.ts                 → construção da instância Fastify (sem listen)
    server.ts              → bootstrap do processo (listen, sinais, encerramento)
    config/
      env.ts               → validação e exportação do ambiente tipado
      constants.ts         → constantes estáveis do backend
    http/
      plugins/             → plugins Fastify (cors, helmet, rate limit, request-id)
      hooks/               → autenticação, resolução de tenant, auditoria
      errors/              → handler global de erro e mapeamento para HTTP
      context.ts           → tipo do contexto autenticado da requisição
    infrastructure/
      prisma/              → Prisma Client e gestão de transação
      redis/               → conexão Redis e cache com escopo de tenant
      queue/               → definição de filas e publicação de jobs
      http-client/         → cliente HTTP com timeout e retentativa
      ai/                  → abstração de provedor de IA (ADR-028)
      storage/             → abstração de armazenamento de arquivo (ADR-029)
      logger/              → logger estruturado
    modules/
      auth/
      tenants/
      users/
      admins/
      branding/
      integrations/
        conta-azul/
      sync/
      analytics/
      insights/
      advisor/
      reports/
      rules/
      notifications/
      audit/
      support-mode/
    shared/
      errors/              → classes de erro de domínio do backend
      pagination/          → contratos de paginação
      period/              → resolução de período analítico
  package.json
  tsconfig.json
```

Notas:

- `app.ts` constrói a aplicação e é reutilizável em teste; `server.ts` executa o processo. Essa separação é obrigatória.
- `src/shared/` é interno ao backend e não substitui `packages/shared`, que é compartilhado entre aplicações (ver `09.1`, seção 4.5).
- os diretórios de módulo são criados conforme as fases do roadmap, não antecipadamente (ADR-035).

## 4.2 Estrutura interna de um módulo

```
modules/<feature>/
  routes/            → declaração de rotas e schemas de rota
  controllers/       → handlers finos
  services/          → casos de uso
  domain/            → regras de negócio e tipos de domínio
  repositories/      → persistência e leitura
  schemas/           → validação de entrada e de dado externo
  dto/               → mapeamento entrada/saída da fronteira HTTP
  adapters/          → tradução entre domínio e recursos externos
  jobs/              → definição de job e contrato de payload
  index.ts           → interface pública do módulo
```

Regras estruturais:

1. subdiretório só é criado quando há conteúdo real — módulo pequeno pode começar com `routes/`, `services/` e `repositories/`;
2. `index.ts` é a **única** porta de entrada do módulo para outros módulos;
3. um módulo nunca importa arquivo interno de outro módulo, apenas seu `index.ts`;
4. `controllers/` pode ser fundido em `routes/` quando o handler é trivial, desde que permaneça fino;
5. `domain/` nunca importa Fastify, Prisma, Redis ou BullMQ.

## 4.3 Camada de rotas

Responsabilidade: declarar o contrato HTTP e o requisito de acesso.

Cada rota declara obrigatoriamente:

- método e caminho;
- schema de body, params, query e resposta;
- requisito de autenticação;
- requisito de escopo (tenant do usuário, administrador, superadministrador);
- handler.

O tipo de `request.body`, `request.params` e `request.query` é derivado do schema declarado. Declarar tipo manualmente em paralelo ao schema é proibido (ver `09.2`, seção 3.5).

Rotas são registradas por plugin de módulo, com prefixo próprio. Não existe arquivo central com todas as rotas do sistema.

```ts
export async function analyticsRoutes(app: FastifyInstance): Promise<void> {
  app.get('/indicators', {
    schema: getIndicatorsSchema,
    onRequest: [app.authenticate, app.requireTenantScope],
    handler: getIndicatorsHandler,
  });
}
```

## 4.4 Camada de controllers

Handler fino, conforme seção 3.4.

```ts
export async function getIndicatorsHandler(
  request: FastifyRequest<GetIndicatorsRoute>,
  reply: FastifyReply,
): Promise<void> {
  const result = await getDashboardIndicators({
    tenantId: request.tenantScope.tenantId,
    period: request.query.period,
    filters: toAnalyticsFilters(request.query),
  });

  await reply.status(200).send(toIndicatorsResponse(result));
}
```

Observe: nenhum `if`, nenhum cálculo, nenhum acesso a banco, um único caso de uso, mapeamento explícito na saída.

## 4.5 Camada de serviços / casos de uso

Responsabilidade: coordenar uma operação de negócio de ponta a ponta.

O serviço:

- recebe entrada tipada, incluindo o escopo de tenant já validado;
- invoca o domínio para aplicar regra;
- invoca repositórios, integrações e filas;
- coordena transação quando necessário;
- emite evento de auditoria quando a operação é auditável (ARQ-019);
- devolve resultado tipado ou lança erro de domínio.

O serviço **não**:

- conhece HTTP;
- conhece Prisma diretamente — ele usa repositórios;
- monta SQL ou consulta;
- decide status de resposta.

Nomenclatura oficial: um verbo de negócio por caso de uso — `runTenantSync`, `connectContaAzulIntegration`, `getDashboardIndicators`, `generateFinancialReport`, `answerAdvisorQuestion`, `enterSupportMode`.

Um arquivo por caso de uso. Serviço que acumula muitos casos de uso não relacionados deverá ser dividido.

## 4.6 Camada de domínio

Responsabilidade: as regras de negócio do Dashboard Economização.

Contém:

- cálculo oficial dos indicadores financeiros;
- regras de fluxo de caixa, inadimplência, comparativo de período e projeção;
- regras de geração e classificação de insight;
- regras de deduplicação, cooldown e severidade de alerta (seção 31 de `02-arquitetura.md`);
- políticas de idempotência de sincronização;
- invariantes das entidades internas;
- tipos de domínio.

Proibições absolutas: `import` de Fastify, Prisma, Redis, BullMQ, SDK de IA ou cliente HTTP.

Quando o domínio precisa de um recurso externo, ele declara a interface e recebe a implementação por parâmetro.

```ts
// domain/delinquency.ts — puro, testável sem infraestrutura
export function calculateDelinquency(
  entries: readonly ReceivableEntry[],
  reference: PeriodRange,
): DelinquencySummary {
  // regra oficial: fonte única para dashboard, relatórios e Consultor Financeiro
}
```

O domínio é a camada mais estável do sistema. Ela deve ser testável sem banco, sem Redis e sem rede.

## 4.7 Camada de repositórios

Responsabilidade: leitura e escrita no PostgreSQL via Prisma.

Padrões:

1. um repositório por agregado de domínio, não um repositório por tabela;
2. interface pública tipada com tipos de domínio;
3. `TenantId` como parâmetro explícito em toda operação sobre dado de empresa;
4. `T | null` para busca sem resultado;
5. retorno de coleção como `readonly T[]`;
6. paginação por contrato explícito, sem retorno ilimitado em endpoint de listagem;
7. transação recebida como parâmetro quando a operação participa de uma unidade maior;
8. escrita de dado sincronizado sempre idempotente, ancorada em identificador externo (ARQ-009, seção 54 de `02-arquitetura.md`).

```ts
export interface SyncRunRepository {
  create(input: CreateSyncRunInput, tenantId: TenantId): Promise<SyncRun>;
  findLatest(tenantId: TenantId, kind: SyncKind): Promise<SyncRun | null>;
  markCompleted(id: SyncRunId, tenantId: TenantId, summary: SyncSummary): Promise<void>;
}
```

Consulta analítica pesada pode usar SQL parametrizado quando o Prisma não expressa a agregação de forma adequada. Nesses casos, o SQL vive no repositório, é sempre parametrizado, e o filtro de tenant é obrigatório e explícito. Interpolação de valor recebido do usuário em SQL é proibida.

## 4.8 Schemas e validadores

Responsabilidade: validação em runtime de todo dado que atravessa a fronteira do processo.

Três famílias distintas, que não devem ser confundidas:

**Schemas de rota** — validam entrada HTTP e descrevem a resposta. Vivem em `modules/<feature>/schemas/`.

**Schemas de dado externo** — validam a resposta da Conta Azul e do provedor de IA. Vivem em `modules/integrations/<sistema>/schemas/`.

**Schemas de payload de job** — validam o conteúdo de job de fila. Vivem em `modules/<feature>/jobs/`.

Regras:

- o tipo estático é derivado do schema, nunca declarado em paralelo;
- schema de dado externo não é usado como tipo de domínio;
- falha de validação de entrada HTTP resulta em erro de requisição inválida com mensagem útil e sem vazamento interno;
- falha de validação de dado externo é tratada como erro de integração, registrada com contexto e sem credencial em log.

## 4.9 DTOs

DTO é a forma do dado na fronteira HTTP. Ele existe para desacoplar o contrato público do modelo interno.

Regras:

1. nenhuma entidade do Prisma é serializada diretamente na resposta;
2. o mapeamento domínio → DTO é explícito, em função nomeada (`toIndicatorsResponse`, `toTenantResponse`);
3. o DTO nunca contém campo sensível: token da Conta Azul, refresh token, hash de senha, segredo de integração, chave de provedor de IA (ARQ-022, seção 55 de `02-arquitetura.md`);
4. o DTO nunca contém nome de campo originado da Conta Azul;
5. o contrato de resposta é declarado em `packages/types` quando consumido pelo frontend.

O mapeamento explícito é o que garante a regra 3. Serialização automática de entidade acaba expondo campo novo no dia em que ele é adicionado ao schema.

## 4.10 Adapters

Adapter traduz entre o domínio e um recurso externo, implementando uma interface declarada pelo domínio ou pelo serviço.

Exemplos aprovados:

- `PrismaTenantRepository` implementando `TenantRepository`;
- `RedisTenantCache` implementando `TenantCache`;
- `BullMqQueuePublisher` implementando `QueuePublisher`;
- `OpenAiAdvisorProvider` implementando `AdvisorProvider` (ADR-028);
- `LocalFileStorage` implementando `FileStorage` (ADR-029);
- `ContaAzulConnector` implementando `ExternalERPConnector`.

Benefício concreto: a abstração de provedor de IA é exigida pela ADR-028, e a de storage pela ADR-029. Adapters são a forma pela qual essas abstrações existem no código.

Adapter não contém regra de negócio.

## 4.11 Camada de infraestrutura do backend

`src/infrastructure/` contém acesso a recurso externo ao processo:

**`prisma/`** — instância única do Prisma Client e utilitário de transação. Nenhum módulo instancia o cliente por conta própria.

**`redis/`** — conexão Redis e utilitário de cache. Toda chave de cache com dado de empresa deverá conter o `TenantId` no seu prefixo (ARQ-024, seções 44 e 45 de `02-arquitetura.md`). Cache nunca é fonte definitiva de dado financeiro; o sistema deve permanecer íntegro se o Redis for perdido.

**`queue/`** — definição das filas BullMQ, nomes de fila, política de retentativa e publicação de job. O backend publica; o worker consome.

**`http-client/`** — cliente HTTP com timeout obrigatório, retentativa controlada e limite de tentativas. Retentativa nunca cria laço infinito (seção 48 de `02-arquitetura.md`).

**`ai/`** — abstração de provedor de IA. Nenhum módulo importa o SDK do provedor diretamente.

**`storage/`** — abstração de armazenamento de arquivo para logo, relatório e anexo.

**`logger/`** — logger estruturado. Todo log carrega identificador de requisição e, quando aplicável, `tenantId`. Credencial e segredo nunca são registrados.

## 4.12 Hooks HTTP

A ordem dos hooks é parte do padrão e não deve ser alterada por rota:

1. **request id / correlação** — identificador único propagado em log e em job derivado;
2. **autenticação** — resolve a identidade do operador a partir da credencial da plataforma;
3. **autorização e escopo** — determina papel e resolve o `TenantId` autorizado;
4. **modo suporte** — quando aplicável, marca a sessão preservando a identidade real do operador (ARQ-020);
5. **auditoria** — registra a intenção de operações auditáveis (ARQ-019);
6. **handler**.

A autenticação da plataforma é independente do OAuth da Conta Azul (seção 6 de `02-arquitetura.md`). Os dois contextos nunca devem ser misturados no mesmo hook, no mesmo tipo ou no mesmo campo de sessão.

Rota pública deverá declarar explicitamente que é pública. Ausência de declaração é tratada como rota protegida — segurança por padrão (seção 2.2 de `02-arquitetura.md`).

## 4.13 Erros

Hierarquia de erro de domínio do backend, em `src/shared/errors/`:

| Classe | Significado | Status HTTP |
|---|---|---|
| `ValidationError` | entrada inválida | 400 ou 422, conforme `09.6-api.md` e `09.10-tratamento-de-erros.md` |
| `UnauthenticatedError` | identidade ausente ou inválida | 401 |
| `ForbiddenError` | identidade sem permissão para o recurso | 403 |
| `NotFoundError` | recurso inexistente no escopo do tenant | 404 |
| `ConflictError` | violação de invariante ou operação concorrente | 409 |
| `IntegrationError` | falha na comunicação com sistema externo | 503 |
| `RetryableIntegrationError` | falha transitória externa, elegível a retentativa | 503 |
| `DomainError` | violação de regra de negócio | conforme o caso |

O catálogo autoritativo de erros, códigos e mapeamento para status HTTP é o documento `09.10-tratamento-de-erros.md`. A tabela acima é a projeção desse catálogo nas classes de erro do backend; em caso de divergência, prevalece o 09.10.

Regras:

1. o mapeamento erro → status ocorre no handler global de erro, nunca espalhado nos controllers;
2. resposta de erro nunca expõe stack trace, SQL, nome de tabela, mensagem de driver ou detalhe de credencial;
3. mensagem exibida ao usuário é útil e em português; detalhe técnico vai para o log;
4. erro inesperado retorna resposta genérica e é registrado com severidade adequada;
5. um recurso de outro tenant deverá resultar em `NotFoundError`, não em `ForbiddenError` — a existência do recurso não deve ser revelada; `ForbiddenError` permanece correto quando o operador legitimamente enxerga o recurso dentro do próprio tenant e não possui permissão para aquela operação;
6. erro de integração da Conta Azul deverá distinguir falha transitória de falha permanente (seção 48 de `02-arquitetura.md`).

A regra 5 é uma decisão de segurança deliberada e deve ser respeitada mesmo quando parecer menos informativa.

## 4.14 Transações

Regras:

1. a transação é iniciada na camada de serviço, nunca no repositório e nunca no controller;
2. o escopo da transação é o menor possível;
3. chamada de rede externa nunca ocorre dentro de transação aberta;
4. chamada ao provedor de IA nunca ocorre dentro de transação aberta;
5. publicação de job ocorre após a confirmação da transação, para que o worker não consuma um estado inexistente;
6. operação de sincronização é estruturada em lotes idempotentes, não em uma transação única gigante.

## 4.15 Módulo de integração Conta Azul

Estrutura oficial:

```
modules/integrations/conta-azul/
  contracts/         → interface ExternalERPConnector
  connector/
    oauth/           → fluxo de autorização e renovação de credencial
    client/          → chamadas HTTP, paginação, limites, erros externos
  normalizer/        → tradução do formato externo para o modelo interno
  schemas/           → validação das respostas externas
  repositories/      → estado da conexão e credenciais cifradas
  services/          → conectar, desconectar, consultar estado, renovar
  index.ts
```

Regras específicas:

1. credencial da Conta Azul é armazenada de forma segura e nunca retorna ao frontend (ARQ-022);
2. credencial nunca aparece em log, nem em mensagem de erro, nem em evento de auditoria;
3. o estado operacional da conexão é modelado explicitamente e consultável (seção 50 de `02-arquitetura.md`);
4. o conector respeita os limites reais da API, que não devem ser presumidos antes de verificação da documentação oficial (seção 56 de `02-arquitetura.md`);
5. no MVP, a integração é de leitura/importação; nenhuma escrita financeira na Conta Azul é implementada (ARQ, seção 68 de `02-arquitetura.md`);
6. adicionar um novo ERP deverá exigir apenas um novo diretório com conector e normalizador implementando o contrato comum, sem alteração dos módulos de análise, relatório ou IA.

## 4.16 Módulo de sincronização

Responsabilidades: orquestrar sincronizações, registrar estado e garantir idempotência.

O registro de execução deverá conter, no mínimo: tenant, tipo, início, conclusão, status, quantidade processada, criada e atualizada, erro quando houver, origem do disparo, tentativa e duração (seção 17 de `02-arquitetura.md`).

Coordenação obrigatória: sincronizações incompatíveis do mesmo tenant não executam simultaneamente. O mecanismo de exclusão usa Redis e é sempre por tenant e por tipo.

## 4.17 Módulo do Consultor Financeiro

Fluxo obrigatório:

```
Pergunta do usuário
    ↓
Autenticação + resolução do tenant validado
    ↓
Composição de contexto (apenas dados daquele tenant)
    ↓
Provider de IA (abstração)
    ↓
Resposta persistida e vinculada a tenant e usuário
```

Regras:

1. o contexto é montado somente após validação do tenant;
2. o contexto contém o mínimo necessário — prefira agregados e indicadores a linhas brutas (seção 59 de `02-arquitetura.md`);
3. prompt configurado e base de conhecimento são tratados como entrada não confiável e nunca ampliam permissão (seção 57 de `02-arquitetura.md`);
4. cálculo financeiro determinístico não é delegado ao modelo;
5. informação inexistente é tratada como falta de informação, nunca preenchida por inferência (seção 27 de `02-arquitetura.md`);
6. insight proativo relevante é persistido, não permanece apenas como resposta efêmera (ARQ-016).

## 4.18 Inicialização e encerramento do processo

Ordem obrigatória na inicialização:

1. validar o ambiente e falhar imediatamente se estiver inválido ou incompleto;
2. construir o logger;
3. abrir conexões de infraestrutura;
4. construir a aplicação Fastify e registrar plugins, hooks e módulos;
5. expor endpoint de verificação de saúde;
6. iniciar a escuta.

Encerramento graciosos obrigatório: ao receber sinal de término, o processo deverá parar de aceitar novas requisições, aguardar a conclusão das requisições em andamento dentro de um limite, fechar conexões de banco e Redis e encerrar.

Motivo operacional: o `update.sh` (ADR-022) reinicia containers. Sem encerramento graciosos, uma atualização interrompe requisição em andamento e pode deixar sincronização em estado inconsistente.

## 4.19 Observabilidade

O backend deverá permitir responder às perguntas operacionais da seção 49 de `02-arquitetura.md`, entre elas: quantas sincronizações falharam, quais empresas estão sem sincronizar, quando cada empresa sincronizou pela última vez, quais jobs falharam, quais chamadas de IA falharam.

Isso implica registrar, de forma consultável: execuções de sincronização, estado de conexão de integração, falhas de job, latência de operação relevante e falhas de chamada externa.

Log técnico não substitui auditoria, e auditoria não substitui log técnico (seções 38 e 39 de `02-arquitetura.md`).

## 6.2 Sincronização manual disparada pelo administrador

```
POST /api/v1/integrations/conta-azul/sync

Backend:
  1. autentica o administrador
  2. autoriza a operação sobre o tenant informado
  3. verifica se já existe sincronização incompatível em andamento
  4. cria o registro de execução com origem 'manual'
  5. publica o job com payload validado, contendo o TenantId já validado
  6. responde 202 com o identificador de acompanhamento

Worker:
  1. valida o payload do job por schema
  2. invoca runTenantSync do backend
  3. registra resultado, contagens e duração

Backend (caso de uso runTenantSync):
  1. conector busca dados na Conta Azul, respeitando paginação e limites
  2. normalizador traduz para o modelo interno
  3. repositório persiste de forma idempotente por identificador externo
  4. módulo analytics recalcula dados derivados
  5. módulo rules avalia eventos e o módulo insights persiste insights
```

Observe que a resposta HTTP não aguarda a sincronização, e que o worker não contém nenhuma regra própria.

## 6.3 O que torna um controller inaceitável

```ts
// Reprovado: seis violações simultâneas
export async function getIndicatorsHandler(request: FastifyRequest, reply: FastifyReply) {
  const tenantId = request.query.tenantId;              // 1. tenant vindo do cliente
  const rows = await prisma.receivable.findMany({       // 2. Prisma no controller
    where: { tenantId },                                //    sem validação de escopo
  });
  let total = 0;
  for (const row of rows) {
    if (row.dueDate < new Date() && row.status !== 'PAID') {
      total += row.amount;                              // 3. cálculo de indicador
    }                                                   // 4. regra duplicada
  }
  if (request.user.role !== 'admin' && total > 0) {     // 5. autorização no controller
    return reply.send({ total: 0 });                    // 6. zero mascarando ausência
  }
  return reply.send(rows);                              // 7. entidade bruta na resposta
}
```

## 6.4 Fronteira entre worker e backend

```ts
// worker/src/jobs/sync/sync-tenant.job.ts — casca fina
export const syncTenantJob: JobDefinition<SyncTenantJobPayload> = {
  name: 'sync-tenant',
  schema: syncTenantJobSchema,
  async handle(payload, context) {
    const result = await runTenantSync({
      tenantId: payload.tenantId,
      trigger: payload.trigger,
      fullReload: payload.fullReload,
    });
    context.logger.info({ tenantId: payload.tenantId, result }, 'Sincronização concluída');
  },
};
```

Toda a regra vive em `runTenantSync`, no backend. O job resolve contexto, invoca e registra.

# 7. Critérios de Revisão

Um commit em `main` (ou a integração de branch de trabalho) no backend deverá ser recusado quando:

1. introduzir framework, ORM ou camada arquitetural não previsto, sem ADR;
2. mover núcleo de negócio para API Routes do Next.js;
3. colocar regra de negócio, cálculo ou condicional de negócio em controller;
4. permitir controller acessando Prisma, Redis ou fila diretamente;
5. permitir repositório decidindo autorização;
6. omitir filtro por `TenantId` validado em consulta a dado de empresa;
7. confiar em `tenantId` recebido do cliente sem verificação;
8. passar `request` ou `reply` para serviço;
9. importar Fastify, Prisma, Redis ou BullMQ dentro de `domain/`;
10. duplicar cálculo de indicador fora do domínio de `analytics`;
11. adicionar chamada síncrona à Conta Azul em rota de leitura de dashboard, relatório ou Consultor;
12. misturar responsabilidades de conector e normalizador;
13. permitir que nome de campo da Conta Azul saia da integração;
14. registrar credencial em log, auditoria ou resposta;
15. serializar entidade do Prisma diretamente, ou expor campo sensível em DTO;
16. executar tarefa pesada na requisição quando ela deveria ser job;
17. reimplementar regra no worker;
18. publicar job antes da confirmação da transação;
19. abrir transação em repositório ou controller, ou fazer chamada externa dentro dela;
20. expor detalhe interno em resposta de erro, ou revelar existência de recurso de outro tenant;
21. interpolar valor do usuário em SQL;
22. criar chave de cache de empresa sem `TenantId`;
23. importar arquivo interno de outro módulo em lugar do `index.ts`;
24. acessar tabela pertencente a outro módulo;
25. registrar rota protegida sem declarar requisito de acesso;
26. compor contexto de IA antes da validação de tenant, ou com dados de mais de um tenant;
27. delegar cálculo determinístico ao modelo de IA;
28. permitir operação de superadministrador ou modo suporte sem auditoria;
29. criar endpoint de listagem sem paginação;
30. omitir timeout em chamada externa, ou permitir retentativa sem limite;
31. remover o encerramento graciosos ou a validação de ambiente na inicialização;
32. implementar escrita financeira na Conta Azul.

Checklist objetivo de revisão de backend:

- [ ] O fluxo da seção 3.2 é respeitado integralmente.
- [ ] Handler fino, sem regra, com um único caso de uso.
- [ ] `TenantId` validado no backend e aplicado em toda consulta de empresa.
- [ ] Serviço sem conhecimento de HTTP.
- [ ] Domínio puro, sem infraestrutura.
- [ ] Repositório aplica escopo, não decide permissão.
- [ ] Dado externo validado por schema antes do uso.
- [ ] Conector e normalizador separados; nenhum campo externo vazou.
- [ ] Nenhuma credencial em log, resposta ou auditoria.
- [ ] Resposta construída por mapeamento explícito para DTO.
- [ ] Tarefa pesada enfileirada; worker sem regra própria.
- [ ] Operação auditável gerou auditoria.
- [ ] `pnpm lint`, `pnpm typecheck` e `pnpm test` passam.

# 9. Diretriz Final

O backend do Dashboard Economização é a autoridade da plataforma. Ele decide quem acessa o quê, calcula os números que o cliente vê e é o único ponto que conhece as credenciais da Conta Azul.

Essa autoridade só se sustenta com fronteiras rígidas: o controller traduz, o serviço coordena, o domínio decide a regra, o repositório persiste, o adapter conversa com o mundo externo. Quando essas fronteiras se dissolvem, a autoridade se dissolve com elas — e em uma plataforma multiempresa, isso significa risco de vazamento entre clientes e divergência entre o número da dashboard, o número do relatório e o número que a IA afirma.

O Fastify foi escolhido justamente para manter o código explícito e sem mágica. Essa escolha deve ser honrada com disciplina de camadas, e não substituída por abstração adicional.

Toda implementação de backend deverá seguir o fluxo da seção 3.2 sem exceção, e toda dúvida sobre a camada correta deverá ser resolvida por este documento antes da implementação.
